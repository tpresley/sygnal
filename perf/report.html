Sygnal Performance Audit

Benchmarked against React 19.2 and Vue 3.5 in headless Chromium 153 (Playwright, macOS). Production builds, median of 10 runs after 3 warmups.

A Sygnal app that renders a list from one component is competitive: it creates 10,000 rows faster than React. It is slow at small updates, where it is 4 to 15 times behind, and it slows down further when every list item is its own component. With Collection, a row costs about 31 KB of heap, a click can repatch the whole page a thousand times, and memory is not fully released on unmount. Most of this comes from a few places in src/component.ts and the Collection plumbing, not from xstream or snabbdom themselves.

Where it hurts

The results split into three patterns.

Small updates carry a fixed cost proportional to the whole view. Selecting one row of 1,000 takes 7.3 ms in single-component Sygnal and 0.5 ms in React; at 10,000 rows it is 44 ms against 4 ms. Every state change re-runs the full view, then walks and copies the whole vnode tree several times before snabbdom diffs it.

Component-per-item is the worst case. Mounting, unmounting, appending, and anything that touches every item (a context change, an update to 100 rows) is 5 to 100 times slower, and most of the CPU lands after the screen has already updated. Each Collection item is a full component with roughly 140 streams, and each item's render repatches the entire page.

Depth adds latency. A click 30 components deep takes 5.8 ms (React: 0.35 ms) and causes 51 DOM patches, because each level adds its own 1 ms debounce timer and its own repatch.

Root causes

Found with CDP CPU profiles of the unminified build, mapped back to src/*.ts through two source-map hops, plus instrumented counts of patches, streams, and timers, and heap-snapshot diffs.

1

No render batching across components: each child render repatches the whole app

A component's render goes through debounce(1) in collectRenderParameters, again in renderVdom, and once more in instantiateCollection. These timers are per component, so 1,000 sibling renders arrive as 1,000 separate emissions. Each one re-runs the parent's injectComponents and processSuspensePost, and the DOM driver patches from the root every time. processSuspensePost also copies every vnode that has children, including all descendants' subtrees, so snabbdom's oldVnode === vnode shortcut never applies and the full tree is diffed on each patch.

  • DOM patches per action: select row (1k Collection) 1,001; update every 10th row 102; leaf click 30 deep 51; single-component table 1.
  • Profile of Collection select: 74% of 514 ms in the DOM driver's patch; patchVnode alone 36%, processSuspensePost 7%, IsolateModule.update 7%.
  • This is also the 152 s clear: 10,000 row renders, each patching a 10,000-row tree.
src/component.ts:1160, 1361, 1614, 1768 (injectComponents), 1839 (processSuspensePost)
2

About 141 streams and 31 KB per component, torn down with one timer per stream

Every instance builds its full wiring whether it uses it or not: context, READY, children and slots, HMR actions, statics, peers, EFFECT, CHILD sources, three debounce stages, and an isolated copy of every source channel. Unmount completes the streams one setTimeout at a time, because xstream stops a stream asynchronously when its last listener goes.

  • Mounting 1,000 counters created 141,008 streams and 4,005 interval timers; heap 30.3 MB vs 2.7 MB (React) and 3.7 MB (Vue).
  • Unmounting them scheduled 74,011 setTimeout calls: 9 ms to clear the screen, 126 ms of CPU after it.
  • Mount profile: about 35% xstream construction and subscription, 10% native setTimeout.
src/component.ts:193–432 (constructor and init*), src/cycle/isolate/index.ts, xstream Stream._remove
3

Quadratic Collection plumbing

Several Collection paths do O(N) work per item, so O(N²) per state change:

  • instanceLens.get finds each item by linear scan with a string conversion, once per item per state emission.
  • fieldLense.set calls newState.find() inside a loop over every old item, on every item write.
  • fieldLense.get copies every item ({ ...item, id }) on every emission, so identity checks downstream always fail and every item runs a deep compare.
  • PickCombine.up() rebuilds the N-element array on every single item emission.
  • In "update 1 of 1k", fieldLense.set and instanceLens.get are 28% of busy time. Collection create at 10k rows is 1.46 s (React 0.25 s).
src/cycle/state/Collection.ts:65, src/component.ts:1398–1426, src/cycle/state/pickCombine.ts:108
4

Event-listener leak on unmount

Bubbling listeners registered by DOM.click(…) and friends are added to the EventDelegator's per-scope priority queues and never removed. Each disposed component keeps its ScopeChecker, its subject stream, and five enriched-stream closures (data, target, key, value, checked) per intent stream.

  • Heap diff after 5 × 1,000 counters mounted and unmounted: exactly 5,000 retained ScopeCheckers and 5,000 of each closure; the 2-stream table row retained 10,000.
  • Retained heap after cycles: 6.3 MB (counters) and 27.6 MB (Collection table), against about 2 MB for React and Vue. It grows without bound in apps whose lists churn.
src/cycle/dom/EventDelegator.ts:247 (insertListener has no removal path)
5

Per-render fixed costs in the view path

For the single-component table, half of a row select is spent creating vnodes. The JSX pragma's sanitizeData runs two mapObject passes per element, and each pass allocates an object per key and merges them with the deep-copying extend(true, …). Each render then walks the whole tree again in stampFields, preprocessVdom, getComponents, and processSuspensePost, even when the view has no components, portals, or Suspense.

  • Select row (1k, single component): pragma 48% of busy time (sanitizeData 42%, extend 9%); snabbdom 12%.
  • Experiment: replacing mapObject with a single shallow pass cut update and select time by 10–15%. Bulk create did not change (it is bound by DOM creation).
src/pragma/fn.ts:24–46, src/pragma/index.ts:144, src/component.ts:892–893, 1901, 1911
6

Latency floor from timers, and per-vnode module work

Even with little to compute, an update waits on at least two 1 ms interval timers (re-armed on every emission), more with nesting. The keystroke test is 4.35 ms latency on 2.7 ms of CPU. Snabbdom runs eight modules on every vnode of every patch; selectModule.queueSelect, controlledInputModule.syncControlled, and classNameModule.syncClassName together cost 12% of the Collection select profile, almost all of it on elements that are not form fields. Smaller costs: deep objIsEqual (depth 5) on state, props, context, and children for every component, and the DOM driver's subtree MutationObserver with old-value recording.

src/extra/xstreamExtras.ts:48 (setInterval debounce), src/cycle/dom/modules.ts, src/component.ts:2089, src/cycle/dom/makeDOMDriver.ts:88

What to avoid

Throttling patches to requestAnimationFrame in the DOM driver as the fixI tried it. It cut the Collection storms (clear after select: 424 → 111 ms; select CPU 180 → 128 ms) but added about 7 ms latency to every single update (update 1 of 1k: 13.7 → 20.3 ms; deep click: 6.1 → 11.3 ms). Batch upstream, at render scheduling.
Replacing xstream or adopting signalsThe cost is in how many streams Sygnal builds per component and how it tears them down, not in xstream's per-event speed. A rewrite would break the public stream API and the Cycle model for gains that items 1, 4, and 5 deliver.
Replacing snabbdomIts diff is fast when it receives identity-stable vnodes. The 36% patchVnode time is self-inflicted by copying and repeated root patches.
Shipping a user-facing memo or thunk API firstIt would push the problem onto app authors and add a non-canonical form. Fix identity and scheduling internally; revisit only if profiles still show view cost.
Micro-tuning objIsEqual or the debounce operator aloneNeither shows up above a few percent in any profile. Their cost is in how often they run, which items 1 and 5 address.
Optimizing for bulk-create numbersSingle-component Sygnal already beats React at 10k rows and is within 1.7× of Vue at 1k. The gap is in updates, Collections, and memory.

Method and limits

Apps, harness, and scripts are in perf/ in this worktree (uncommitted). React uses hooks with memo rows, as in js-framework-benchmark; Vue uses SFCs with shallowRef and immutable updates, the same data pattern as Sygnal. Sygnal apps use the canonical forms from llms.txt and the sygnal/vite plugin; the production bundle carries no diagnostics. Each op runs on a fresh page with warmups. Ops whose setup would be distorted by the previous run (10k create, 10k select, clear after select) use a new page per iteration.

Limits: one machine, headless Chromium, no CPU throttling, so absolute numbers are optimistic for phones; ratios are the useful part. React 19 and Vue flush discrete events synchronously or on a microtask, so their latency is close to CPU time, while Sygnal's includes timer waits; both are reported. Retained-heap numbers taken 200 ms after the last cycle include some deferred teardown; the heap-snapshot diff, taken after 1.5 s, isolates the true leak.
