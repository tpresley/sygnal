
Composing UI with a model (PLAN-9). An app declares its parts once in a catalog, the user describes a page or an edit in words, and a model builds it from those parts: a decision model answering multiple-choice questions (TypeSafe Jev, Ollama's `nimble`) or an LLM with structured output, with the same catalog, app code and tests for both. The composition is plain JSON in state, each part is an ordinary child component, and follow-up requests edit the page while keeping the state of the parts they don't touch. The same catalog lets a chat assistant ask the user with a card instead of in text (`chat({ ask })`), on top of client tools for the `chat` behavior. Around it: `decide()` splits large question sets, `byId()` lenses, and a component's `key` is now its identity.

Everything is additive, and `sygnal/ai` stays tree-shaken from apps that don't import it. The lowercase marker tags (`<collection>`, `<switchable>`, ...) are deprecated (they keep working in 6.x; `sygnal-check --fix` migrates them).

**Measured impact.**
- Live accuracy (E-3, `npm run test:compose-live`, every PLAN-9 gate passing): Jev structure 61–65/70, follow-up edits 22/22 tuned and 15/16 held out, keys 100%, about 0.35 s per call; `qwen3:8b` with a schema 11/11 flat dashboards and 15/15 dashboards, 0 invalid; `nimble` with `profile: 'small'` structure 29/70 with 0 invalid layouts (was 5 before the `decide()` split, G-757).
- Size: the kanban gate went down, (a) 42,504 B with `nativeGlobalThis: false` (was 42,690 B; budget 42,700 B) and (b) 38,485 B by default (was 38,679 B): the lazy marker handlers (G-751) save 223 B, `key` identity and the DOM move fixes add 28 B. `sygnal/ai` is tree-shaken from apps that don't import it; `<Composed>` adds about 0.5 KB gzipped over `catalog.render()` when used, and the fetch driver's `batch` about 0.3 KB.

### Added

- **Large question sets in `decide()`.** A set over `maxQuestions` (default 64, Ollama's limit) or an estimated `maxPromptTokens` goes as parallel requests whose replies arrive as one (`answers` merged, `usage` summed), and a request a server rejects as too large (HTTP 400/413 naming tokens, fields or a limit) is halved and sent again, at most 3 deep; `split: false` turns both off. The fetch driver does it for any request through the new `batch`, `combine` and `split` keys; `renderComponent`'s fake answers such a request as one. Fixes `compose.decisions({ profile: 'small' })` on Ollama, whose layout step for 6–7 elements got HTTP 400 (G-757). [Large question sets](https://sygnal.js.org/guide/ai-decisions/#large-question-sets)
- **Composing UI with a model** (`sygnal/ai`, PLAN-9). The user describes a page in words, and a model builds it from parts the app prepared: it picks parts, their params and their places, and never writes markup, state paths or action names. `defineCatalog({ parts, containers, guidance, limits, examples })` declares the parts once for both kinds of model: each part is a Sygnal component (or a `render` view function) with a `description` (all a model sees of it), `params` (options, numbers with `bins`, LLM-only `text` / `list`, and records: `from: (state) => records`, one node per record), `state` (a key, a lens, or `(node) => lens`) or `local` state, and placement fields (`in`, `group`, `maxUses`, `required`, `pin`, `companions`). Containers are view functions with named slots (tabs, sections; a built-in `row`), never components, and the model never chooses one. The `compose(catalog, { backend, form, prompt })` behavior keeps the composition as plain JSON in the host's state (`status`, `layout`, `preview`, `decisions`, `error`) with the actions `COMPOSE`, `SET_LAYOUT`, `REMOVE`, `CONTROL` and `DONE`; `catalog.render(state.page, state)` renders it in the host's view, each part a child of the host keyed by its identity, so lenses, `CHILD.select`, `EVENTS`, context and drivers work as for any child. A follow-up `COMPOSE` edits the page (remove, change a setting, add, move, swap) and keeps the instances and state of the parts it doesn't touch; `{ prompt, fresh: true }` starts over. Guide: [Composing UI with a Model](https://sygnal.js.org/guide/ai-compose/), with live demos.
- **Two backends, one catalog.** `compose.decisions({ model })` asks a decision model (TypeSafe Jev, Ollama's `nimble`) multiple-choice questions through `decide()` on the `HTTP` sink, in at most two calls, posting to `/api/decide` by default so the API key stays on your server (options `url`, `rowMean`, `prefilter` (`'auto'` by default: on for large catalogs with categories), `maxOptions`, `maxParts`, `profile: 'small'` for small local models, and `maxQuestions` / `maxPromptTokens` / `split` for `decide()`). `compose.llm()` sends one structured-output request with the catalog's JSON Schema on the `LLM` sink, streamed as a preview, with a repair step; a reply still invalid after it is an error, never a layout. Measured on the research catalogs: Jev 9/11 flat dashboards, 191/210 structure cases and 57/60 enum params at about 0.35 s; `qwen3:8b` with a schema 11/11 at about 3.4 s (the guide's table). Switching backends changes no app code and no test.
- **`<Composed catalog={catalog} from="page" />`**: `catalog.render()` as a tag (from `sygnal/ai`, also `sygnal`), reading the composition from the host's state at a key or a path; a container view that throws renders the host's `onError` (SYG408). An app that never renders it ships none of it (about 0.5 KB gzipped when used).
- **Composing from an agent**: `actions: { ...compose.action('page') }` on an `agent` declaration offers `<agent>_page_compose({ prompt, fresh? })`, which answers once the composition is done; `compose.summary(slice)` is the page as an agent's `read` shows it.
- **Cards in a chat: `chat({ ask: { catalog } })`.** The model gets an `ask_user({ need })` tool; the app composes a card from the catalog (`compose.llm()` on the chat's sink by default, or `compose.decisions()`; `direct: true` takes the card as the tool input for providers that enforce tool schemas), keeps it on the tool part as `part.ui` (status, layout, answer, local state, the backend's decisions; persisted with the chat), and `askCard(catalog, state, part)` renders it. A part with `result: true` answers with `compose.answer(props, value)` to `PARENT`; the call closes with `{ part, answer }` and the chat goes on. STOP and a new message cancel open cards; a card that fails closes the call with the reason, so the model can ask in text. Guide: [Cards in a Chat](https://sygnal.js.org/guide/ai-cards/), with a live demo.
- **Client tools on the `chat` behavior**: `clientTools: { name: { description, inputSchema } }` declares tools the app answers itself (the AI SDK's `onToolCall` / `addToolOutput`): their calls stay open until `'assistant.TOOL_OUTPUT'` (`{ toolCallId, output }` or `{ toolCallId, errorText }`) answers them, a host entry `'assistant.TOOL_CALL'` runs as each opens, and `openToolCalls(state.assistant)` lists them. A Standard Schema input is validated first. The chat driver's `abort` takes a list of keys, and a chat request with `output` and `parse: false` sends the schema but leaves the reply's `text` for the caller to parse (`compose.llm()` parses leniently).
- **`chat({ model: (state) => id })`** and `compose.llm({ model: (state) => id })`: the model as a function of the host's state, resolved per request, so one chat behavior follows an app's model picker.
- **`composeWith(t, catalog, tree)`** for tests: it answers the pending composition, a page or a card, so that it becomes `tree`, through the pending backend's own fake reply, so one test runs against both backends; it throws when the backend can't reach the tree. Also `fromTree`, `toTree` and `removeNode` for layouts.
- **`byId(field, id)`** (from `sygnal`): a `{ get, set }` lens to the array element with that id, for a catalog's record parts or any child (`<TodoItem state={byId('todos', 3)} />`).
- **A component's identity is its `key`** (PLAN-9 D470): a component tag's instance belongs to the component plus its `key`, else its `id` prop, else its position in the view (before, `key` was ignored on component tags). A new key disposes the instance and starts a new one, which is how to reset a child; a `key` on `<Collection>` re-creates its items. New **SYG453** (dev only): two tags of one component with the same identity in one view share one instance. +6 B gzipped.
- **New diagnostic codes** for catalogs, compositions and cards, at run time in development and, where a literal `defineCatalog({...})` shows them, in `sygnal-check`: SYG160 (a result part outside a card), SYG161 (a container that is a component), SYG162 (a part with neither `component` nor `render`), SYG250–SYG252 (unknown part or slot, invalid param value, a record `from()` that returns no `{ value }` array), SYG450–SYG452 (an `in` naming an unknown slot, `<Composed>` misuse, a node listed twice), SYG680–SYG683 (an LLM-only part under a decision backend, a backend option problem, an answer outside the criteria, an LLM layout invalid after repair), SYG684–SYG686 (a client tool shadowing an agent tool, an answer for a call that isn't open, an `ask` catalog without a result part).
- **`sygnal-check`: catalog rules.** New **SYG253** (warn: a misspelled catalog declaration key, with a rename quick fix) and **SYG254** (info: a description lint: two parts outside one group sharing a phrase, a description naming its own param's value, options that overlap between a part's params); the `chat` and `compose` behaviors' keys and actions are known to the checker (no false SYG127 for `ask`). New **SYG426** for the deprecated lowercase marker tags (below), with `--fix`.
- **Agent context**: `llms.txt` (now up to 322 lines, D461) and the `sygnal-dev` skill describe catalogs, `compose`, `<Composed>`, `composeWith`, chat cards, client tools and `key` identity; `dist/guide` ships `ai-compose.md` and `ai-cards.md`. Examples: `examples/ai-compose` (both backends, a model picker, an optional dev proxy for Jev that keeps the key in an env file outside the repo) and `examples/ai-ask` (an assistant that asks with cards).

### Changed

- **`examples/ai-panel-spa` runs on `sygnal/ai`** against a local Ollama: `makeChatDriver` over `openResponses()` with structured output and streamed turns (it had a hand-written driver with an API key in the browser), model pickers read from Ollama's installed models, a decision model that picks each speaker through `decide()`, `persist()` and the browser driver's clipboard instead of custom drivers, and canonical forms throughout. No library change.

### Deprecated

- **The lowercase marker tags** (PLAN-9 D471): `<collection>` and `<switchable>`, which worked without an import, and the undocumented `<clientonly>`, `<portal>`, `<transition>` and `<suspense>`. They keep working in 6.x and will be removed in the next major, where they render unknown elements; the Collection and Switchable handlers will then load only in apps that import them (measured on a prepared patch: about 2.9 KB gzipped less for an app that uses neither, about 0.7 KB for kanban). To migrate, `import { Collection } from 'sygnal'` and write `<Collection …>` (`Switchable`, `Portal`, `Transition`, `Suspense` from `'sygnal'`, `ClientOnly` from `'sygnal/vike'`); `sygnal-check --fix` renames the tags and adds the import. New code SYG426: the dev diagnostics warn once per tag for `<collection>` / `<switchable>` (0 production bytes), `sygnal-check` reports every lowercase marker tag, and the JSX types mark the two intrinsic elements `@deprecated`. A plain `<slot>` is an HTML element, as before (G-480). `examples/todomvc` uses `<Collection>`.

### Fixed

- **Real DOM: a keyed component that moves to another parent element in one patch** (G-750, G-753). Moving an instance to an earlier parent element threw `NotFoundError` in the DOM driver and stopped the app's DOM updates, and moving one into a parent element created in the same patch (a new row) left the DOM at the old arrangement, silently. Both are fixed in the DOM driver's isolation module; the mock DOM of `renderComponent` never showed them. Browser tests on Chromium, Firefox and WebKit.
- **The `chat` behavior after a reload.** A chat slice persisted while a reply streamed came back with `status: 'streaming'`, and Send did nothing until the page was cleared, in every app that persisted a chat. It now comes back `'ready'`, and tool calls left open are closed.
- **`Portal`, `Transition`, `Suspense` and `lazy` are tree-shaken** (G-751): they were registered when the main entry loaded, so every app carried them; they now register when first rendered. Kanban is 223 B gzipped smaller.
