# Loading-guard migration assessment

The initial linked-app feedback identified a real gap in the then-current sygnal-check 0.11.0
source, rather than a stale checker or a runtime regression. An in-memory App fixture with the
reported START action, a DONE handler, and an installed `sygnal@7.0.0` manifest produces
`diagnostics: []`. `project.sygnalFor(file)` resolves version 7.0.0 and default `after` correctly.
At that point, the timing rule validated declarations and binding compatibility without comparing
STATE writes against output guards. The subsequently authorized implementation below closes the
bounded case while preserving the runtime contract.

## Runtime finding

For `STATE: s => s.status !== 'working' ? {...s, status:'working'} : ABORT`, repeating the
same predicate in HTTP rejects the updated state and sends no request. Removing the HTTP
guard sends duplicate requests when START repeats: STATE's ABORT leaves state unchanged but
does not cancel the other sinks. Keep the guard and read `previousState.status` for admission.
Use the updated state for any payload fields generated by STATE.

This is also consistent with explicit `before` timing, where the original repeated predicate
works. No runtime error or general warning on ABORT is appropriate: suppression is intentional
in many valid applications. Making STATE's ABORT cancel the whole action would change the
existing independent-sink contract and is not recommended.

## Delivered guidance

- Added a loading-guard subsection to the migration guide, including DONE and the duplicate
  request explanation; refreshed its shipped offline copy.
- Added the admission/payload distinction to llms.txt, its site copy, and the development skill.
- Added tests that execute the actual guide model: first START sends once, a repeated START
  while working sends none, DONE restores admission, and the next START sends again.
- Added regression cases for the reported self-blocking guard (zero requests), unconditional
  output (two requests), and the original guard under before timing (one request).

Verification: 27 tests pass across the guide-transition, llms consistency and offline-guide
suites; shipped-guide freshness and `git diff --check` pass. Runtime implementation and linked
JavaScript build are unchanged.

## Authorized diagnostic follow-up — implemented

Added **SYG256: Output guard rejects the updated state**, a static-only warning alongside
SYG255. It is included in the unreleased checker 0.11.0 work; no package publishing or new
dependency is needed.

Implemented boundaries:

1. Require an installed 7+ runtime and a proven `after` context. Respect explicit component
   contracts. For inherited timing, resolve imported run/renderComponent/defineElement entries,
   their options, and reachable child components. Parent declarations do not cascade. Dynamic
   options, unknown versions, or standalone library components without a known context cannot
   establish the active timing. Multiple entries qualify a finding with a proven after context.
   Apparent option mutations, aliases, accessors and conditional/repeated component contracts
   invalidate timing evidence. Per-project mutation indexes avoid repeated full-AST scans.
2. Prove a STATE return assigns a literal field value, and that a same-action output predicate
   on its first argument returns imported ABORT for that value. Start with simple strict equality
   comparisons and boolean guards in ternary or straightforward return/if forms. The reported
   status example is covered. Pure inline functions, object methods and shorthand sink entries
   are supported; arbitrary control-flow analysis is not attempted.
3. Skip writes obscured by spreads/computed keys, unknown helpers, composition or calculated
   overrides. All components with uses/calculated declarations are skipped in this first version.
   Apparent model mutations, duplicate state contributors, dead branches, computed/default
   parameter side effects, async reducers, and prototype-setter fields are excluded as well.
4. Highlight the output predicate and relate the STATE write. Explain that the guard sees the
   committed state and suggest previousState for admission. No automatic guard removal or
   general signature rewriting.

Verification criteria: warn for the reported pattern under default7 and explicit after; remain
silent for installed6, explicit before, app-before, unknown timing, corrected previousState
guards, predicates that accept the assigned value, shadowed ABORT, and unprovable writes.
Include child-context and mixed-entry tests, composition/calculated exclusions, precise source
ranges, explanations, suppressions, and CLI/editor consistency. Keep it static-only so it adds
no core production runtime bytes.

The diagnostic highlights the contradictory output predicate, with related STATE assignment
and effective timing locations. Registry/explanation metadata, generated diagnostic docs, the
checker README, changelog, migration guide, llms/skill and shipped offline guidance agree.

Production-size verification: generated the current ESM entry in memory without changing the
linked dist. Its only executable difference is the dev-only severity metadata. Built kanban with
both old and candidate entries through the same Vite configuration/alias: production JS is
byte-identical (129,943 raw bytes in that comparison). Thus this warning adds no production
bundle bytes and leaves the approved size budget unchanged. Root linked JS artifacts were not
replaced. Repository examples produce no SYG256 warnings or rule crashes.
