Sygnal 6.0 · core rewrite study

A rewritten component core for Sygnal 6.0

The current core gets its performance by managing three competing clocks. This proposal removes two of them: state updates become synchronous and startup timers go away. Streams stay only where users and drivers see them. A 370-line prototype running the same apps mounts components 2.4× faster and builds a 10k-row Collection 4× faster.

What the prototype leaves out

It covers only the canonical subset the benchmark apps use: view, object intent, model sinks, initialState, function context, tag children, Collection and CHILD.select(Fn). A production core adds calculated fields, statics, Suspense and the other markers, Switchable, replies, hooks and the error boundary. Those costs scale with the features a component declares, not with the number of instances, so most of the speed gain should survive. The size gain will shrink.

Why rewrite

Three clocks the current design can't remove

PLAN-4.5 already took the "lower-level xstream primitives" route inside the current design. It added single-stream helpers, a keyed microtask scheduler, and a patch to Stream.prototype._remove for batched teardown. That took streams per Collection item from 151 to 22 and patches per update to 1. Its own review findings show the cost. G-257, G-266, G-272–274, G-284 and G-287 are all races between three timing sources:

withState · microtask per reducer

State lags its action

The lag requires STATE_SNAPSHOT, a module-global pendingReducers, "fresh" checks, and a scheduler that waits up to 10 microtask hops for reducers.

0 / 1 / 10 ms timers

Startup on timers

INITIALIZE, then the intent, then BOOTSTRAP each run on a timer. First-render gates and patch holds with a 50 ms bound exist so that a newly visible element always responds.

StateSource + isolate per child

A stream chain per component

State reaches every child through its own map/filter/dropRepeats/remember chain. Writes climb back up as one reducer wrapper per ancestor. Sink values pass through one hub per ancestor.

Proposal

Streams at the edges, plain data inside

Users write streams (intent) and drivers speak streams, so those stay xstream. Nothing between "an action arrived" and "a vnode went to the DOM driver" needs to be a stream. In that span the core uses function calls over plain objects:

  • One clock. Actions run synchronously and to completion, in order. Rendering happens once, in a microtask after the queue drains. Timers exist only where the user asked for time: next(…, ms), timers, transitions.
  • Per app, never per module. Queue, scheduler, ids and flags hang off the app runtime.
  • Normalize at definition time. The model table, calculated order, context entries and statics are computed once per component function, in a WeakMap.
  • Explicit extension points. Every module that patches instance methods today gets a named hook instead.
sources.ts · edge

Boundary streams

The isolated DOM source with its shorthand; STATE.stream/watch as a lazy facade; CHILD; props$, children$, dispose$ created on first use.

runtime.ts

App runtime

Root state, a run-to-completion action queue, one microtask flush, one bus stream per driver sink, the hooks registry.

cell.ts

State cells

{ get, set } lens views memoized on parent identity: root, key, lens, Collection item (shared id → index map), local (isolatedState).

define.ts

Definitions

A normalized Def per component function. defineComponent(opts) replaces the component() factory and returns an ordinary function component.

instance.ts · actions.ts

Instances

Dirty-checked render (state, props, children, context keys read), children reconciled through a Map, handler execution for STATE, driver sinks, PARENT, EFFECT and ELEMENT.

hosts/ · markers.ts · statics.ts

Hosts and markers

Collection, Switchable (hidden pages skip render), tag children. Portal, Transition, ClientOnly, Lazy and Suspense register their handlers on import (D157). The generic __sygnalStatic path stays, because PLAN-5's B-3 browser sources reuse it.

Runtime semantics

How an action and a render work

An action. Read pre = cell.get(), then run the handlers in model order with (pre, data, next, props).

  • STATE writes the cell unless the handler returns ABORT or the same state.
  • Every other sink receives pre, which is exactly the documented "every sink sees the state from before this action". No snapshot symbol or extra microtask is needed.
  • EFFECT runs synchronously, so preventDefault() on the live event keeps working.
  • PARENT goes straight to the parent's CHILD hub.
  • Driver values are stamped with __emitterId and the instance's scope chain, then pushed to the app bus. That is O(1) per value instead of one hub per ancestor.

Startup. A new instance writes its initialState to its cell synchronously; INITIALIZE becomes a synchronous action. Its intent is subscribed immediately, and anything emitted on subscribe is queued. The first render lands in the same flush, so no element can be visible before its intent listens. BOOTSTRAP fires after the first commit, which matches the docs' "once, just after mount".

A render. The flush walks top-down. An instance re-runs its view only when its state cell, props, children, or the context keys its last view read changed. Otherwise it returns the same vnode object, and snabbdom skips the whole subtree. The context passed to the view is a Proxy that records reads, so selecting a row re-renders only the rows that read the changed key.

interface Hooks {
  transformDef?(def, view): Def            // behaviors, undo, selection, persist
  onCreate?(inst); onDispose?(inst); onRender?(inst, vnode)
  onAction?(inst, action, cause)           // devtools, action log, t.actions
  wrapHandler?(inst, action, sink, fn): fn // SYG222 / action-log wrappers
  onReducer?(inst, action, prev, next)
  onNext?(inst, type, data, ms)            // replaces testing's regex over debug-log text
  wrapSources?(inst, sources): sources     // test fakes, diagnostics proxies
}

Trade-offs

Behaviour changes and risks

ChangeWho notices
A STATE reducer is applied synchronously, not in a microtaskCode reading STATE.stream._v mid-tick; tests that awaited a microtask "for the reducer"
BOOTSTRAP fires in a microtask after mount, not at 10 msFake-timer tests that advanced 10 ms to see it
Context changes skip components that don't read the changed keyA view that relied on re-rendering for a side effect (unsupported)
Sink values skip ancestor hubs: same values, same order, possibly earlier in the tickNothing documented
  • Test coupling. Many test/p45-*, p4-* and diagnostics/* tests poke internals. The behavioural suites (examples, browser tests, docs samples, agent evals) are the parity bar.
  • Extensions (behaviors, undo, selection, persist, action log, testing, devtools) all move to hooks in the same release.
  • Reentrancy: drivers that emit synchronously during sink delivery (event bus, driverFromAsync early replies, G-176, G-189) need failing-first tests before the switch.
  • Value isolation: the fetch and socket drivers tag requests with every ancestor's scope. The bus applies the instance's whole scope chain per value. A value-level isolateValue(v, scopes) joins the source contract, with a stream fallback.
If pursued

A dual-core path to parity

The new core ships behind run({ core: 'next' }), so the full suite runs against both cores. The old core remains the parity oracle until the last phase deletes it.

Open questions

Decisions needed

Which API removals to accept?

PLAN-1 says non-canonical forms are never removed. Dropping the forms above needs a 6.0 exception, with migration notes and the strict codes that already flag them.

Where does this run?

Either as its own plan (PLAN-4.6) before PLAN-5, so PLAN-5's components are built on the new core, or as a PLAN-5 pre-phase.
