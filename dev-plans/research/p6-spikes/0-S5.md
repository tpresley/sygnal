# PLAN-6 spike 0-S5: live examples for the AI docs

**Branch:** `exp/p6-s5` (from `plan6-integration` e3c86070). **Date:** 2026-10-09.
**Question:** how can the docs' live examples demo `sygnal/ai` (streaming chat, a tool call, a
decision) with no network model and no keys, and pass `check-live` on three engines?

**Answer in one line:** give the `js live-server` demo server streamed bodies (`sse:` /
`stream:`), let the real `openResponses()` transport run over the page's demo fetch, and have the
live runtime provide `LLM` the way it provides `HTTP`. Every demo on the spike page passes
`check-live` on Chromium, Firefox and WebKit, and an interaction script checks streaming, Stop,
the tool loop and the decision in all three.

## What the spike adds (all on `exp/p6-s5`, docs only, 0 library bytes)

| File | What |
|---|---|
| `docs/src/live/server.ts` | +71 lines: a route handler may return `{ sse: events }` (an object is `event: <type>` + `data: <JSON>`) or `{ stream: chunks }`, as an (async) iterable sent one item per `chunkMs` (default 40) after the headers (`delayMs`). The body is a real `ReadableStream`. The request stays pending (`data-live-pending`) until the body ends. An abort after the headers errors the body with an AbortError, as `fetch` does. Notes read `→ 200, streamed 17 item(s) (1342 ms)` or `→ aborted after 7 item(s)` |

| `docs/src/live/ai-spike.ts` + `modules.ts` | **The `sygnal/ai` stand-in is in the live modules registry** (`'sygnal/ai': () => import('./ai-spike')`), not a live-file, so the demos import what the real guides will. | `docs/src/content/docs/spikes/ai-live.md` | the spike page (`/spikes/ai-live/`, not in the sidebar, `pagefind: false`): a `live-file` `./demoModel.js` (Open Responses event builders, 30 lines) and 5 demos (below) |
| `docs/scripts/spike-ai-interact.mjs` | spike-only Playwright script that drives the demos (check-live only loads them) |

The demos:

1. **Chat** (§1 of the samples, nearly verbatim): Send streams a 60-word reply word by word (60 ms
   per event). **Stop** sends `{ abort: 'reply' }` and keeps the partial text. Nothing arrives
   after it, and the demo server notes `→ aborted after 7 item(s)`.
2. **Summary**: streams on `BOOTSTRAP`, so `check-live` itself has to wait for a stream to finish.
3. **Lamp: a tool call.** `Lamp.agent = { name, description, read, actions: { SET_COLOR: { description, input } } }`.
   The request carries `tools: agentTools(Lamp)`, and the demo model answers with a
   `function_call` for `lamp_set_color`. The `tool: 'TOOL'` reply runs it as the lamp's own
   `SET_COLOR` reducer (the same one the colour buttons use). `DONE` sends the tool result back,
   and the model answers "Done: the lamp is blue now." Asking for blue again makes `SET_COLOR`
   return `ABORT`, so the tool returns "SET_COLOR changed nothing" and the model says so.
4. **Ticket: a decision.** `Ticket.resources = { triage: (s) => decide({ url: '/v1/systemone', model: 'nimble', state: s.text, questions }) }`
   over the `HTTP` driver, answered by a `POST /v1/systemone` demo route. Editing the text
   re-triages (billing/urgent → bug).
5. **Echo: the scripted alternative.** `export const drivers = { LLM: makeChatDriver({ transport: scriptedTransport(() => '…') }) }`, with no HTTP.

## 1. How live demos get drivers today, and can a route stream?

Today: `runPanel` calls `run(Component, defaultDrivers(...), { mountPoint, uid, onError })` with
`HTTP: makeFetchDriver({ ...server.options, fetch: demoFetch })`, `DOM` (the View Transition DOM
driver), `TIMER`, `BROWSER` and `DND`. `demoFetch` (`server.ts`) answers from the route table of
the last `js live-server` block before the panel. It matches the **pathname only**, so
`http://localhost:11434/v1/responses` hits a `'POST /v1/responses'` route. The page can't see
which drivers a demo gets: they are documented in the remark-live header, with no `main.js` on
the page. A demo had no way to add a driver.

**Streaming: no.** A handler returned `json` or `text`, and the whole body was built as a string
and handed to `new Response(string)` after `delayMs`. A `ReadableStream` or iterator in `text`
would have been `String()`-ed. Also, only the `HTTP` driver got `demoFetch`, so a chat
transport had no path to the demo server.

**Minimal change (done here):**
- `sse` and `stream` responses in `server.ts`: a timer-paced `ReadableStream` body, kept
  pending until it ends, and errored on abort (71 lines, no new dependencies).
- An `LLM` driver whose transport takes the demo fetch.

With both, the page runs the real Open Responses path end to end: the request body (`input`,
`tools`, `instructions`), SSE framing, `response.output_text.delta`, `function_call` +
`function_call_arguments.done`, `response.completed`, and abort mid-body. That's D243's
transport, so the docs exercise the code readers ship.

## 2. The alternative: a scripted transport

| | **A. SSE demo route + real `openResponses()`** (recommended) | **B. `scriptedTransport()` + a visible `drivers` export** |
|---|---|---|
| Honesty | The page shows the "model" as a route table speaking the real wire format. The only unseen part is the documented `LLM` default (as for `HTTP` today) | Everything is on the page, but what runs is not what ships: no HTTP, no SSE, no transport |
| What readers copy | the component, unchanged; `main.js` shown separately with `openResponses({ baseURL: 'http://localhost:11434', … })` | a `drivers` export (a docs-only convention) and a transport they must replace |
| Simplicity per demo | one route; the event builders are verbose (30 lines of Open Responses JSON, a live-file per page today) | shortest: a function returning a string or steps |
| Coverage | real transport, SSE parsing, abort of a body, request notes (`streamed 17 item(s)`, `aborted after 7`) | the driver only |
| `check-live` | streams count as pending, so a stream that never ends fails after 30 s | **invisible**: no pending count, so check-live can't wait for its streams (a stream-on-load demo could be checked mid-stream) |
| Edit-and-run | readers can edit the route to try tool calls or errors (`status: 500`) | readers can edit the script |

B's one strength, a short script, is better served by A plus a shared event encoder (P6-Q9).
B shouldn't be a public export for docs. L-4's in-memory transport already covers tests.

**Flakiness: none seen** in 18 spike-page check-live runs and 9 interaction runs.

Timings that matter for check-live:
- The stream-on-load demo's 60-word reply takes about 1.4 s (300 ms to headers + 17 events ×
  60 ms). check-live's 500 ms settle wait plus `data-live-pending` covers it, and a stream adds
  its duration to the page's check time.
- Stop after 5 rendered drafts at about 1.6 s: the partial text was kept, and nothing changed in
  the 800 ms after.
- Frame coalescing gave one render per 60 ms event, since rAF is faster than the events. At
  40 ms chunks, it would still be one per event.

Keep demo replies short (≤ 2 s) so the docs gate stays fast.

## 5. Recommendation for Phase 4 and what PLAN-6 must add

**Use A.**
- Guides show `main.js` with `openResponses({ baseURL: 'http://localhost:11434', model })` as a
  plain (non-live) block.
- Live demos are the component plus a `js live-server` block whose `POST /v1/responses` route is
  the model.
- The runtime provides `LLM` (documented in remark-live and on the live-examples help) as it
  provides `HTTP`.
- Decisions need nothing new: `decide()` → `HTTP` → a `/v1/systemone` route works today.

PLAN-6 must add:

1. **Docs infra item (a new "D-1", Phase 2, before the guides):** move the spike's `server.ts`
   streaming (`sse`/`stream`/`chunkMs`) and the runtime's `LLM` default into the docs for real,
   with unit tests for `makeDemoFetch` (there are none today: pacing, abort before and after the
   headers, `cancel()`, pending accounting), and document them in the remark-live header.
   - Provide `LLM` whenever **any block on the page** imports `sygnal/ai`, not just the demo
     itself. A demo that only sends to the `LLM` sink, without importing `sygnal/ai`, gets no
     driver in the spike.
2. **L-2: every HTTP transport takes `fetch`** (`openResponses`, `chatCompletions`,
   `uiMessageStream`, `anthropicMessages`, `agui`). The docs need it, and so do tests, proxies,
   SSR and auth wrappers. Add it to the L-2 table's notes.
3. **An Open Responses event encoder that ships with `sygnal/ai`** (P6-Q9), e.g.
   `openResponsesEvents(['Hello ', { toolCall: { name, input } }])`, taking the same chunk shape
   as L-4's `t.stream` items. The mock SSE server (`test/helpers/`), the transport fixture tests
   and every docs demo server use it. This replaces the 30-line per-page live-file.
4. **`modules.ts`:** `'sygnal/ai': () => import('sygnal/ai')` (one entry, D240). `zod` is
   already there for `agent` inputs.
5. **check-live rules for streams:**
   - A streamed request counts as pending until its body ends. This is done: the existing
     "still waiting after 30 s" check now fails a stream that never ends.
   - An aborted stream is never a failure (as now).
   - Each AI page has at least one demo that streams on load, so the gate parses a real stream
     on all three engines.
   - Stop, tool loops and edits are interactions check-live doesn't do. Either keep a per-guide
     interaction script like `spike-ai-interact.mjs` in the docs gate, or rely on L-1's browser
     tests. P6-Q11.
6. **L-1:**
   - Frame coalescing needs a timer fallback when no frame comes (a hidden tab or a background
     iframe). Without it, deltas pause in background tabs until `ok`. The spike uses
     rAF-or-100 ms, as the live runtime's `frame()` does.
   - The 0-S1 render-budget assertion should state its rAF assumption.
7. **K-1:** SYG102 has to count the `delta` and `tool` reply keys of an `LLM` request. It must
   also follow a request built by a local helper (`ask(messages)` returning `{ tool, ok, error }`).
   The spike page shows six non-strict SYG102 false positives.
8. **D243 wording:** "the docs' live examples use `openResponses()` against the page's demo
   server (a `js live-server` route speaking Open Responses SSE), with Ollama in the `main.js`
   they show".

## Gaps (G- candidates, unnumbered)

- The demo server couldn't stream (fixed on the spike branch). It has no unit tests at all.
- A live demo can't declare or show its drivers. The spike's `export const drivers` works and
  is generic (sockets, routers later), but it's a docs-only convention. P6-Q10.
- A scripted (non-HTTP) transport is invisible to check-live's pending count.
- check-live never interacts, so the abort/Stop paths in docs demos are unchecked by the gate.
- SYG102 false positives for the `delta`/`tool` reply keys and helper-built requests.
- L-1's prototype coalescer stalls without animation frames (hidden tabs).
- The tool-loop-by-hand demo (TOOL + a DONE follow-up, about 20 lines) is what L-3 removes. The
  guides should show it only in a "how the behavior works" aside, and use `chat()` elsewhere.
- A demo server's streaming note appears only when the stream ends. A "streaming…" line while it
  runs would help readers. Minor.
- The `LLM` default in the spike triggers on the demo's own import of `sygnal/ai`. It should be
  page-level (item 1).
