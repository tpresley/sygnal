# PLAN-6 spike 0-S3: WebMCP in a real browser

Branch `exp/p6-s3` (from `plan6-integration` e3c86070), 2026-10-09. Code: `browser-tests/webmcp-spike/`.
Question: how can the gate test A-2 (`experimentalExposeWebMcp`) and A-3 (form → declarative
WebMCP) in real browsers?

**Short answer.** Playwright's chromium-1243 is **Chrome for Testing 153.0.8010.12**. It ships
WebMCP behind `--enable-features=WebMCP`, which is exactly what `chrome://flags/#enable-webmcp-testing`
sets. With that switch, `document.modelContext` is native, the page can act as the agent
(`getTools()` / `executeTool()`), and the declarative form API works. `@mcp-b/webmcp-polyfill`
6.0.0 provides the same surface in Chromium, Firefox 155 and WebKit 26.6. A Sygnal todo app with
`agent` declarations completed a full agent round trip in every engine and mode: 20/20 checks
natively, 20/20 under the polyfill in each engine, and 21/21 with the polyfill installed over the
native API. The whole existing browser suite also passes with the switch on (364/364).

## How to rerun

```bash
npm ci && npm ci --prefix browser-tests && npm install --prefix examples/kanban && npm run build
node browser-tests/webmcp-spike/run.mjs            # the round trip: engines × modes (exit 0 = all pass)
node browser-tests/webmcp-spike/run-compat.mjs     # native vs polyfill API answers, side by side
node browser-tests/webmcp-spike/probe-flags.mjs [--shell]   # which launch args expose the API
node browser-tests/webmcp-spike/probe-api.mjs --shell       # native imperative + declarative details
node browser-tests/webmcp-spike/probe-declarative.mjs --shell
node browser-tests/webmcp-spike/probe-cdp.mjs               # the CDP WebMCP domain
node browser-tests/webmcp-spike/probe-chrome-flags.mjs <tmp-profile-dir>  # flag → switch mapping
```

The scripts use the cached engines only. No browsers were downloaded. The only network access was
`npm install` of the polyfill.

## 1. Chromium 1243 and the switch

- **Version.** `chromium-1243` is `Google Chrome for Testing.app` **153.0.8010.12**, and
  `chromium_headless_shell-1243` reports the same version. Chrome 153 falls inside the origin
  trial window (149–156).
- **Binary strings** (`strings` on the framework binary) include:
  - `third_party/blink/renderer/core/script_tools/model_context.cc`;
  - `ModelContext::registerTool` returning `ScriptPromise<IDLUndefined>`, plus `getTools`,
    `executeTool(RegisteredTool, String, ExecuteToolOptions)` returning
    `ScriptPromise<IDLNullable<IDLString>>`, `ToolUnregisterAbortAlgorithm` and
    `HTMLFormElement::ScheduleDeclarativeWebMCPToolRegistration`;
  - the features `kWebMCP` ("Enables the WebMCP API."), `kWebMCPTesting`, `kDeclarativeWebmcp`,
    `kDevToolsWebMCPSupport`, `kWebMCPDeclarativeFileInput` and
    `kWebMCPFormAssociatedCustomElements`, and the flags `enable-webmcp-testing` and
    `devtools-webmcp-support`;
  - the CDP domain `WebMCP.enable`, `WebMCP.invokeTool`, `toolsAdded`, `toolsRemoved`,
    `toolInvoked` and `toolResponded`;
  - `readOnlyHint` and `untrustedContentHint`, but **no `consequentialHint`**, and no
    `unregisterTool` or `provideContext`.
- **Launch args** (`probe-flags.mjs`, in both the headless shell and full CfT). Each of these
  exposes `document.modelContext` (`ModelContext`: `registerTool`, `getTools`, `executeTool`,
  `ontoolchange`) and `SubmitEvent.prototype.agentInvoked`/`respondWith`:
  - `--enable-features=WebMCP`
  - `--enable-features=WebMCPTesting`
  - `--enable-blink-features=WebMCP`
  - `--enable-blink-features=WebMCPTesting`
  - `--enable-experimental-web-platform-features`, which also adds `LanguageModelTool*` globals

  Without any of them, `document.modelContext` is undefined. `navigator.modelContext` is
  **undefined in every variant**: the deprecated form is gone.
- **chrome://flags mapping** (`probe-chrome-flags.mjs`). Enabling `#enable-webmcp-testing`
  ("WebMCP for testing — Enables the WebMCP API.") in a throwaway profile shows
  `--flag-switches-begin --enable-features=…,WebMCP` in `chrome://version`. The flag is therefore
  **`--enable-features=WebMCP`**. Use that switch; it is what the gate should pass.
- A secure context is required. The spike used `http://127.0.0.1:<port>` (Vite), and the probes
  used `http://localhost` answered by a route.

## 2. The native API (Chrome 153)

**Imperative**

- `registerTool(tool, { signal })` **returns a Promise**. Errors reject rather than throw
  synchronously:
  - a duplicate name rejects with `InvalidStateError: Duplicate tool name`;
  - an invalid name (outside 1–128 of `[A-Za-z0-9_.-]`) rejects with `Invalid tool name`;
  - an empty description rejects with `Description is required`;
  - a missing `description` or `execute` is a `TypeError`;
  - an already-aborted signal rejects with `AbortError`.
- Aborting the signal unregisters the tool. Aborting and re-registering the same name in the
  same tick works.
- Inputs that are accepted without complaint:
  - a 31-character name and a 600-character description: Chrome's documented budgets
    (≤ 30 / ≤ 500) are **not enforced**;
  - a nonsense `inputSchema` (`{type:'nonsense'}`) is stored as is;
  - a cyclic schema throws `TypeError` (it can't be serialized to JSON).
- `tool.title` is accepted and reflected. `annotations`:
  - `readOnlyHint` and `untrustedContentHint` are kept;
  - `consequentialHint` (and any unknown key) is **dropped**;
  - with annotations, `getTools()` reflects `{readOnlyHint, untrustedContentHint}` with defaults
    `false`; without them, `annotations` is absent.
- `exposedTo: [origin]` is accepted. `getTools({ fromOrigins })` is accepted, but in a single
  page it doesn't filter.
- **Agent side, testing surface:** `getTools()` returns `RegisteredTool`s
  `{name, title, description, inputSchema, annotations?, origin, window}`.
  - **`inputSchema` is a JSON string.**
  - `executeTool(registeredTool, inputJson, { signal })`:
    - **the input must be a JSON string**: an object, or `null`, rejects `UnknownError: Failed to parse input arguments`;
    - **both arguments are required**;
    - a tool name instead of the handle is a `TypeError`;
    - it resolves with a **string**: a string result is returned raw (`'plain'`), anything else
      as its JSON (`42`, `null`, `{"x":1}`), and `undefined` as `"undefined"`;
    - a throwing `execute` rejects `UnknownError: Tool was executed but the invocation failed…`
      and logs `WebMCP tool execution failed: Uncaught Error: …` as a console error;
    - executing a handle whose tool was unregistered rejects `UnknownError: The operation failed for an unknown transient reason`;
    - a tool unregistered while it runs still resolves.
  - **No schema validation.** `{a:"x"}` against `{a: number}` and a missing required property
    both reach `execute`.
  - `execute(input, { signal })` receives the parsed object and an options object with a
    `signal`. Aborting `executeTool`'s signal rejects with `AbortError` and aborts `execute`'s
    signal.
- `toolchange` (a plain `Event` on `document.modelContext`) fires once per registration,
  synchronously within `registerTool`. On unregistration it fires **asynchronously**: not in the
  same task, but before a following `getTools()` resolves.
- The `toolactivated` / `toolcancel` events (`WebMCPEvent` with `.toolName`) fire on `window`.
  `toolactivated` fires on every execution, imperative tools included.
- **CDP** (`probe-cdp.mjs`): `WebMCP.enable`; `WebMCP.invokeTool({ frameId, toolName, input: <object> })`
  returns an `invocationId`, and the events give `toolInvoked` and `toolResponded`
  `{status: 'Completed', output}`. `toolsAdded` lists tools with annotations renamed
  (`{readOnly, untrustedContent}`, and `{autosubmit: true}` for a form) plus a `stackTrace` and,
  for forms, a `backendNodeId`. This is a real agent outside the page, but Chromium only.

**Declarative (forms)**

- A `<form toolname tooldescription>` registers on its own, shortly after insertion: the spike
  waited 100–150 ms. The input schema comes from the named controls:
  - `required` sets `required`;
  - `<select>` options become `enum` + `anyOf` of `{const, title}`;
  - the descriptions come from the `<label for>` / wrapping `<label>` or `toolparamdescription`;
  - **`aria-label` is not used**.
- Removing the `toolname` attribute or the form unregisters the tool. Changing it registers the
  new name.
- **Without `toolautosubmit`,** `executeTool` fills the controls and stays pending until a submit:
  the user's click, or a script's `requestSubmit()`. It never settled on its own within 3 s.
  **With `toolautosubmit`,** the browser submits.
- The submit event has `agentInvoked === true`. `respondWith(promise)` must be called **during
  the event's dispatch**, and `executeTool` resolves with the promise's value (an object becomes
  its JSON).
- An agent fill that fails constraint validation rejects `executeTool` with
  `UnknownError: Form validation failed: email: Please include an '@'…`, and no submit event
  fires.
- `toolname` is attribute-only: there is no reflected `toolName` property on
  `HTMLFormElement` in 153.

## 3. The polyfill

`@mcp-b/webmcp-polyfill@6.0.0`, MIT. It was published 2026-10-08, one day before this spike; the
earlier line was 5.1.0 (2026-08-31). It depends only on `webmcp-types@0.1.9` and adds 27 KB as an
IIFE.

- It vendors the upstream `webmachinelearning/webmcp-polyfill` at revision `6bf6c57`, which has
  no npm distribution of its own yet. It adds a "temporary declarative tools layer", and says
  the package "will eventually be removed".
- `installWebMCP()` is idempotent and **keeps a native context**: in Chromium with the switch,
  `executeTool` stays `[native code]`. It is a no-op on insecure pages and on old engines. It has
  no uninstall and no `navigator.modelContext` alias.
- The API matches the draft (`webmcp-types`): `registerTool(tool, { signal, exposedTo })` returns
  a Promise, and `getTools`, `executeTool(tool, inputObject?, { signal })` and `ontoolchange`
  are all there. The members are identical to native.

Native vs polyfill (`run-compat.mjs`; the three polyfill engines agree on every row):

| Question | Native Chrome 153 | Polyfill (Chromium, Firefox 155, WebKit 26.6) |
|---|---|---|
| `RegisteredTool.inputSchema` | JSON **string** | **object** |
| `executeTool` input | JSON **string** (object → `UnknownError`) | **object** (string → `TypeError: inputObject must be an object`); optional |
| string result | raw `plain` | JSON-encoded `"plain"` |
| `undefined` result | `"undefined"` | rejects `UnknownError: Tool execution failed` |
| `consequentialHint` | dropped | kept (plus `debugging: false`) |
| error messages | `Duplicate tool name`, `Invalid tool name`, `Description is required` | longer messages, same `InvalidStateError` names |
| throwing tool / declarative validation failure | descriptive `UnknownError` messages | generic `UnknownError: Tool execution failed` |
| name ≤ 128, description non-empty | enforced | enforced |
| name ≤ 30, description ≤ 500 | not enforced | not enforced |
| schema validation of inputs | none | none |
| `execute(input, { signal })`, abort, same-tick re-register, `toolchange` timing, `agentInvoked` | same | same |

## 4. The Sygnal round trip

`roundtrip.jsx` contains:
- `TodoApp` with `agent: { name: 'todos', read, actions: { ADD, SET_FILTER, CLEAR_DONE (consequential, when), SHOW_STATS } }`;
- a `Collection` of `TodoItem` with `agent: { name: 'todo', actions: { TOGGLE, REMOVE (consequential) } }`;
- a conditional `<Stats state="stats" />` child with its own `agent`.

The exposer (`exposer.js`) registers one tool per action, and one per item action with an
`id` enum of the live keys. It re-registers a tool when its description, schema or annotations
change, re-syncing on `onCreate`/`onDispose`/`onPatch` (coalesced to a microtask). Each call
validates, confirms, dispatches, awaits `flushed()`, then returns `{ ok, state: read(state) }` or
`{ ok: false, error }`.

Checks, each acting as the agent through `getTools`/`executeTool`:

1. The tool list is exactly `todo_remove, todo_toggle, todos_add, todos_clear_done, todos_read, todos_set_filter, todos_show_stats`.
2. The schemas, descriptions and annotations come through. `todo_toggle.id.enum` is `[1,2]`, and
   `todos_read` carries `readOnlyHint` and `untrustedContentHint`.
3. `todos_read` returns the projection.
4. `todos_add {value:'call mom'}` updates the state, the **DOM** (3 `<li>`), and the item tool's
   enum (`[1,2,3]`).
5. `todo_toggle {id:3}` checks the item's checkbox in the DOM.
6. `todo_toggle {id:7}` returns `no todo with id 7; ids: 1, 2, 3`.
7. Invalid input (`42`, `''`) is refused before dispatch.
8. A no-op (`set_filter 'all'`) returns "changed nothing".
9. Consequential: a declined call leaves the DOM unchanged; a confirmed call removes the item, and
   the enum becomes `[2,3]`.
10. `when`: `todos_clear_done` is offered only while a todo is done. Once the last item goes,
    the item tools are unregistered.
11. A child mounted later registers `stats_*`. `stats_bump` updates its DOM, and unmounting the
    child unregisters its tools.
12. `toolchange` fired 22 times.
13. There were no registration rejections.
14. `app.dispose()` + `stop()` leaves no tools. A call in flight gets `UnknownError` (native) or
    "no tool" (the polyfill: the handle was looked up after removal).

The A-3 checks used the same app with a `Signup` form:

15. `attrs-toolname="sign_up"` registers a form tool. `toolname="via_prop"` (a JSX prop) does
    **not**, because Sygnal's pragma sends unknown keys to `props` (an expando), and WebMCP reads
    attributes.
16. An agent submit (`toolautosubmit`) reaches the Sygnal **intent** with `agentInvoked: true`.
    `respondWith` called in the intent's `.map` works, because it runs synchronously inside the
    delegated listener. `executeTool` resolves with `{ok:true,email}`, and the view rendered
    `agent:a@b.c:pro:ok`.
17. An invalid agent fill is rejected. The rejection message differs, as the table in §3 shows.
18. A user submit (`requestSubmit()`) is unchanged: `agentInvoked` is false.
19. Removing the form unregisters the tool.

## 5. Recommendations

**How the gate tests A-2**

- **Chromium: native.** Launch with `--enable-features=WebMCP`. It is safe to pass on every
  Chromium run of `browser-tests`, since the full suite passes with it. That makes `run-headless.mjs`
  accept launch args: a fixed `args` for chromium, or a `BROWSER_ARGS` env var.
- **Firefox and WebKit: the polyfill** (`BROWSER=firefox|webkit`, as today's opt-in engines).
  Also run a **polyfill pass in Chromium**, so the polyfill's object-input path runs in the
  default engine too. Flags are per launch, so that is a second launch of about 2 s.
- **A separate page.** Run the WebMCP suite on its own page (like `webmcp-spike/index.html`), not
  inside `main.js`. The polyfill can't be uninstalled, and both the native and the polyfill
  registry are page-global. One option is an entry page selected by
  `BROWSER_TESTS_ONLY`/a query, reusing `run-headless.mjs`'s server and console allowlist.
- **The agent side.** Normalize in a test helper, `browser-tests/src/webmcpAgent.js`, from
  `agent.js`: parse a string `inputSchema`, and pass a JSON string to native `executeTool` but an
  object to the polyfill. Detect native through `Function.prototype.toString` (`[native code]`).
  Where it helps, wait for `toolchange` or re-`getTools()` rather than a fixed delay.
- **Optional extra for Chromium:** the CDP `WebMCP.invokeTool` path, exposed as
  `window.__pw('webmcp', …)`, tests "an agent outside the page". The in-page `executeTool` path
  is enough for the gate.

**Spec and API differences the implementation must handle (A-1/A-2)**

1. `registerTool` returns a Promise. Catch rejections (duplicates, invalid names) and report them
   as dev diagnostics; never let them become unhandled rejections.
2. **Always return an object result** (`{ ok, … }`), never a bare string or `undefined`. Strings
   and `undefined` differ between native and polyfill, and `undefined` fails under the polyfill.
3. **Never throw from `execute`.** A throw becomes a generic `UnknownError` (plus a console error
   natively), and the model loses the message. Return `{ ok: false, error }`, as already planned.
4. **Validate in Sygnal.** Neither native nor the polyfill checks inputs against the schema. This
   confirms Experiment 3's finding.
5. **Enforce the budgets in Sygnal** (name ≤ 30, description ≤ 500, parameter description ≤ 150)
   as the planned dev diagnostic. Neither implementation does. Hard limits that do throw: a name
   of 1–128 characters of `[A-Za-z0-9_.-]`, and a non-empty description.
6. **`consequentialHint` isn't in Chrome 153.** Keep emitting it (the draft and the polyfill have
   it, and unknown keys are ignored), but the app-side `confirm` is the only enforcement. The docs
   shouldn't promise that the browser asks.
7. **Feature detection** of `document.modelContext ?? navigator.modelContext` is right; the
   `navigator` form no longer exists in 153.
8. **Re-registration on change** (an enum of live ids, `when`) by abort + register works in the
   same tick in both. `toolchange` on removal is asynchronous.
9. **A call in flight across a dispose** may reject with `UnknownError` natively. Tests shouldn't
   assert on its message.

**A-3 is testable**, natively in Chromium and through the polyfill in all three engines:
`agentInvoked`, `respondWith`, `toolautosubmit`, schema from labels, constraint validation, and
unregistration on removal. What it needs:

- **The form behavior must write attributes, not props.** Use `attrs-toolname`,
  `attrs-tooldescription`, `attrs-toolautosubmit` and `attrs-toolparamdescription`, generated by
  the behavior. That costs 0 core bytes. The alternative, adding them to the pragma's `ATTRS`
  regex, costs core bytes against about 10 B of headroom.
- **`respondWith` must be called in the submit listener.** The behavior's intent-side handler
  runs synchronously in the delegated listener, which works. It has to pass a promise there and
  resolve it after validation and `flushed()`, rather than calling it from a reducer.
- **`toolparamdescription` should be emitted explicitly from the behavior's labels**, because
  `aria-label` isn't read.
- **Tests should assert only that an invalid declarative call rejects**, not its message, since
  the two implementations' messages differ.

## Gaps (G- candidates, unnumbered)

- **G-? JSX tool attributes become props.** `toolname`, `tooldescription`, `toolautosubmit`,
  `toolparamdescription` and `toolparamtitle` on an element become props (expandos), so
  hand-written declarative forms register nothing unless written as `attrs-toolname`. Options: the
  A-3 behavior emits `attrs-*`, the docs say so, and a `sygnal-check` rule flags a bare `toolname`
  on `<form>`; or add the names to `ATTRS` (core bytes).
- **G-? `run-headless.mjs` can't pass launch args** (needed for `--enable-features=WebMCP`), and
  its 90 s limit is fixed. Under heavy machine load (load average about 40) the clean suite timed
  out at 359/359 passed.
- **G-? The browser tests need a WebMCP entry page** separate from `main.js`, because the
  polyfill and registry are page-global.
- **G-? An agent-side test helper** must normalize the native and polyfill differences (§3 table).
- **G-? Results must always be objects** (string and `undefined` results differ, and `undefined`
  fails under the polyfill). This is an A-2 implementation rule plus a test.
- **G-? Budgets (30 / 500 / 150) are enforced by neither implementation.** The Sygnal dev
  diagnostic is the only check, so it needs a test.
- **G-? No `consequentialHint` in Chrome 153.** The docs must not imply that the browser confirms.
- **G-? Without `toolautosubmit`, an agent call stays pending until the user submits.** A-3 has
  to choose a default (see P6-Q11).
- **G-? The declarative layer ignores `aria-label`** for parameter descriptions. A-3 must emit
  `toolparamdescription`.

## Open questions for the user (P6-Q8+ candidates)

- **P6-Q8: the gate matrix.** Recommendation: native Chromium with `--enable-features=WebMCP` on
  every Chromium browser-tests run, plus the WebMCP page under the polyfill in a second Chromium
  launch, and polyfill runs in Firefox and WebKit. Alternative: the switch only for the WebMCP
  page.
- **P6-Q9: the polyfill as a `browser-tests` devDependency.** `@mcp-b/webmcp-polyfill`, exact pin
  `6.0.0`, a day old, from WebMCP-org/MCP-B, vendoring upstream `6bf6c57`. D209 is satisfied
  (test-only, never bundled). Should the docs also mention it to users for non-Chrome browsers,
  or stay silent until upstream publishes?
- **P6-Q10: A-3 attribute emission.** Recommendation: the `form` behavior writes `attrs-*` (0 core
  bytes), plus a `sygnal-check` hint for a bare `toolname` on `<form>`. The alternative is pragma
  `ATTRS` (core bytes).
- **P6-Q11: A-3 `tool` default for autosubmit.** Recommendation: `autosubmit: false` by default
  (the user confirms by submitting, matching Chrome's guidance for consequential forms), with
  `tool: { autosubmit: true }` to opt in. Note that an agent call then stays pending until the user
  acts.
- **P6-Q12: CDP `WebMCP.invokeTool` in the gate.** Recommendation: not needed. In-page
  `executeTool` covers it; CDP could be added later as a Chromium-only "outside agent" check.

## Plan changes

- **§2 row 0-S3:** done. The switch is `--enable-features=WebMCP` (= `#enable-webmcp-testing`) on
  chromium-1243 (Chrome 153.0.8010.12). The polyfill is `@mcp-b/webmcp-polyfill@6.0.0`.
- **§3 browser tests:** replace "in Chromium with the real flag if 0-S3 finds it" with "natively in
  Chromium (`--enable-features=WebMCP`) and through `@mcp-b/webmcp-polyfill` in Chromium, Firefox
  and WebKit, on a dedicated page; A-3's declarative form likewise".
- **§1.3 A-2:**
  - `registerTool` rejections are reported, never thrown;
  - results are always objects;
  - `consequentialHint` is advisory only, since Chrome 153 drops it;
  - the 30/500/150 budgets are Sygnal's own check.
- **§1.3 A-3:**
  - attributes go through `attrs-*`;
  - `respondWith` is called in the submit listener with a promise resolved after validation and
    flush;
  - `toolparamdescription` is emitted from labels;
  - an `autosubmit` option (P6-Q11).
- **§6 risk "WebMCP changes":** the mitigation stands. The two implementations already differ
  (§3 table), so the test helper normalizes both, and the spec gets rechecked at each phase start.
