## 1. Standard JSON Schema in the three libraries

### 1.1 The interface (spec 1.1.0, standardschema.dev/json-schema)

- The entry point is `schema['~standard'].jsonSchema.input(options)` and `.output(options)`. Each returns a plain object.
- `options` is `{ target, libraryOptions? }`. The targets are `'draft-2020-12' | 'draft-07' | 'openapi-3.0' | string`. Libraries are "strongly recommended" to support 2020-12 and 07, and "should throw" on a target they don't support.
- Both methods **may throw** when a part has no JSON Schema form. The consumer handles that.
- `input` vs `output`: they differ only when the schema transforms. For both tool arguments **and structured output**, the model produces the value that `validate()` receives, so **Sygnal always uses `.input`**. Using `output` would be wrong even for `output:`. Example: `z.string().transform(Number)` has input `{type:'string'}`, while its output schema throws.
- `StandardJSONSchemaV1` is separate from `StandardSchemaV1` (validation). Sygnal needs both on one object. Zod and ArkType put both on every schema.

| | Zod 4.6 | Valibot 1.5 | ArkType 2.2 |
|---|---|---|---|
| Where `jsonSchema` lives | on every schema's `~standard` | **only on `toStandardJsonSchema(schema)`** from `@valibot/to-json-schema` (a new object that spreads `~standard` and keeps `validate`) | on `~standard`, which is a getter returning a **new object per read** |
| Zod Mini | `~standard` has only `validate`/`vendor`/`version`: **no jsonSchema** (`z.toJSONSchema()` exists) | n/a | n/a |
| `draft-2020-12` / `draft-07` | ✓ / ✓ (07 uses `items: [...]` tuples) | ✓ / ✓ | ✓ / ✓ |
| `openapi-3.0` | ✓ (`nullable: true`) | ✓ | **throws** ("must be draft-2020-12 or draft-07") |
| Unknown target | **does not throw** (drops `$schema`) | throws | throws |
| `$schema` key | always | always | always |
| Lossy switch (`libraryOptions`) | `{ unrepresentable: 'any' }` | `{ errorMode: 'ignore' }` | `{ fallback: (ctx) => ctx.base }` (or per code: `date`, `predicate`, `morph`, …) |

The full output is in `out/probe.txt`. "≡" means the same as Zod up to key order.

## 2. Provider constraints and normalization

### 2.1 What the providers accept (docs read 2026-10-09)

| | OpenAI strict (tools and `json_schema`) | Anthropic strict (tools and `output_config.format`) | Anthropic non-strict `input_schema` | Gemini | Ollama 0.40.2 `/v1/chat/completions` |
|---|---|---|---|---|---|
| Root | object, not `anyOf` | object | object | — | tools: anything; `response_format`: grammar-compiled |
| `additionalProperties` | `false` on every object | `false` only | any | allowed (Interactions API) | — |
| Every property in `required` | yes; optional means `[T,"null"]` | no | no | — | — |
| `$ref`/`$defs` | ✓, recursion via `#` or `$defs` | ✓, **no recursion** | ✓ | `"$ref":"#"` in examples | `#/$defs/…` ✓; **`"$ref":"#"` → 400** |
| `oneOf` | not listed (use `anyOf`) | not listed | ✓ | not listed | ✓ |
| `allOf`, `not`, `if/then/else` | ✗ | `allOf` partly | ✓ | — | — |
| min/max on numbers | ✓ | **✗** | ✓ | ✓ | ✓ |
| `minLength`/`maxLength` | ✓ (✗ for fine-tuned models) | **✗** | ✓ | — | ✓ |
| `minItems`/`maxItems` | ✓ | `minItems` 0 or 1 only | ✓ | ✓ | ✓ |
| `prefixItems` | not listed | not listed | ✓ | ✓ | ✓, but **`items:false` → 400** |
| `format` | 9 formats | 10 (adds `uri`) | any | `date-time`, `date`, `time` | — |
| Limits | 5,000 properties, 10 levels, 1,000 enum values, 120 K characters | 20 strict tools, 24 optional params, 16 unions per request | — | "very large schemas may be rejected" | — |
| Enforced? | yes (grammar) | yes (grammar) | no | `responseJsonSchema` yes | **tool args: no** (even with `strict: true`); `response_format`: yes |

The OpenAI strict rule and the Anthropic SDK practice of moving unsupported constraints into the description are in `PROFILES` in `normalize.mjs`. Gemini's legacy `parameters` field is an OpenAPI-3.0 subset that ArkType can't target. No planned transport speaks Gemini natively, and its OpenAI-compatible endpoint or `parametersJsonSchema` take JSON Schema.

### 2.2 Proposed normalization (two layers)

**Layer 1: portable, in `sygnal/ai`'s A-1 module.** Every consumer (WebMCP, `chat`, `commandBar`, `t.tools()`, E-1) sends this schema.

1. `jsonSchemaOf(input)` calls `input['~standard'].jsonSchema.input({ target: 'draft-2020-12' })`.
   - If that throws, it retries once with the vendor's lossy `libraryOptions` (the table above, keyed by `~standard.vendor`). A lossy result is a dev **warning** (proposed SYG243). Validation still enforces the dropped part.
   - If there is no `jsonSchema`, or the retry also throws, the result is **SYG240**.
2. Clean-up, applied to every subschema:
   - drop the root `$schema`/`$id`;
   - `oneOf` → `anyOf`;
   - drop Zod's `±(2^53-1)` integer bounds;
   - `prefixItems` + `items:false` → `maxItems`, because Ollama rejects boolean subschemas.
3. Root self-references are hoisted. `"$ref":"#"` moves into `$defs.__root`, because Ollama rejects `#`, and wrapping changes what `#` means. ArkType's `$ref`-only root is inlined, so an object stays an object.
4. **A non-object root is wrapped** as `{ type:'object', properties:{ value }, required:['value'], additionalProperties:false }`. The root `$defs` are hoisted, and the root `description` moves onto `value`.

**Layer 2: strict, in the transports, opt-in** (`strict: true` on `openResponses`/`chatCompletions` against OpenAI, and on `anthropicMessages`).
- `strictify(schema, 'openai' | 'anthropic')`:
  - sets `additionalProperties:false` everywhere;
  - makes every property required, with optional ones nullable (type array + `null` in the enum, or `anyOf[…, null]`);
  - moves unsupported keywords and formats into the description as `{"minLength":1}`;
  - turns tuples into `items: {anyOf}`.
- It returns `errors` for a record (any provider) and for recursion (Anthropic). The transport then sends that tool non-strict, and dev reports it.
- The transport runs `unstrict(args, schema)` on every tool call and on the `output` JSON. It drops the `null`s the strict schema forced for keys the original schema leaves optional and non-nullable, so A-1 and the `ok` reply see the original shape.
- `uiMessageStream` sends the portable schema; the server's AI SDK applies its own provider rules.

**Results** (`out/normalize.md`), 21 cases × 3 libraries:
- every portable schema compiles in Ajv 2020 and accepts the JSON sample;
- every round trip validates, except `Date`, as expected: JSON can't carry a Date;
- every `strictify` output has 0 violations of the documented OpenAI and Anthropic rules, and its strict round trip validates;
- records have no strict form;
- recursion has no Anthropic strict form.

### 2.3 Where each part belongs

| Part | Where | Why |
|---|---|---|
| `jsonSchemaOf`, clean-up, hoisting, `{ value }` wrap, `fromToolArgs`, `repair` | `sygnal/ai` shared A-1 module | Every consumer needs the same tool schema and the same reverse step before validation |
| `strictify` / `unstrict` | `sygnal/ai`, imported only by transports that offer `strict` | Strictness is provider-specific (OpenAI ≠ Anthropic), most consumers never need it, and it is tree-shaken out otherwise |
| Caching | A-1, `WeakMap` keyed by **the schema object** (not `~standard`, which ArkType rebuilds on every read) | Conversion costs 0.1–1 ms per schema; tools are re-listed on every flush |

## 3. Non-object inputs: the `{ value }` rule

- **The rule.** Wrap when the root isn't `type: 'object'`, after inlining a `$ref` root. That covers string, number, enum, literal, array, tuple, union, discriminated union, nullable and recursive non-object roots. Object roots and records aren't wrapped.
- **The round trip.** `fromToolArgs(args, wrapped)` returns `args.value` when `args` is an object with a `value` key. Otherwise it returns `args` unchanged, which is the lenient unwrap. The result goes to `validate()`, and the validated output becomes the action's data.
- **On Ollama:**
  - Both models wrapped the primitives correctly in 12/12 calls (`{"value":"water the plants"}`, `{"value":"done"}`).
  - **Both models sent the wrapped discriminated union bare** (6/6 calls, `{"kind":"color","id":2,"color":"red"}`) and ignored `value`. The lenient unwrap made those calls succeed. It stays in the contract.
- **Structured output** uses the same rule. A `z.array(z.string())` output is sent as `{value:[…]}` and unwrapped before validation. It worked 4/4 on both models, strict and non-strict.
- **Edge cases.**
  - A wrapped schema whose own object branch has a `value` key is ambiguous under the lenient unwrap. The `value` key wins, which is the documented behavior.
  - A Collection item's `id` parameter has a collision problem; see P6-Q11.

## 4. Plain JSON Schema as `input`

| Option | Validation | Bytes (min / gzip) | Assessment |
|---|---|---|---|
| A. Pass-through, documented | none | 0 | Experiment 3's corruption returns for exactly the users who skip a library. ✗ |
| **B. Subset validator** (`mini.mjs`) | type (incl. integer and type arrays), enum, const, required, properties, additionalProperties, items, prefixItems, anyOf/oneOf, min/max, minLength/maxLength, pattern, local `$ref` | **1,725 / 885 B** (tree-shaken unless used) | Agrees with Ajv on **126/126** samples (all cases' good and bad samples). It doesn't check format, allOf, not, if/then, multipleOf or uniqueItems; those pass. |
| C. Require a Standard Schema | the library's | 0 | Simple, but forces a library for a one-enum tool and blocks Zod Mini users. |

**Recommendation: B, behind an explicit helper `jsonSchema<T>(schema)`** (the AI SDK uses the same name and shape). It returns a Standard Schema with `validate` (the subset) and `jsonSchema.input` (the object as is), so it takes the same path as the libraries. A raw object as `input` is SYG240 with the fix "wrap it with `jsonSchema()`".
- Types: a raw object in a `Standard | JsonSchema` union makes TypeScript report the wrong branch ("'~standard' is not assignable to undefined") instead of "number is not assignable to string" (tested). With the helper, `input` is one type and the errors are clear.
- Escape hatches: the helper also serves Zod Mini, older Zod, and any library without the extension, as `jsonSchema<T>(z.toJSONSchema(s))`. That checks less than the library would; a two-argument form `jsonSchema(json, { validate: s })` keeps the library's validation (P6-Q8).
- This changes PLAN-6 §6's risk line ("plain JSON Schema accepted as `input` too") to "through `jsonSchema()`".

## 5. A schema with no JSON Schema form: SYG240

The cases:
1. Not a Standard Schema at all (a function, a raw object, a Zod 3 schema without `~standard`).
2. A Standard Schema with no `jsonSchema`: Valibot without `toStandardJsonSchema`, Zod Mini, other libraries.
3. Conversion throws even with the lossy options. After the retry this is rare: Zod with `unrepresentable:'any'` gives `{}` for a Date.
4. Lossy conversion: a Valibot `check`, an ArkType `narrow`, or a Date that became `{}`. Zod drops refinements without saying so, so no warning is possible there.

| | Dev (`sygnal/diagnostics` loaded) | Production |
|---|---|---|
| 1–3 on `agent.actions[X].input` | **SYG240 error**, once per (component, action), at discovery (`onCreate`). It names the vendor and the fix: "wrap with `toStandardJsonSchema()` from `@valibot/to-json-schema`", "Zod Mini: `jsonSchema(z.toJSONSchema(s), { validate: s })`", "`z.date()` can't come from JSON: use `z.iso.datetime()` or `z.coerce.date()`". **The tool is not offered.** | The tool is not offered, silently (0 diagnostics bytes; dev already said). `t.tools()` lists it with `error: 'SYG240 …'` so tests catch it. |
| 1–3 on an LLM request's `output` | SYG240 error, plus the request fails with an `error` reply `{ error, request }` | the same `error` reply, with no console output |
| 4 (lossy) | **SYG243 warning** (proposed: SYG243, since 241/242 are taken): "the model doesn't see `<check>`; it's still validated" | nothing |

Rationale for not offering the tool: experiment 3 showed that schemaless tools corrupt state, and a tool the model can't call correctly only produces failed calls.

Rationale for no throw: one bad declaration mustn't take down the assistant for the whole subtree.

Static support: the K-1 `sygnal-check` rule can flag `input: v.…(` with no `toStandardJsonSchema` and `input: z.date()` without running anything. That is a new rule candidate below.

## 6. TypeScript

The sketch is `types/agent.d.ts`; the tests are `types/agent.type-test.ts`. `tsc` passes, and all 10 `@ts-expect-error`s fire.

```ts
type AgentAction<STATE, D> = { description: string; consequential?: boolean; when?: (state: STATE) => boolean } & (
  NoData<D> extends true ? { input?: never }                // the action takes nothing
  : IsAny<D> extends true ? { input?: AgentSchema<any> }    // untyped component
  : { input: AgentSchema<D> })                               // required; output assignable to D
type AgentDeclaration<STATE, ACTIONS> = { name: string; description?: string; read?: (s: STATE) => unknown
  actions: { [K in keyof ACTIONS]?: AgentAction<STATE, ACTIONS[K]> } }
// AgentSchema<D>: structural `~standard` with types?: { input: unknown; output: D } (no @standard-schema/spec dependency)
```

**What is checked:**
- keys are actions of the component (an excess-property error on the literal);
- **the schema's output** (after transforms) is assignable to the reducer's data type: `z.number()` for a `string` action is an error, and `z.enum(['all','later'])` for a filter type is an error;
- `input` is required when the action takes data, which catches "the model sends nothing";
- `input` is forbidden when the action takes none;
- `when`/`read` get the state type;
- the static is checked when the component function is assigned to a component type (the expando pattern);
- `ChatOk<typeof request>` infers `value` from `output`;
- this works the same with Zod, Valibot (wrapped) and ArkType.

**Limits:**
- On the expando pattern, a typo key slips through when at least one other key is valid. TypeScript only catches the all-wrong case, via weak-type detection. SYG150 in `sygnal-check` covers the rest.
- `jsonSchema<T>()` asserts T rather than inferring it.
- Untyped components get no checking.

**For the gate:** move the type test into `type-tests/p6-agent.tsx` against `src/ai.d.ts`, with the `agent?` member added to `Component` in `src/index.d.ts` (types only, 0 bytes).

## 7. End to end on Ollama (local, no keys)

`/v1/chat/completions` with five tools: Zod, Valibot (wrapped) and ArkType inputs; two wrapped primitives, one object, one discriminated union and one object with an optional field. Each prompt ran 3 times at temperature 0, with the `read` state in the system prompt.

| Model | Plain | With `repair` | Notes |
|---|---|---|---|
| qwen3:8b | **12/15** | — | All 3 misses were a hallucinated discriminator (`"kind":"label"`), rejected by validation as intended. The first calls took 60–180 s (model load); after that, 7–16 s. |
| llama3.2 (3B) | **9/15** | **15/15** | All 6 misses were **integers sent as strings** (`"id":"3"`). `repair` coerces them because the schema says integer. |
| llama3.2, strict schemas (`strictify` openai + `strict:true`) | — | **10/10** | Ollama accepts strict-shaped schemas and ignores `strict`. The arguments are still unconstrained (strings for integers again). |

- Structured output (`response_format: json_schema`) passed **8/8**: a wrapped array and an object with an optional field, both models, strict and non-strict, all valid after unwrap and `unstrict`.
- Schema acceptance (`ollama-refs.mjs`, `response_format`, 12 schemas): **two Ollama 400s found and fixed by layer 1.**
  - Zod's `"$ref":"#"` gave "unsupported $ref #"; the fix is hoisting into `$defs.__root`.
  - The tuple's `items:false` gave "schema must be an object"; the fix is dropping it in favor of `maxItems`.
  - After the fixes, 12/12 were accepted and valid.
- Takeaway: **Ollama doesn't enforce tool schemas.** Sygnal's validation is what protects state, and `repair` is what makes small models usable.

## Recommended contract

```jsx
Comp.agent = { actions: {
  ADD:        { description: 'Add a todo', input: z.string().min(1).describe('The todo text') },   // Zod 4.2+ / ArkType 2.1.28+
  SET_FILTER: { description: '…', input: toStandardJsonSchema(v.picklist([...])) },                // Valibot: wrapped
  PING:       { description: '…', input: jsonSchema({ type: 'object', properties: {…} }) },        // plain JSON Schema
  CLEAR_DONE: { description: '…' },                                                                // no data: no input
}}
// chat: { messages, output: z.object({ priority: z.enum([...]) }), ok: 'TRIAGED' } → TRIAGED gets { …, value }
```

1. `input` and `output` are **Standard Schemas that also implement Standard JSON Schema**, or `jsonSchema(json[, { validate }])`. Anything else is SYG240.
2. The model gets the **input-side** JSON Schema at `draft-2020-12`, after the layer-1 normalization.
3. A tool call goes through these steps in order:
   - `fromToolArgs` (`{ value }`, lenient);
   - `repair` (on by default; P6-Q10);
   - `validate`;
   - dispatch of the **validated output** with `cause: 'agent'`.

   An invalid call returns `{ ok: false, error, issues }` to the model. Each issue is `{ message, path }`.
4. `output` is validated the same way on `ok`. The `ok` reply gains **`value`**, the validated output, beside `text`. A failure goes to the `error` reply with `issues`, as `makeFetchDriver`'s `validate` does.
5. Strict mode is a **transport option**, default off. `unstrict` runs inside the transport, so nothing downstream sees forced nulls.

## Gaps (unnumbered G- candidates)

- **G-? L-1 `ok` has no field for the structured value.** PLAN-6 §1.1 lists `{ key, message, text, toolCalls, finishReason, usage }`; add `value`, and say that an `output` failure is an `error` reply with `issues`.
- **G-? PLAN-6 §1.1 says "the transport sends the JSON Schema form" without saying which.** It must be the `input` side (the model produces what `validate` takes), normalized by layer 1, and wrapped when not an object.
- **G-? PLAN-6 §6 promises raw plain JSON Schema as `input`.** Replace it with `jsonSchema()` (§4).
- **G-? The non-object wrap needs the lenient unwrap** (bare args accepted). Small models skip `value` for wrapped object unions (6/6). Not in A-1 today.
- **G-? Ollama rejects `"$ref":"#"` and boolean subschemas** in `response_format`. Layer 1 must hoist and clean them (fixed in the spike); recorded fixtures should cover both.
- **G-? Arg repair**: llama3.2 failed 6/15 on numeric strings without it. Not in PLAN-6.
- **G-? ArkType's `.describe()` replaces its validation message** ("must be The todo text"), which is what the model gets back on an invalid call. The docs should say so; A-1's error text could add the JSON pointer and the expected type.
- **G-? Schema conversion caching** must key on the schema object; ArkType's `~standard` is a fresh object per read.
- **G-? Diagnostic codes**: SYG240 covers "not a Standard Schema" and "no JSON Schema form" (one code; the message differs). The lossy case needs **SYG243** (warn). Strict-incompatible tools (records, recursion for Anthropic) need a dev info, perhaps folded into SYG673's range or a new **SYG675**.
- **G-? `sygnal-check` rule candidates**: an un-wrapped Valibot schema as `input` (it imports from `valibot` without `@valibot/to-json-schema`), and `z.date()`/`v.date()`/`'Date'` in `input`.
- **G-? Strict-mode limits**: Anthropic allows 24 optional params and 16 unions across all strict tools per request. A `chat` behavior over a big subtree can exceed that, so the transport should fall back to non-strict per tool past the budget.

## Plan changes (proposed)

- §1.1 L-1:
  - "Structured output: `output: schema` (a Standard Schema with Standard JSON Schema, or `jsonSchema()`). The transport sends the normalized **input-side** JSON Schema (a non-object wrapped as `{ value }`). `ok` gets `value`, the validated output. A failure is the `error` reply with `issues`."
  - Add `strict?` to the transports that support it (OpenAI-backed `openResponses`/`chatCompletions`, `anthropicMessages`).
- §1.3 A-1 Input: replace the bullet with the contract above. In order, the steps are:
  - layer 1 normalization;
