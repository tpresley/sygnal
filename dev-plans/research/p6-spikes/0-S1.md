## Answers

### 1. The driver on the reply machinery: works as specified

Under `run()` (jsdom), `test/p6-s1-chat-driver.test.js`:

- `delta` / `tool` / `ok` / `error` reach exactly the sender, with the PLAN data shapes. Sinks see
  the pre-action state (the request carried `q0` while the STATE reducer had made it `n: 1`).
- **latest** (default) per `(sender, key ?? ok ?? error)`: a second SEND aborts the first's
  signal synchronously; events pushed into the aborted stream afterwards deliver nothing. Another
  key runs alongside; `latest: false` keeps both (replies in completion order).
- `{ abort: 'reply' }` stops only that key; `{ abort: true }` stops all of the sender's runs.
- **Sender dispose** (a Collection item removed mid-stream): its signal is aborted at once,
  nothing delivered, no console error. **App dispose**: every stream aborted synchronously.
  A coalesced delta already scheduled (`coalesce: 50`) is dropped when the run is aborted.
- **Isolation**: two Collection items of the same component with the same key stream at once;
  latest/abort are per sender (item 1's STOP doesn't touch item 2's stream); each draft shows
  only its own text. A default-isolated sub-component and its parent with the same action names
  each get their own reply. Requests carry their scope path (`isolateValue` tagging, as
  `makeSocketDriver`), different per item. Since replies go by sender, isolation's only job here
  is to give the core a value-level isolator (no pipe per instance).
- **SYG610**: a request with a `then` key is refused (no stream), through `allowed()`.
- Over real `fetch` (Node, mock server): STOP mid-stream makes the server see the socket close
  early (`closedEarly: true`), and the draft doesn't change afterwards. Same in all three
  browsers against the Vite dev server's SSE route, for STOP and for `app.dispose()`.
- Real model (opt-in): llama3.2 via Ollama's `/v1/responses`, 91 chunks → 45 renders in 1,082 ms;
  STOP mid-stream leaves the draft unchanged.

### 2. Frame coalescing with a real rAF: budget confirmed, with one correction

300 tokens at 1 token / 2 ms under `run()`; renders counted in the view, DOM patches by a
MutationObserver (callbacks), frames by an independent rAF loop; `ms` from SEND to `ok`.

| Engine | transport | coalesce | renders | patches | ms | frames (ms/frame) | budget `ceil(ms/16)+2` |
|---|---|---|---|---|---|---|---|
| Chromium | SSE | none | 302 | 302 | 785 | 46 (17.1) | 52 |
| Chromium | SSE | frame | 47–64 | = renders | 745–1115 | 45–67 (16.6) | 49–72 |
| Chromium | in-page timers | frame | 92 | 92 | 1,494 | 90 (16.6) | 96 |
| Firefox | SSE | frame | 48–57 | = renders | 765–995 | 92–115 (**8.3–9.2**) | 50–65 |
| Firefox | in-page timers | frame | 100–136 | = renders | 1,686–2,523 | 203–254 (**8.3–9.9**) | 108–160 |
| WebKit | SSE | frame | 45–67 | = renders | 760–1208 | 46–72 (16.7) | 50–78 |
| WebKit | in-page timers | frame | 138–144 | = renders | 2,400 | 144 (16.7) | 152 |
| 120 Hz simulated (rAF every 8 ms), `minGapMs: 0` | SSE | frame | Chr 87, FF 73–79, WK 80–83 | | 914–1079 | | **50–66: over** |
| 120 Hz simulated, `minGapMs: 15` (default) | SSE | frame | Chr 46–51, FF 45–48, WK 45–62 | | | | 53–82: inside |

Findings:
- **One DOM patch per render, always** (patches = renders in every run, all engines): the core's
  one-flush-one-patch holds under streaming. A per-token stream costs 302 patches; frame
  coalescing 45–65 for the same 300 tokens over SSE.
- **renders ≤ frames + 2** in every run: one render for SEND, one per frame with new text, and
  the last delta and `ok` share a render (the driver flushes the pending delta synchronously
  before `ok`, so both land in one flush).
- **Correction: "per frame" isn't "per 16 ms".** Firefox's headless rAF runs at 8.3 ms (120 Hz),
  and so do ProMotion Macs, iPhones and most new Android phones. With pure per-rAF coalescing a
  120 Hz display gets twice the renders and breaks `ceil(duration/16)+2` (87 vs 60 in
  Chromium with a simulated 120 Hz rAF). The spike skips a frame that comes less than
  `minGapMs` (15 ms, by rAF's timestamp) after the last delta. That gives ≤ 60 deltas/s at
  60/75/90/120/144 Hz, and the budget holds in every run.
- In-page `setTimeout(2)` chains run at ~5 ms per token in browsers (the nested-timer clamp), so
  "300 tokens at 2 ms" takes 1.5–2.7 s there. The SSE route (server-side timers) gives the
  intended ~0.8 s. The budget uses the measured duration, so both are valid, but the gate should
  use the SSE route.

**Proposed gate assertion:** `renders <= Math.ceil(ms / 16) + 2`, with `ms` measured from the
action that sends the request to the render of `ok`, and `coalesce: 'frame'` defined as "at most
one `delta` per animation frame **and per 15 ms**". In vitest, run it under `vi.useFakeTimers()`:
it is then deterministic (39 renders, 38 deltas for 600 ms of fake time; budget 40), so assert
the exact count as well as the budget. In browsers, use Chromium (the gate engine), and keep the
Firefox run as the >60 Hz canary.

### 3. Hidden tab: rAF stalls; race it with a timer

- **Playwright can't hide a page headless.** Bringing another tab of the context to the front
  (Firefox, WebKit) or minimizing the window through CDP `Browser.setWindowBounds` (Chromium)
  both leave `document.visibilityState === 'visible'`, and rAF keeps firing. So the hidden state
  was simulated: rAF never runs its callbacks, and `visibilityState` reads `'hidden'`.
- **rAF-only coalescing (`fallbackMs: 0`):** no delta while hidden. The stream itself keeps
  flowing: fetch reads aren't throttled, and the driver accumulates the text. `ok` arrives on
  time, because the pending delta is flushed synchronously before it. Measured in all three
  engines: exactly 1 delta (the flush before `ok`), same final text.
- **Raced with a 100 ms timer (the spike's default):** 8–13 deltas over ~1 s, the same text.
  In a real background tab the browsers throttle that timer to about 1/s (Chrome: 1 s alignment;
  after 5 minutes hidden, intensive throttling makes chained timers ~1/min). So a background stream
  still ends at network speed, and its draft updates about once a second.
- Either way nothing is lost and `ok` / `tool` never wait. The race matters only for apps that
  act on deltas while hidden (a title "typing…", speech, logging), and it also covers rAF
  starvation under main-thread jank. It costs one `setTimeout` + `clearTimeout` per frame.
  **Recommendation:** rAF raced with `setTimeout(100)`, as built.

### 5. The L-4 fake: shape settled, prototype works

Built into `renderComponent`. The sink named by `llmSink` (default `'LLM'`), with no driver
passed, is **the real `makeChatDriver` over `memoryTransport`**, the way the HTTP fake runs
`makeFetchDriver`. So latest, abort, dispose, isolation and the reply data are the driver's own
rules, with no copy in the harness.

- `t.requests('LLM')`: the requests as sent (`{ abort }` commands not listed). Each stream is a
  pending entry in the same list as HTTP's, so t.respond's targets work unchanged: an action
  name or key, a partial request (compared by value), a predicate, `{ nth }`.
- `await t.stream('LLM', chunks, target?)`: chunks are strings, `{ reasoning }`,
  `{ toolCall: { id?, name, input } }`, `{ data, name? }` and `{ finish: reason | { reason, usage } }`.
  The stream **ends after the chunks** (`ok`) unless the options form says `{ end: false }`, and
  a `{ finish }` chunk also ends it. The promise resolves once the replies are reduced and the
  tree rendered.
- **Each `t.stream` call is one frame.** The fake owns the frame scheduler (the driver's
  internal `frame` option). A frame fires when the driver has consumed everything pushed so far
  (the transport's `onIdle`), so a call yields at most one `delta`, then `ok` if it ends. That
  is deterministic and independent of timers: the same tests pass under `vi.useFakeTimers()`
  with no clock driving.
- `await t.fail('LLM', error, target?)`: the stream's iterator throws, and the driver sends the
  `error` action. `await t.respond('LLM', 'text')` streams the whole text as one chunk.
- An aborted or superseded stream is no longer pending: `t.stream` on it throws "no pending LLM
  request" or "…is not pending" (the respond/fail wording), which is what a STOP test asserts.

Tests written on it (`test/p6-s1-llm-fake.test.js`, the samples §1 `Chat` and §9 test):
streams a reply (1 DELTA, then DONE); streams across calls with `end: false`, then STOP
mid-stream (draft cleared, later `t.stream` throws, DELTA texts `['Once', 'Once upon a']`); a
failure as FAILED; tool call + reasoning + data parts + finish reason; latest supersedes;
`t.respond`; fake timers; two Collection items answered by predicate and by partial request.

## Recommended internal design

**L-1 `makeChatDriver`** (about 1.5 KB gzip):
- State: one `Set` of runs `{ sender, key, ac }`. Key = `key ?? ok ?? error ?? 'default'`.
  `latest !== false` aborts the sender's runs under the same key before starting. Abort =
  remove + `ac.abort()`. `makeReplies(onStop)` aborts a disposed sender's runs; `dispose()` and
  sink `complete` abort all.
- Every reply goes through one `send(type, data)` that checks `!signal.aborted && !disposed`.
  That is the whole "an aborted stream delivers nothing" rule, and it covers scheduled deltas.
- Per run: `parts` (text and reasoning merged into the trailing part of the same type; tool and
  data parts appended), `text`, `pending` (text since the last delta), `toolCalls`. `delta` data
  carries a snapshot of the message (copied per frame: ≤ 60/s).
- Coalescing: `'frame'` = rAF raced with `setTimeout(fallbackMs = 100)`, else `setTimeout(16)`
  without rAF. A frame closer than `minGapMs = 15` (by rAF timestamp) to the last delta is
  skipped. `'none'`: per chunk; a number: a timer. **Before `tool` and `ok`, the pending delta is
  flushed synchronously.**
- An internal `frame` option replaces the scheduler (the fake). `transport.stream()` is called
  synchronously in the sink's `next`, so the fake links each stream to the request being sent
  (as `_tap` does for fetch).
- Isolation: `isolateSink` / `isolateValue` tag the scope path (as the socket driver);
  `isolateSource` returns the same replies-only source.
- **Packaging:** `sygnal/ai` must import the reply helpers from `sygnal` (internal exports), never
  bundle `replies.ts` (G-1). Better still, the driver itself lives in `src/extra/chatDriver.ts`
  as an internal export of `sygnal`, and `sygnal/ai` re-exports it. That keeps one copy for apps,
  the `sygnal/ai` subpath and the L-4 fake in `testing.ts`, at 0 B for apps that don't use it.
  Transports stay in `sygnal/ai`.

**L-4:** as in answer 5. Pending entries share HTTP's list, so `targetOf` / `pick` /
`noPending` / `scripted` are reused as they are. Add `end` to the options keys, and treat a
string `request` as a key or action name for the LLM sink.

## Gaps found (G- candidates)

- **G-1 (real bug, would ship): a subpath that bundles `src/extra/replies.ts` carries a second
  copy of `diagnostics/index.ts`, whose module init replaces `globalThis.__SYGNAL_DIAGNOSTICS__`.**
  With the first spike bundle, importing `sygnal/ai` silenced the app's dev checks: 13 browser
  tests failed (SYG103/104/149/430/640/641/645 never reported) and the suite hung in the Zag
  menus. With the replies helpers taken from `sygnal`, all 371 pass. This also costs ~1.1 KB
  gzip, and SYG610 from the second copy ignores the app's diagnostics mode. **Gate:** no
  `dist/*` subpath bundle may contain `__SYGNAL_DIAGNOSTICS__ =` (a dist-exports test). Check
  the existing subpaths for the same pattern while adding it.
- **G-2:** per-rAF coalescing doubles renders above 60 Hz (Firefox headless runs at 120 Hz; so
  do ProMotion and phone displays). Fix: `minGapMs` 15, as built.
- **G-3:** the 7 spike browser tests add ~20 s and push the full Chromium suite past
  run-headless' 90 s `TIMEOUT` (it ran in ~100 s). The gate's L-1 browser tests must be lean
  (one SSE frame measurement and one abort: ~3 s), or the limit must rise.
- **G-4:** a chat request without `error` loses failures silently (the fetch driver
  `console.error`s "nothing listens to errors()"). The chat driver should log an unhandled
  failure with a code, and K-1's SYG152 should cover `error` as well as `ok`.
- **G-5:** `t.fail('LLM', …)` on a request without `error` throws the HTTP wording ("no intent
  listens to LLM.errors() …"). The chat source has no `select()` / `errors()`, so the fake needs
  its own message.
- **G-6:** a request with no sender (sent from outside a component) is dropped silently. It
  needs a dev diagnostic (SYG671's family).
- **G-7:** `{ abort: true, key }` (fetch's form) isn't handled. Align with fetch.
- **G-8:** Playwright can't emulate a hidden page in any engine (headless), so hidden-tab
  behaviour is testable only by stubbing rAF and `visibilityState`. PLAN-6 should say so.
- **G-9:** PLAN-6 calls the parts "AI SDK `UIMessage`-compatible (`text`, `reasoning`,
  `tool-call`, `tool-result`, …)". But `tool-call` / `tool-result` are *model*-message content
  parts. AI SDK UI messages use `tool-<name>` / `dynamic-tool` parts with `toolCallId`, `state`,
  `input` and `output`. The spike used `{ type: 'tool-call', toolCallId, toolName, input }`.
  This needs a decision before L-1's types (P6-Q9).

## Open questions (P6-Q8+ candidates)

- **P6-Q8:** should `reasoning` stream as deltas? The spike grows the reasoning part but fires
  `delta` only for new text. A "thinking…" UI wants `{ text, reasoning, delta, message }` on
  reasoning chunks too. Recommendation: yes, the same frame budget, with `delta` holding only
  the new text.
- **P6-Q9:** the message part model: true `UIMessage` parts (`tool-<name>` with `state`), so
  messages round-trip to `useChat` servers unchanged, or the simpler `tool-call` / `tool-result`
  pair? Recommendation: true `UIMessage` parts, because D243's production default is an AI SDK
  server.
- **P6-Q10:** where the driver code lives: core `src/extra/` (an internal export re-exported by
  `sygnal/ai`, one copy, 0 B to apps; recommended) or only in the `sygnal/ai` bundle (then the
  L-4 fake in `testing.ts` either duplicates it or comes from a separate `sygnal/ai/testing`
  import)?
- **P6-Q11:** should `fallbackMs` / `minGapMs` be public options? Recommendation: no. Keep
  `coalesce: 'frame' | 'none' | ms` public and the two internal, documented as "at most one
  delta per frame, ≤ 60/s; ~1/s in a background tab".
- **P6-Q12:** `t.stream` ends the stream by default (`end: false` keeps it open). Is that the
  right default? Recommendation: yes. Most tests want the whole reply, and the samples §9 test
  reads that way. Also: keep `t.respond('LLM', text)` as the one-chunk shorthand?

## Changes to PLAN-6

- **§1.1 L-1:**
  - `coalesce: 'frame'` means "at most one `delta` per animation frame and per 15 ms; rAF raced
    with a 100 ms timer so a hidden tab still gets ~1/s".
  - The pending delta is flushed before `tool` and `ok`.
  - Add `{ abort: true, key }`.
  - An unhandled failure is logged (G-4).
  - Request key = `key ?? ok ?? error`.
- **§1.1 L-1 Messages:** settle the part model (G-9, P6-Q9).
- **§1.1 L-4:**
  - add `{ end: false }`;
  - add "each `t.stream` call is one frame (at most one `delta`), no timers involved";
  - `t.respond('LLM', text)` as the shorthand;
  - the fake is the real driver over an in-memory transport whose streams share HTTP's pending
    list and targets.
- **§3 Render budget:** keep `ceil(duration/16)+2`. Define `duration` (from the sending action to
  `ok`), and require the ≤ 60/s cap. In vitest, run under fake timers and assert exactly 39 renders
  (budget 40). In Chromium, use an SSE route on the dev server, not page timers; Firefox is the
  >60 Hz canary.
- **§3 new gate (G-1):** no subpath bundle contains a copy of the diagnostics module;
  `sygnal/ai` gets the reply helpers (or the driver) from `sygnal`.
- **§3 Browser tests:** hidden-tab behaviour by stubbing rAF / `visibilityState` (G-8). Keep the
  L-1 browser tests within the runner's 90 s budget (G-3).
- **§6 Risks, "streaming renders get expensive":** add ">60 Hz displays" with `minGapMs` as the
  mitigation.
