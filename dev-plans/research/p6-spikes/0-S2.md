## Answers

### 1. Discovery, registration, Switchable, HMR

**Discovery.** The layer walks `api.root` and `children()`, skipping instances that are
`disposed` or not `shown`. It reads `iv.def.view.agent`. Instances with the same declaration
name are grouped: kind `'item'` becomes one keyed tool.

**When the walk runs.** The tool table is marked dirty by `onCreate`, `onDispose`, `onPatch`
and `onReducer`. It is rebuilt lazily, at most once per flush: subscribers are notified after
`api.flushed()`.

**Correction to PLAN-6 A-1: hidden Switchable pages.** The plan says "registration follows
`onCreate`/`onDispose`, so a hidden Switchable page has no tools". That isn't true.
- Every Switchable page is created at mount and stays alive while hidden (`hosts/switchable.ts`).
  So `onCreate`/`onDispose` never fire on a page switch.
- The layer filters on `InstanceView.shown`, which is false on a hidden page and below it.
- It re-scans on `onPatch`, because a page switch changes the vnode.
- Tested: `shell_go('b')` swaps `page_a_hello` for `page_b_read`/`page_b_inc`, and a call to the
  hidden page's tool returns "no tool".

**HMR.** `run()`'s `hmr()` disposes the app, starts a successor, then reassigns
`app.__runtime`. A layer that holds the API is left on a dead runtime. So:
- the layer takes the **app object** (the `run()` result);
- on the root's `onDispose` it queues a microtask and re-binds to `app.__runtime` (new
  `addHooks`). Each public call also checks `app.__runtime !== api`.
- Tested:
  - `stats.rebinds === 1`;
  - the new component's `agent` description is live;
  - state and earlier agent changes carry over;
  - calls work after the swap;
  - the context subscription keeps publishing.
- `renderComponent` passes the API itself (there is no HMR there).

### 2. Collection items

**Shape.** One tool per item declaration, e.g. `todo_toggle({ id })`. Its `id` is an `enum` of
the live keys, in display order. A call is routed to the item whose `state.id` matches. Ids
are compared as strings, so `'2'` reaches item 2. An unknown id returns
`{ ok: false, error: 'no a todo with id 7; ids: 1, 2', keys }`. The "a todo" comes from the
declaration's `description`; the wording needs a separate label field.

**Keys.** The key isn't on `InstanceView`. The core keeps it as `inst.k` on the raw instance.
The layer uses `state.id`, which is what `keyOf` keys by. Id-less items (keyed by index) can't
be addressed; SYG441 covers that.

**Sort.** The enum follows display order: `[2, 1]` after `sort: 'text'`.

**Filter.** A filtered-out item is **disposed** (the Collection host keeps only shown items).
So it has **no tool**:
- With `filter: active`, `todo_toggle({ id: 2 })` (a done todo) returns "no … id 2; ids: 1".
- The todo is still in the owner's `read` projection, so the model can see it but not reach it.
- This is a gap (below).

**Nested Collections** (a kanban: lanes of cards):
- `card_star` covers every lane's cards, and the result state is the nearest ancestor with a
  `read`, here the lane.
- An id that appears in two lanes is listed twice in the enum (`['c1','c2','c3','c1']`), and the
  first instance wins. This is a gap.

**Removal.**
- **Removed while the user confirms:** the layer resolves the key again after `confirm` and
  reports "the … with id 2 is gone; ids: 1".
- **Removed between dispatch and processing** (an action queued ahead removes it): the drain
  skips the disposed instance, so `onAction` never fires for the call. The record's `ran` flag
  stays false and the call reports "did not run: … was removed first". The test reaches this
  path through a hook that dispatches during the drain.
- **An item that removes itself** (`REMOVE: () => undefined`) returns
  `{ ok: true, removed: true, state: <the list's read> }`.

### 3. `cause: 'agent'`

`api.dispatch(target, type, data, 'agent')` works at run time with only a type change: the
core stores the cause verbatim (`App.dispatch` → queue → `handle` → `onAction`).

What needed changing, all outside the core's run-time code:
- **Types:** `hooks.ts` `ActionCause` (0 bytes), and the cause unions in `index.d.ts`
  (`ActionCause`, `DevToolsActionCause`), `devtools.d.ts` and `checks/public.d.ts`.
- **The action log** (`checks/actionLog.ts`, used by `t.actions`, devtools and `inspect()`)
  normalizes causes and relabelled an unknown one as `'intent'`. One token keeps `'agent'`.
  This is dev-entry and testing bytes, not core.

Tested: `t.actions` shows `{ type: 'ADD', data: 'z', cause: 'agent' }`.

### 4. No-op, ABORT, throw, non-STATE sinks

**No core hook tells ABORT from same-state.** `handle()` skips `onReducer` for both ABORT and
`v === pre`, silently. A throw goes to `caught` → SYG216 → `onError` without the call's
identity.

**`wrapHandler` answers it.** The layer wraps handlers only for the action of the current agent
call. `onAction` matches the call: cause `'agent'`, target id, type, and data by identity.
Calls are serialized, so attribution is exact. The wrapper records each handler's outcome:

| Outcome | Meaning |
|---|---|
| `changed` | STATE, a structurally different state |
| `same` | STATE, `v === pre` |
| `equal` | STATE, a new object but `objIsEqual` |
| `abort` | ABORT, with an optional reason |
| `threw` | the handler threw (re-thrown, so the core still reports SYG216) |
| `sent` | a non-STATE sink got a value |
| `effect` | an EFFECT ran |

Constant model entries are wrapped with the core's semantics (`true`/`undefined` → the data). A
constant EFFECT is left alone, as the core ignores it. `ORIGINAL` is set on each wrapper, so the
action log shows the user's reducer.

**Finding: identity alone misses experiment 3's own failure mode.** Experiment 3's
`TOGGLE: s => ({...s, todos: s.todos.map(t => t.id === id ? … : t)})` with a wrong id returns
a **new, deep-equal** object. "Same state object" says it changed. The layer therefore
compares the pre-action and returned state structurally (`objIsEqual`, depth 50). This runs only
on agent calls, never per flush. Tested: `todos_toggle_by_id(99)` → "changed nothing";
`(1)` → ok.

**Proposed rule.**
- **Success:** at least one handler of the action had an effect:
  - a structural STATE change;
  - a non-ABORT value on any non-STATE sink (HTTP, EVENTS, PARENT, ELEMENT, READY, a driver);
  - an EFFECT that ran without throwing (its effect can't be observed, so it counts).
- **Failure:**
  - any handler threw → `'<A> failed: <message>'`;
  - else an ABORT → `'<A> was refused[: reason]'`;
  - else `'<A> changed nothing: check the input against the current state'`.

  Each failure returns the current `read` projection. Tested:
  - `SAVE` (HTTP only), `PING` (EFFECT only) and `TELL` (PARENT only) all return `ok`;
  - `MAYBE_SAVE`, whose HTTP handler returns ABORT, returns "refused";
  - `BROKEN` returns "BROKEN failed: kaboom".

**ABORT with a reason, at 0 core bytes.** `abort(reason)` returns `ABORT` and leaves the reason
in a module variable that the wrapper reads and clears. Tested:
`RENAME` → "RENAME was refused: the todo already has that text". A symbol can't carry
data, and `isAbort` compares the description, so this side channel is the cheap option.

### 5. `when` and the per-flush `read` publication

**`when` and `read` are cached by state identity.** Reducers are immutable, so an
instance's `when`/`read` result is reused while `iv.state` is the same object. No context
read-tracking is needed. D168's tracking is internal to the view and not reachable from hooks
anyway, and `when(state)` only reads state.

**Measured: 100 Collection items, 200 flushes each changing one item.**
- Exactly **1 `read()` and 1 `when()` call per flush**: 100 + 200 reads, 200 whens.
- **201 publications**: one per flush that changed the context, plus the initial one.
- Time per flush, jsdom, three runs:

  | Run | Without the layer | With the layer |
  |---|---|---|
  | 1 | 1.360 ms | 1.495 ms |
  | 2 | 1.376 ms | 1.545 ms |
  | 3 | 1.443 ms | 1.477 ms |

  The "with the layer" runs also rebuild `tools()` (with the 100-key enum) every flush, so the
  overhead is about **0.03–0.17 ms per flush** at 100 items. Most of it is the context diff
  (`objIsEqual` over all projections) and the walk.

**Optimizations, if needed:** compare per-instance projection identity instead of deep-diffing
the whole context, and skip the walk when only `onReducer` fired (the tree didn't change).

**Publication timing.** One of the four hooks marks the layer dirty, then `api.flushed()`, then
publish, so it runs once per flush. `subscribe(fn)` gets the whole context. L-3, A-2 and the
MCP Apps adapter all consume this.

### 6. `consequential`

**Shape.** `confirm(info) → boolean | Promise<boolean>`, where
`info = { tool, component, action, description, input, id? }`. The default is to decline.
- A per-call `{ confirm }` (boolean or function) overrides the layer's option.
- L-3 maps it to `pending` plus `APPROVE`/`DENY`; A-2 to a dialog.

**Queuing.** The confirmation is awaited **before** dispatch. So the action enters the FIFO
queue when the user approves, behind anything the user did meanwhile. Tested: the log order is
`ADD:simulateAction`, then `CLEAR_DONE:agent`.

**After approval** the layer resolves the target again and re-checks `when`:
- a removed item → "gone";
- `when` false now → "`todos_clear_done` is not available any more".

**Calls are serialized** in call order (default `serial: true`). Small models send their whole
batch at once (experiment 3), so each call sees the previous one's result. Tested with three
parallel calls.

### 7. Testing: `t.tools()`, `t.callTool()`, `t.agentContext()`

Prototyped in `renderComponent` on `agentLayer(api)`, created on first use.
- `t.tools()` returns `{ name, description, inputSchema, annotations }`.
- `t.callTool(name, args, { confirm })` returns the A-1 result. A consequential call with no
  `confirm` **throws** ("pass `{ confirm: true }` or `{ confirm: false }`"): a test should state
  which answer it means.
- `t.agentContext()` returns the `read` projections by declaration name. An item declaration
  gives an array with `id`.
- Zod's `~standard.jsonSchema` gives the input schema (`$schema` dropped). A non-object schema
  is wrapped as `{ value }`. A plain JSON Schema object is accepted too, with a minimal check.

The no-context traces add two findings:
- **llama3.2** called `todo_toggle({ id: "2" })` for "water plants". The enum was offered as
  `[1]` before the adds, and by the time of the call id 2 existed ("buy milk"), so the call
  passed and toggled the wrong todo. **An id-only enum doesn't help a model pick the right
  item.** The labels question (P6-Q11) follows from this.
- Both models called `todos_set_filter('active')` twice. The second call returned
  "SET_FILTER changed nothing". That is a **false failure for an idempotent setter** (P6-Q8),
  though it did no harm here.

## Recommended A-1 module design

```
sygnal/ai: agentLayer(app | api, { confirm?, serial = true }) → {
  tools(): Tool[]                       // { name, description, inputSchema, annotations }
  call(name, args, { confirm? }): Promise<Result>
  context(): Record<name, projection>   // the read projections (items: [{ id, ...read }])
  subscribe(fn): unsubscribe            // fn(context) once per flush that changed it
  stop()
}
abort(reason)                           // ABORT with a reason (see P6-Q12 for where it lives)
```

**Hook usage** (one layer through `api.addHooks`; nothing global, so it only touches the app it
was given):
- **`onCreate`, `onDispose`, `onPatch`, `onReducer`:** dirty flag, then a publish after
  `api.flushed()`.
- **`onDispose` of the root:** a microtask, then the re-bind for HMR.
- **`onAction`:** matches the pending agent call (sets `ran`).
- **`wrapHandler`:** wraps only the matched call's handlers; returns nothing otherwise
  (G-312 keeps the layers below).
- **RuntimeAPI:** `root`, `get`, `children()`, `dispatch(…, 'agent')`, `flushed()`,
  `addHooks()`.

**Tool naming:** `<snake(name ?? componentName)>_read` and `<name>_<snake(ACTION)>`.

**Call sequence:**
1. `serial` queue.
2. Find the tool (else "no tool …; tools: …").
3. Validate the input (Standard Schema, or JSON Schema).
4. Resolve the target (key → item).
5. `when`.
6. `confirm`.
7. Resolve and check `when` again.
8. Dispatch with `'agent'`.
9. `flushed()`.
10. The outcome rule from §4.
11. The nearest ancestor's `read` as `state`.

**Contracts this relies on.** They should be written into `04-hooks-contract.md`:
- `handle()` calls `onAction`, then `wrapHandler` per handler, synchronously, for the same
  action;
- the drain skips disposed targets without `onAction`;
- `run().hmr()` reassigns `app.__runtime` synchronously after the successor starts.

## Gaps (G- candidates, unnumbered)

1. **Filtered-out Collection items have no instance, so they have no item tool.** The owner's
   `read` still shows them, so an agent sees a todo it can't toggle. See P6-Q9.
2. **The same key in two Collections of one item component** (per-lane ids on a board) gives
   an ambiguous route: the enum lists the key twice and the first instance wins. The core
   allows it (keys are per Collection). It needs a dev warning (extend SYG441) or qualified ids.
3. **The item key isn't on `InstanceView`.** The layer uses `state.id`, so id-less items can't
   be addressed (SYG441). A `key` getter on `View` would cost core bytes; it isn't needed if
   ids are required.
4. **The action log relabelled unknown causes as `'intent'`.** Fixed on the branch
   (`actionLog.ts`). Devtools' cause filter types need `'agent'` too.
5. **Identity no-op detection is insufficient** (§4). A-1's text says "same state object". It
   should say "structurally unchanged".
6. **Idempotent setters report "changed nothing"** (P6-Q8).
7. **Id enums carry no labels**, so models guess ids without the context (P6-Q11).
8. **A `setState` on a hidden Switchable page's state** fires neither `onReducer` nor `onPatch`,
   so the context publish misses it until the next flush that does. An `onFlush` hook would fix
   it (core bytes), or accept it.
9. **Duplicate non-item declarations** (two tag children with one `agent.name`): the first wins,
   silently. SYG440, as reserved.
10. **The testing prototype puts the layer into `index.esm.js` and the UMD** (about 3.1 KB
    gzip). P6-Q10.
11. **`wrapHandler` replicates the core's constant-entry semantics.** That is fragile coupling;
    a core test should pin it.

## Open questions for the user (P6-Q8+ candidates)

| # | Question | Recommendation |
|---|---|---|
| P6-Q8 | An agent call that changes nothing because the state is already as requested (`SET_FILTER('active')` twice): failure or success? | Keep it `ok: false`, but say "changed nothing (already so, or the input matched nothing)" and include the state. Per action, `idempotent: true` makes it `{ ok: true, unchanged: true }`. |
| P6-Q9 | Filtered-out items have no tool. | Document it: put an owner-level action that takes an id (`TOGGLE_BY_ID`) next to filters. Optionally, the layer lists filtered keys in the error ("hidden by the current filter"). Don't keep instances for hidden items: that's a core change. |
| P6-Q10 | `t.tools`/`t.callTool`/`t.agentContext` need the layer inside `renderComponent`. | Accept the ~3.1 KB gzip in `index.esm`/UMD (apps tree-shake it). Or have `renderComponent` load it through a registry that `sygnal/ai` fills, which makes tests import `sygnal/ai`. The first is simpler. |
| P6-Q11 | Item ids for models: enum of ids only, or labelled? | Add `agent.label: (state) => string` for items. The `id` parameter becomes `oneOf: [{ const: 1, title: 'water plants' }, …]`, or the labels go in the parameter description (Chrome's 150-char budget limits that). |
| P6-Q12 | Where does `abort(reason)` live? | In `sygnal` (`shared.ts`, tree-shaken, 0 core bytes), so reducers don't import `sygnal/ai`, with `sygnal/ai` reading the reason through the same module. |
