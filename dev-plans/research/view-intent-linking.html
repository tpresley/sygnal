View–Intent Linking Options

Today a view and its intent are linked by a CSS class written twice: className="inc" in the view and DOM.click('.inc') in the intent. This page measures how that link is used in practice, shows six alternatives on the same component, and recommends one. Every option keeps actions defined only in .intent and puts no handlers in the view.

Plan numbers (updated 2 October 2026): the ecosystem plan, called PLAN-4 when this page was written, is now PLAN-5. Controls are planned in PLAN-4 (controls and core ergonomics), as CT-1.

Hard constraint, from PLAN-1 §0: the view never names an action. That rules out <button action:click="X"> and its relatives, which are discussed separately at the end.

What the code actually does

I parsed the Sygnal code from the final Opus eval (p4-final2, 105 trials) and the Haiku eval (p4-haiku2), plus the 11 repo examples. Each intent selector was resolved to the JSX element it targets.

96–99%of intent targets are form controls (button, input, textarea, select, form): 292/303 Opus, 285/294 Haiku, 67/68 examples. The rest are mostly span.
81%of class names in agent intents are the action name re-spelled: INC ← .inc, ADD_TASK ← .add-task (66% exact, 15% a near match). The second vocabulary is mostly redundant.
38%of intent classes in the examples are also styling hooks (26/68), so renaming a style can silently unwire an action. The eval tasks have no CSS, so this can't be measured there.
0complex selectors in agent code. Every selector is a single .class, [attr] or document. Full CSS selector power is unused.

Three conclusions follow:

  • The link is almost always "this one control". It isn't a query.
  • People already name the control after the action, so the second vocabulary adds little.
  • The class doing double duty as style hook and wiring hook is a real hazard in hand-written apps.

The cognitive load comes from two sources. The link is a string by convention, so nothing in the language connects its two ends. And a reader of the view can't tell which elements are wired.

The same component, six ways

This is a todo item with two controls inside a Collection, plus a draft field. The status quo comes first for reference.

0

Status quo: shared class string

View
<li className="item">
  {state.text}
  <button className="done">✓</button>
  <button className="remove danger">x</button>
</li>
Intent and test
Item.intent = ({ DOM }) => ({
  DONE:   DOM.click('.done'),
  REMOVE: DOM.click('.remove'),
})
t.simulateEvent('.done', 'click')

A typo is caught by SYG110 (sygnal-check or the runtime), not by the editor. Renaming takes edits in three places: view, intent and tests. Agents know CSS well.

A

Reserved naming prop + DOM.target() (your baseline)

Works, small gain
View
<button ui="done">✓</button>
<button ui="remove" className="danger">x</button>
Intent
DONE:   DOM.target('done').events('click'),
REMOVE: DOM.target('remove').events('click'),
  • It separates wiring from styling and marks the wired elements.
  • The link is still a string in two places, it adds a reserved prop and a source function, and typos are still found only by the checker.
  • Prior art: @cycle/react uses a sel prop and select('inc'), and also accepts Symbols, which points toward option D. (From memory; not re-checked.)
B

Native name attribute

Cheap, partial
View
<button name="done">✓</button>
<button name="remove" className="danger">x</button>
<input name="draft" value={state.draft} />
Intent
DONE:  DOM.click('[name="done"]'),       // works today
DRAFT: DOM.input({ name: 'draft' }).value(),  // possible sugar
  • It needs no new concept, since name is HTML and works today (experiment X6). It is valid on form-associated elements, which is 96–99% of the measured targets, and the gap is mostly clickable spans, an accessibility smell anyway.
  • It lines up with forms: PLAN-5's F-1 and processForm key fields by name.
  • It is option A with a native attribute: two strings, checker-only typo detection, no editor support.
C

Role + accessible name (Testing Library style)

Not for wiring
View
<button aria-label="Mark done">✓</button>
<button className="danger">Remove</button>
Intent
DONE:   DOM.click({ role: 'button', label: 'Mark done' }),
REMOVE: DOM.click({ role: 'button', label: 'Remove' }),
  • It reads best of all: the intent describes what the user sees, there is no name to invent, it forces accessible labels, and agents know getByRole well. A userland version passed in X6.
  • It breaks as soon as copy changes or the app is translated. Duplicate labels are ambiguous, a label built from state ({state.x}) can't be checked statically, and computing accessible names costs runtime bytes in both the real and the mock DOM.
  • It belongs in tests (G-14), not in wiring.
D

Element tokens used as JSX tags ("controls")

Recommended
View
import { controls } from 'sygnal'
const { Done, Remove } = controls({ Done: 'button', Remove: 'button' })

function Item({ state }) {
  return (
    <li className="item">
      {state.text}
      <Done>✓</Done>
      <Remove className="danger">x</Remove>
    </li>
  )
}
Intent and test
Item.intent = ({ DOM }) => ({
  DONE:   DOM.click(Done),
  REMOVE: DOM.click(Remove),
})

// renders <button data-control="Done">✓</button>
t.simulateEvent(Done, 'click')
expect(t.query(Remove).className).toBe('danger')
Why it is better
  • The link is a variable, not a string. A typo is a ReferenceError at import time or a TS error in the editor. Go to definition, find references and rename across view, intent and tests come free from the TypeScript language service, with no Sygnal tooling.
  • The view shows what's wired. Capitalized control tags stand out from static markup, so a reader can see every interactive element without opening the intent.
  • Styling is decoupled. className goes back to being style-only, which removes the 38% double-duty hazard.
  • It types the element. controls({ Draft: 'input' }) makes <Draft> accept exactly the props an input accepts, and DOM.input(Draft).value() knows it's an input.
  • Nothing else changes. The shorthands (DOM.click, .value(), .data('id')), isolation (each Collection item sees only its own Done), document selectors and SSR stay as they are. Names are given, so the attribute is deterministic and readable in HTML.
  • It fits existing habits. 81% of agent code already names the element after the action, so INC: DOM.click(Inc) is the same habit with a checked link. The pattern resembles styled.button, which agents know.
Prototype (experiment X5)

A 15-line userland controls() using the pragma's fragment path rendered <button class="danger" data-sygnal-control="Remove">. It drove a todo list with a draft input and a Collection with per-item Done/Remove, and passed in both mock and real DOM. One thing failed: today DOM.select() requires a string ("expects the argument to be a string as a CSS selector"), so the prototype used DOM.click(Done.sel). Accepting the token is the core change.

Costs and risks
  • Core: estimated at about 80 B gzipped, not measured. That covers a control marker in the pragma (instead of borrowing the fragment path), the DOM source and shorthands accepting a token, and simulateEvent/query accepting one.
  • One new concept, and a declaration line per component. The view, intent and tests lose their string bookkeeping in exchange.
  • Capitalized tags normally mean components. An agent might give Done an intent or state. Name the concept "controls, not components" in the docs, and diagnose .intent/.model set on a control.
  • Isolation still applies. A parent that imports a child's control and listens to it never fires, the SYG104 case. The checker can now flag it exactly by identifier, rather than by CSS cross-referencing.
  • Two forms during migration. Class selectors keep working as an alternative form. sygnal-check --fix can rewrite the 96–99% single-control cases mechanically: create the control, replace the tag, and drop the class when no CSS uses it.
D′

Variant: controls as a component static

Fallback shape
View
Item.controls = { Done: 'button', Remove: 'button' }
function Item({ state, controls: { Done, Remove } }) {
  return <li>{state.text} <Done>✓</Done> <Remove>x</Remove></li>
}
Intent
Item.intent = ({ DOM, controls: { Done, Remove } }) => ({
  DONE: DOM.click(Done), REMOVE: DOM.click(Remove),
})

This keeps everything in Sygnal's fixed component slots, which agents like. But it means destructuring in two signatures, it loses import-time ReferenceErrors for typos (a missing key is just undefined), tests can't import the controls, and TypeScript typing needs another generic. Prefer D unless the eval shows agents struggle with the module-level declaration.

E

Keep strings, add editor tooling

Complement only

A TypeScript language-service plugin would give completion of view classes inside DOM.click('…'), go-to-definition between class and selector, cross-file rename, and inlay hints showing → DONE beside each wired element. It changes no API and helps humans in an editor. It does nothing for agents, who already rely on sygnal-check, and doesn't fix the style/wiring overlap. If D is adopted, standard TS tooling makes most of this unnecessary.

Recommendation

Adopt D (controls) for 6.0, gated by an eval A/B before it becomes the canonical form. It is the only option that removes the string link instead of moving it, and it does that with the language's own scoping, so humans get IDE navigation and agents get immediate errors. It is also the only option that improves both ends: the view shows what's wired, and the intent names a real, typed element.

Steps:

  1. Core: a pragma marker for controls; DOM.select and every shorthand accept a control; simulateEvent, query and queryAll accept one. Measure the bytes against the D77 reserve.
  2. Types: controls() infers intrinsic props per tag, and enriched streams know the element type.
  3. Checker: a control declared but never rendered (the new SYG110), rendered but never listened to (info), listened to by a parent (SYG104 by identifier), and a control given .intent/.model. Plus --fix to migrate single-class selectors.
  4. Eval: run tasks 06, 07, 08, 12 and 16 plus the TS tier, on Opus and Haiku, with the skill rewritten to controls. Measure learn time, iterations and wiring failures. Make it canonical only if learn time doesn't rise. Task 06 ("fix selector typo") becomes a ReferenceError, which is itself the point.
  5. Docs: about neutral in llms.txt. The control recipe replaces the class-selector and SYG110 guidance lines. CSS-selector strings move to alternative forms, still used for document and the rare structural query.

Use B (name) for forms through F-1, and C only in tests (G-14). Both complement D; neither replaces it.

Follow-up: should DOM.click(MyComponent) work?

The idea: let intent take a component as well as a control, with the event bound to the component's root element. Recommendation: don't support it. Raise a diagnostic with a fix instead, and point to two patterns that already work.

Why not

Three problems

  • The parent would depend on the child's markup. A child's public output is what its PARENT sink returns, read with CHILD.select(Child). A listener on the child's root also hears every click that bubbles up from inside the child. In experiment X7, one click on the child's inner button produced both the child's PARENT value and the parent's wrapper event. Restructuring the child would silently change the parent's behaviour.
  • "Root element" is often undefined. Fragments have several roots. Some components switch roots between renders (a loading <div> that becomes a <ul>). A component can render nothing. A Collection holds many instances, so the parent would need an id anyway. A Portal's DOM lives elsewhere, so its events never bubble to the root. Each case would need its own rule.
  • Agents will try it, because controls look like components. DOM.click(Component) should therefore fail loudly with the fix, not quietly do something.
Instead

Two patterns, depending on who owns the interaction

The child owns it (canonical, unchanged)
// TaskCard
TaskCard.intent = ({ DOM }) => ({ PICK: DOM.click(Pick) })
TaskCard.model  = { PICK: { PARENT: (s) => ({ id: s.id }) } }
// parent
Board.intent = ({ CHILD }) => ({ PICKED: CHILD.select(TaskCard) })
The parent owns the area around a child
const { Pick } = controls({ Pick: 'div' })
// the parent's view: its own element around the child
<Pick><TaskCard state="task" /></Pick>
Board.intent = ({ DOM }) => ({ SELECT: DOM.click(Pick) })

In the second pattern the wrapper belongs to the parent, so ownership is explicit and the child's root shape doesn't matter: fragments, conditional roots and empty renders all work. It depends on one rule that still needs to be decided (see below).

Bugs found

Testing this exposed two isolation problems

Fix in 6.0
  • Fragment-root components lose isolation in the real DOM (experiment X8). A child whose view returns <>…</> never receives its own events, and the parent's DOM.click('.fa') catches them instead (fragHits=0, leakFrag=1). The mock DOM gets it right (fragHits=1, leakFrag=0), so renderComponent tests pass while the real app is broken. The likely cause is that makeIsolateSink puts the scope on a single root vnode, and a fragment doesn't have one. Fragment roots are already broken with today's plain selectors, independent of controls.
  • The mock and real DOM disagree about bubbling out of a child (X7). Clicking inside an isolated child reaches the parent's wrapper listener in the mock DOM but not in the real DOM. Until they agree, the wrapper pattern above works only under the mock DOM.
Decision needed: should a listener on an element the parent itself rendered hear events that bubble out of its children? Recommendation: yes. That is native DOM behaviour, it is what the mock already does, and the wrapper pattern needs it. The parent still can't select elements inside a child, so SYG104 is unchanged.

Deliberately not proposed: action-tagged elements

The data shows that 81% of the time the class already is the action name, so <button intent="INC">, with a default event by element type and the intent listing only exceptions, would remove the most code. It is also how Elm (onClick Msg) and Hyperapp (onclick={Action}) work, and PLAN-3's router already intercepts plain <a href> clicks, a view-declared intent of the same kind. It still names actions in the view, though, which is exactly what PLAN-1 rejected because readers would look in two places. I'm recording the data point, not reopening the decision. Option D gets most of the benefit while keeping intent as the only place where actions are defined.

Experiments

  • Corpus analysis: Babel parse of 270 + 270 agent-written source files and 44 example files; selectors resolved to JSX tags by class; class names compared with intent keys.
  • X5 controls prototype: userland, 15 lines, mock and real DOM, Collection isolation. Passed. The only blocker is that DOM.select requires a string.
  • X6 native name + role/label: both selection styles passed under dom: 'real', including a click on a child <b> inside a named button.
  • X7 parent wrapper around children: the mock DOM logged wrap:BUTTON | child:inner-clicked | wrap:SPAN | wrap:BUTTON | wrap:P; the real DOM logged child:inner-clicked | wrap:a | wrap:b.
  • X8 fragment-root isolation: the mock DOM gave frag=1 box=1 | leak frag=0 box=0; the real DOM gave frag=0 box=1 | leak frag=1 box=0.
