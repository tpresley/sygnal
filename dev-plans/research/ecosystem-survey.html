Research · Sygnal 5.4 / 6.0 planning

Sygnal Ecosystem Survey

Which React/Vue ecosystem libraries are worth porting or adapting to Sygnal, and whether an adapter can bring the long tail in. npm data for the week 2026-09-24 to 09-30. Six throwaway experiments, all passing.

The good news is that most of the ecosystem's real value has already moved into framework-agnostic cores: TanStack's *-core packages, Zag.js machines, Floating UI, Tiptap/ProseMirror, chart libraries and validation libraries. Their official React/Vue/Lit adapters are often under 150 lines. Sygnal does not need ports of most of these. It needs one well-designed integration primitive and a handful of native features where the gap is architectural.

Recommendations

  1. Add a first-class Widget primitive to core P1. It gives any imperative library (or a React/Preact/Vue component) a host element with mount/update/unmount hooks, and turns its callbacks into DOM events that intent reads. I prototyped it in about 25 lines; it unlocks charts, editors, carousels, date pickers, maps and the React long tail in one move.
  2. Endorse web components as Sygnal's "component library" answer P1. Web Awesome, Ionic and Material Web already work with zero code (experiment E1). Add docs, JSX typings for custom elements, and a .detail() stream enricher.
  3. Build three things natively, because their state belongs in Sygnal's state tree: a router P1, forms with Standard Schema validation (zod/valibot/arktype) P1, and toasts P2.
  4. Ship accessible headless primitives (Dialog, Menu, Popover, Select, Combobox, Tooltip) as a separate sygnal-ui package backed by Zag.js P2. Accessible focus/keyboard behaviour is the part nobody should rewrite. A Zag dialog ran under Sygnal state in about 45 lines (E3).
  5. Fold a query cache into the planned network layer (ROADMAP #16) P2. TanStack Query is the most-loved React library; its core runs as a 25-line Sygnal driver (E5).
  6. Treat a React adapter as an opt-in escape hatch, not a strategy P3. It works (E2), but costs 69 KB gzip, more than Sygnal itself. Running the same component on preact/compat also works (E6) and costs about 10 KB.

Update, 2026-10-02: the router and the query cache (items 3 and 5) went to the 6.0 network-layer session, which now plans them as additions to its existing PLAN-3 work. Everything else is planned in PLAN-5 (drafted as PLAN-4 and renamed when plans were numbered in run order). It runs after PLAN-4 (controls and core ergonomics) and ships in the same 6.0.0 release. Plans: dev-plans/PLAN-5.md and dev-plans/HANDOFF-to-PLAN-3.md.

Three ways a library can reach Sygnal

Each ecosystem category falls into one of three tiers. The tier decides the work: documentation, a thin adapter, or a native feature.

Tier A · works today

Use as-is

Web components, pure functions (zod, date-fns, clsx, i18next core), and libraries that take an element through a ref (Floating UI, AutoAnimate, Motion animate). Work needed: documentation and recipes.

Tier B · thin adapter

Wrap the core

Agnostic cores with a state or lifecycle (TanStack Table/Virtual/Query, Zag.js, Tiptap, CodeMirror, Embla, Chart.js, dnd-kit/dom), plus foreign-framework components. Work needed: the Widget primitive, plus a small driver or helper per library.

Tier C · native

Build in Sygnal

Features whose state must live in the one state tree, or that shape the app: routing, forms and validation, toasts, list transitions, browser-API sources. Work needed: a Sygnal design (MVI, drivers, diagnostics, test fakes).

Experiments

I ran each experiment as a Vitest + jsdom test against the built sygnal 5.4.0 dist/, using renderComponent(App, { dom: 'real' }). All six pass. The code is in dev-plans/research/ecosystem-experiments/ (uncommitted; npm i && npm test).

Web components

pass
E1

A shadow-DOM custom element (a stand-in for Web Awesome). JSX props become element properties, so arrays and objects pass through intact. attrs={{…}} covers attribute-only APIs, and a composed CustomEvent fired inside the shadow root reaches DOM.select('.pick').events('x-change').

adapter code: 0 lines

React island

pass
E2

A React 19 component with its own useState, mounted on a host vnode's insert hook, re-rendered on postpatch, and unmounted on destroy. Callback props dispatch bubbling CustomEvents on the host, so the app's intent stays canonical. Props flow both ways across re-renders.

island ≈ 25 lines · React adapter ≈ 10 lines

Zag.js dialog

pass
E3

A VanillaMachine per host element, rendered through a private snabbdom patch (the same technique as Portal). Sygnal JSX spreads zp(api.getTriggerProps()), which converts to { attrs, on, props, style }. The open prop is controlled from Sygnal state, onOpenChange becomes an action, and ARIA wiring and Escape dismissal work.

adapter ≈ 45 lines

TanStack Table

pass
E4

createTable() is called in the view as a pure function of Sygnal state. Sorting, global filter and pagination live in the state tree and change through ordinary model reducers. No adapter was needed. I tested v8; v9 (now current) changed the API and needs a re-check.

adapter code: 0 lines

TanStack Query driver

pass
E5

query-core as a driver: a sink of { category, queryKey, queryFn, staleTime } and a source of QUERY.select(category). Verified a cache hit when switching back to a cached key, and a refetch after invalidate.

driver ≈ 25 lines

preact/compat island

pass
E6

The same React-API component source running on preact/compat through the same island(). This is how a bundler alias could host React-only libraries at a seventh of the cost.

adapter ≈ 6 lines

What the app code looks like (E2)

function App({ state }) {
  return <div>
    {island(reactAdapter(StarRating), {
      props: { value: state.rating },   // in: plain props, re-sent on every render
      events: ['onChange'],              // out: callbacks become DOM events on the host
      className: 'rating',
    })}
  </div>
}
App.intent = ({ DOM }) => ({ RATE: DOM.select('.rating').events('onChange').map(e => e.detail) })
App.model  = { RATE: (state, rating) => ({ ...state, rating }) }

This keeps Sygnal's rule that JSX has no event handlers: the foreign component's callbacks never reach the view, only the intent. Findings from building it:

  • A hand-built vnode without explicit children/text/elm keys is silently dropped by Sygnal's JSX child handling. A core Widget should own vnode construction so users never hit this.
  • The host must be opaque to snabbdom (no children in the vnode), or the two renderers fight over the subtree. A stable key keeps the host element, and its widget instance, across reorders.
  • The first Zag version had a stale-closure bug: props captured at mount overrode later ones. A core primitive should take props from the newest vnode in every hook. This is the kind of bug users would otherwise write themselves.
  • Zag's controlled props settle in a microtask after updateProps. Sygnal's t.next() already waited long enough here, but the test helpers should document or absorb this.

Can an adapter bring in React and Vue libraries?

Yes, and it's cheap to build (E2, E6). It is the same technique Astro islands, qwik-react and r2wc use: each foreign component gets its own root on a host element. Their documented pitfalls apply to Sygnal too:

  • Size. React 19 + react-dom is 69 KB gz, Vue's runtime 25 KB, against Sygnal's 42 KB. One date picker can more than double an app. preact/compat (9.8 KB) is the realistic host, but libraries that depend on React 19 internals may misbehave on it.
  • Context doesn't cross roots. Theme, QueryClient and router providers must be recreated inside every island. Component systems (MUI, Radix Themes, antd) fit badly; standalone widgets fit well.
  • Portals escape the host. Radix and MUI overlays render to document.body, so their DOM events never pass the host and only the bridged callbacks reach intent. That's fine as long as the adapter exposes callbacks, not DOM.
  • Testing and SSR. Islands need dom: 'real'; the default mock DOM can't run them. SSR would render a placeholder unless each adapter adds renderToString and hydration.

Verdict: ship the generic Widget in core, and offer sygnal/react (and possibly sygnal/vue) as small, explicitly opt-in packages, documented as "for that one component you can't replace". Don't make them the answer for anything common. Common needs should have a native or Tier-A answer, which is the point of this survey.

Widget: proposed core API

Based on what the prototypes needed. It follows the preventInstantiation marker pattern that Portal and Transition use, so the pipeline treats it like the other special components.

import { Widget, defineWidget } from 'sygnal'

const DatePicker = defineWidget({
  mount(el, props, emit) { const fp = flatpickr(el, { ...props, onChange: (d) => emit('change', d[0]) }); return fp },
  update(fp, props)      { fp.setDate(props.value, false) },
  unmount(fp)            { fp.destroy() },
  events: ['change'],                         // declared, so sygnal-check / SYG110 know the names
})

// view
<Widget of={DatePicker} className="due" value={state.due} />
// intent
DUE: DOM.select('.due').events('change').detail()
  • Testing: in the mock DOM, record the widget's latest props (t.widget('.due').props) and fake its output (t.widget('.due').emit('change', date)), mirroring the t.respond fakes for drivers.
  • Diagnostics: catch a widget emitting an undeclared event, a missing key inside a Collection, and a mount that throws (handled by the error boundary, as for views).
  • Adapters on top: fromReact(Comp), fromPreact, fromVue, fromZag(machine, render), fromWebComponent (properties + events). Each is a defineWidget call.
  • SSR: renders the host element (optionally with a fallback) and mounts on the client.

Suggested sequence

First
  • Widget / defineWidget in core, with test fakes and diagnostics
  • Web components guide, JSX typings, .detail() enricher
  • Recipes: Chart.js, Tiptap, Floating UI, auto-animate, TanStack Table
Next major
  • Native router (SPA), designed alongside the Vike integration
  • Forms with Standard Schema validation
  • Network layer with a query cache (ROADMAP #16)
Packages
  • sygnal-ui: Zag-backed Dialog, Popover, Menu, Tooltip, Select, Combobox; native Tabs, Accordion, Toast
  • VirtualCollection, FLIP list transitions, browser sources pack
Opt-in / later
  • sygnal/react (preact/compat-friendly), possibly sygnal/vue
  • DnD pointer/touch + sortable; HEAD driver; i18n recipe

Each native feature should follow the PLAN-1 conventions: canonical forms only, SYG codes, a renderComponent fake, llms.txt and skill coverage, and an agent eval. That is where Sygnal can beat the React versions, which agents often misuse.
