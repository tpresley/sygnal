# The `mod` eval tier (tasks 35–43): modifying existing code

**Question.** Does Sygnal 6.0's structure (MVI: intent / model / view, canonical forms, diagnostics) let an agent *modify* an existing app — add, change and remove functionality in existing components — as well as React, despite React's pre-training advantage? Tiers 01–34 mostly ask for new code in small starters; this tier starts every trial in a working app that already has its own tests.

**Design.** 3 app sizes × 3 operations = 9 tasks, both arms, run under the current conditions (D234 built-in skill block; full SKILL.md, `llms.txt`, offline guides via the `p5-final` variant).

| Level | App | Tasks |
|---|---|---|
| S | one component (`App.jsx`): a pantry stock list | 35 add, 36 change, 37 remove |
| M | 9 components: a hiring pipeline (Collection of cards, lenses, context, EVENTS → activity log, notes per card) | 38 add, 39 change, 40 remove |
| L | 14 components: a routed expenses SPA (HTTP, `form` + zod, persistence, a timed flash) | 41 add, 42 change, 43 remove |

- **One starter per level and arm**, shared by its three tasks (byte-identical; `SHARED_STARTERS` in `evals/agent-ergonomics/lib/common.mjs`, checked by `verify.mjs`). Each arm's starter is written the way that framework is normally written (Sygnal: canonical forms, `sygnal-check --strict` 0 warnings; React: function components and hooks, plus the libraries the React arm already uses elsewhere — react-router as in 25, react-hook-form + zod as in 30 — only at level L). Both arms have the same product, seed data, visible text and the classes the hidden tests query, the same component names and files, and an equivalent test suite of their own (same test names and cases; Sygnal `renderComponent`, React Testing Library).
- **Prompts** are identical across arms, describe the change in product terms, and say what happens to the project's tests: add — they must still pass; change — update them where the behavior they check changes; remove — remove the feature "completely: its controls, data, logic and tests, leaving no code behind that only served it".
- **Hidden tests** are byte-identical across arms and drive the real app through the DOM. Each suite has:
  - behavior tests for the change, including edge cases where a partial change goes wrong, and regression tests for the neighbouring features;
  - one `project: …` test that runs the trial's own test suite with its own config (`runProjectTests()` in `hidden/_support/project.js`; none failing, and at least `MIN_PASSING_OWN_TESTS` passing, a per-task floor: see "Tests as part of the change"). This is how "existing tests must be updated" is checked, in both arms the same way;
  - remove tasks only: `audit: …` tests that scan `src/` (app and tests, comments stripped) for the removed feature's identifiers, which both starters deliberately share (e.g. `listMode` / `list-tabs`, `activity`, `settings` / `currency` / `localStorage` / `persist`). A leftover state key, action, handler, component or test fails the audit.
- **Scoring**: `pass` needs every hidden test (as in every tier). `score.mjs` also records `groups` (`behavior`, `project`, `audit`: passed/total) and `behaviorPass`, and `analysis/mod.mjs --run <run>` reports pass / behavior / project-suite / audit rates per level × operation × arm, so "did the feature work", "did the agent keep the tests in order" and "did it leave dead code" can be read separately.
- **References and mutants**: every task has a reference solution per arm that passes (`verify.mjs`), including its updated tests; a remove task's reference deletes files through an `.overlay-delete` list. Each task ships at least 2 mutants per arm that must fail: for add, a missed edge case; for change, a half-applied change, "tests not updated" and (36, 39) "deleted failing tests" (both fail only `project:`); for remove, "feature removed but a neighbour broken" and "UI removed but state/handlers left" (fails only `audit:`).

## Level S — pantry (35–37)

Starter (both arms): `src/App.jsx` + `src/App.test.jsx` (+ `main`). A stock list with a per-item minimum (low when quantity < minimum: row class `low`, summary "6 items · 2 low"), +/− buttons (− disabled at 0), Remove with an Undo notice, an add bar (button or Enter; blank ignored; a known name → "Already in the pantry."), All / Low stock tabs and a Name / Quantity sort. Sygnal: one component with `calculated` (`lowCount`, `visible`), 10 actions, rows rendered by a plain helper with `data-id`; React: `useState` × 7, `useMemo`, an `ItemRow` component with callbacks.

| | Sygnal | React |
|---|---|---|
| App code (lines) | 158 | 173 |
| Own tests (lines / tests) | 131 / 11 | 123 / 11 |
| Components | 1 (rows are a plain helper) | 2 (`App`, `ItemRow`) |

- **35 add — search.** A search field over the list (case-insensitive, trimmed), combined with the tabs and the sort; tab buttons count what they would list for the current search ("All (3)", "Low stock (1)"), live through +/−, add and remove; "No items match “xyz”." instead of "Nothing here." while searching; a "Clear search" button only while there is text; the summary still counts the whole pantry. Touches state, two actions, three derived values and three places in the view. Hidden: 8 tests (7 behavior + project; the regression test also covers Undo). Mutants: `case-sensitive`, `counts-ignore-search`, `no-match-message`.
- **36 change — restock rules.** Low becomes "at or below the minimum" everywhere (row, summary, tab), adding a known name adds one to it instead of the message, and the Quantity sort becomes "Most urgent" (quantity − minimum, then name). 7 of the starter's 11 tests assert the old numbers or behaviors, so they must be updated. Hidden: 7 tests (6 + project). Mutants: `row-rule-not-updated` (summary and tab use the new rule, the row class the old one), `duplicate-adds-row`, `urgency-sorts-by-qty`, `tests-not-updated`, `deleted-failing-tests` (the 7 broken starter tests deleted, 4 left; both fail only `project:`).
- **37 remove — the tabs.** Remove the All / Low stock tabs: buttons, `listMode` state, the two actions/handlers, the tab test. The low marks, summary, sort, add, Undo and the "Nothing here." message stay. Hidden: 7 tests (5 behavior + audit + project); audit `/listmode/i, /list-tabs/i, /tab-(all|low)/i, /low stock/i, /SHOW_(ALL|LOW)/`. Mutants: `low-marks-removed`, `empty-message-removed` (neighbours broken), `state-left` (fails only `audit:`).
- Fairness: the whole feature lives in one file in both arms. Sygnal's derived values are `calculated` entries next to the state; React's are inline / `useMemo`. The audit tokens appear in both starters only in the tab code (`listMode`, `tab-all`/`tab-low`, `list-tabs`, "Low stock"; Sygnal's action names `SHOW_ALL`/`SHOW_LOW` and React's `setListMode` are each the arm's own spelling of the same handlers).

## Level M — hiring pipeline (38–40)

Starter (both arms, same files): `App`, `Header`, `StageTabs`, `Toolbar`, `CandidateList`, `CandidateCard`, `CandidateNotes`, `AddCandidateForm`, `ActivityLog`, plus `pipeline.js` (stages, labels, next stage, roles, counts, sorts, seed data; identical in both arms). 8 seeded candidates (tabs "All (8)", "Applied (2)", "Interview (2)", "Offer (2)", "Hired (1)", "Rejected (1)"; summary "6 active · 1 hired"; a role line), Advance / Reject / Remove per card, a toolbar (name search, role filter, Board order / Newest first, Reset view, "N candidates"), notes per candidate (add / delete, "N notes"), an add form ("Enter a name."), and an activity log (newest first, "No activity yet.", Clear). Sygnal: root state + `context` for counts, `<StageTabs state="view">` and `<Toolbar state="view">` lenses, a `<Collection>` with `filter`/`sort` in `CandidateList`, `<AddCandidateForm state="draft">` reporting through `PARENT` / `CHILD.select`, `CandidateNotes` with `isolatedState` for its draft, and `event('ACTIVITY', …)` from cards and the root to `<ActivityLog state="activity">` (`EVENTS.select`). React: state in `App`, handler props, an `addActivity` helper, local state for drafts.

| | Sygnal | React |
|---|---|---|
| App code (lines) | 414 | 389 |
| Own tests (lines / tests) | 309 / 15 (3 files + 2) | 264 / 15 |
| Components | 9 | 9 |

- **38 add — on hold.** Hold / Resume on in-progress cards (`on-hold` class, "On hold" badge, Advance and Reject disabled), an "On hold (N)" tab listing held candidates of any stage, the summary "N active · M hired · K on hold", log entries "X put on hold" / "X resumed", counts live through Remove. The new tab and summary break 2–3 starter tests, and the prompt says to update them. Hidden: 14 tests. Mutants: `held-still-advanceable`, `no-hold-activity`, `held-hidden-from-stage-tab`.
- **39 change — stage flow.** A "Screen" stage between Applied and Interview (Advance path, tab with live count, active, rejectable) and reversible rejection: "Reconsider" returns a candidate to the stage they were rejected from ("X reconsidered (back to Interview)"); seeded rejections were at Applied. Breaks 3 starter tests (advance flow, tab list, log order). Hidden: 13 tests. Mutants: `screen-tab-missing`, `reconsider-to-applied`, `tests-not-updated`, `deleted-failing-tests` (the 3 broken starter tests deleted, 12 left; both fail only `project:`).
- **40 remove — activity log.** The panel, its state, the entries that advancing, rejecting, adding and removing record, Clear, its tests and its file. Hidden: 9 tests incl. 2 audits (`leftovers([/activit/i])` empty, `src/ActivityLog.jsx` gone). Mutants: `advance-broken`, `add-broken` (neighbours broken), `events-left` (fails only `audit:`).
- Fairness: adding Screen is a data change in the shared `pipeline.js` in both arms (tabs, counts and labels follow the stage list), so most of 39's work is Reconsider, which needs the stage a candidate was rejected from in both. In 40, Sygnal drops `EVENTS` sinks in the card and root model entries (next to the STATE reducers they must keep), React drops `addActivity` calls inside handlers (next to the state updates they must keep): the same "remove one effect, keep its neighbour" shape. Sygnal's own tests wait for states (`t.next`), React's assert after `fireEvent`; same cases.

## Level L — expenses (41–43)

Starter (both arms, same markup, text and API): routes `/` dashboard, `/expenses` list (status / category / sort filters, "Showing N expenses", loading and retry), `/expenses/new` (description, amount, category, date; zod schema shared by both arms; messages after leaving a field or on submit, then live; POST; "Saving…"), `/expenses/:id` (Approve / Reject for pending, Delete), `/settings` (currency $ / € / £ and default category, saved in `localStorage`), "Page not found"; a flash message after each action that clears itself after 3 s or on "Dismiss". `schema.js`, `expenses.js`, `money.js` and the test `fixtures.js` are identical in both arms. Sygnal: `makeRouter` + `Switchable instance={route.path}`, page `resources` and reply-action writes (`updates: 'expense'`) through `makeFetchDriver`, `event('FLASH')` to a `FlashMessage` with a `timers` static, the `form` behavior with the zod schema (reset on each visit), `App.persist = persist({ key: 'expenses-settings', pick: ['settings'], format: 'plain' })` with the currency in `App.context`; `main.js` wires `ROUTER`, `HTTP`, `TIMER`. React: react-router 7 (`createBrowserRouter` inside `App.jsx`), `api.js` fetch helpers and `useResource` hooks, `flash.jsx` and `settings.jsx` contexts (the same `{ settings }` format in `localStorage`), react-hook-form + zodResolver.

| | Sygnal | React |
|---|---|---|
| App code (lines) | 633 | 732 |
| Own tests incl. fixtures / test utils (lines / tests) | 266 / 16 (6 files) | 321 / 16 (6 files) |
| Components | 14 | 14 + `Layout`, `FlashProvider`, `SettingsProvider` |

- **41 add — budgets.** Four budget fields in Settings (saved and restored with the other settings), a "Budget" column on the dashboard ("$730.50 of $500.00" / "No budget", `over-budget` rows), an over-budget summary line, and a live, non-blocking `p.budget-warning` in the new-expense form; budgets follow the currency. The starter's settings test checks the exact stored object, so it needs updating in both arms. Hidden: 6 files (dashboard, summary, warning, persistence across a reload, regressions, project). Mutants: `rejected-counted`, `warning-not-live`, `budgets-not-saved`, `no-within-summary`.
- **42 change — drafts.** "Save draft" POSTs `status: 'draft'` and opens the new expense's page ("Draft saved"); a "Draft" badge and filter option; "Submit for approval" (PUT `{ status: 'pending' }`); Delete only on drafts and rejected expenses; "Drafts: N" on the dashboard, drafts excluded from pending and the category totals. Breaks 4 starter tests (submit, detail buttons, deleting a pending expense). Hidden: 5 files (draft flow, delete rules, dashboard, regressions, project). Mutants: `pending-deletable`, `drafts-counted`, `posts-pending`, `tests-not-updated` (fails only `project:`).
- **43 remove — settings.** The nav link, the page (`/settings` → "Page not found"), the currency choice (always `$`), the default category (the form starts at "Choose…"), all `localStorage` use (a stale entry is ignored; spies on `Storage.prototype` filtered to `localStorage`, since React's router uses `sessionStorage`), and its tests. Hidden: 6 files incl. the audit (`leftovers([/settings/i, /currency/i, /localStorage/i, /\bpersist\b/])` empty, `src/SettingsPage.jsx` gone). Mutants: `dollar-sign-lost` (neighbour broken), `nav-link-left`, `persistence-left`, `currency-code-left` (fails only `audit:`), `deleted-failing-tests` (`App.test.jsx`, whose nav assertion breaks, deleted instead of updated: 13 left; fails only `project:`).
- Fairness: in 43, React has more edit sites (five components call `useSettings()` for the currency, ~3 lines each, against one `context.currency` read per component in Sygnal), but keeps most of the feature in one deletable `settings.jsx`; Sygnal's persistence is one `persist` static. Sygnal pages share root state and reset transient flags in the root `ROUTE` reducer; React keeps them in page state (re-clicking "Expenses" on `/expenses` resets the filters in Sygnal only; no hidden test depends on it). The 41 reload test opens each "reloaded" page by its URL, because a re-mount leaves the first Sygnal app's router listening in the same jsdom.

## Fairness notes (all levels)

- **Same product, same contract.** Seed data, visible text, the classes and names the hidden tests query, the component names and files, and the cases of the project's own tests are the same in both arms; shared logic modules (`pipeline.js`; `schema.js`, `expenses.js`, `money.js`) are byte-identical, so neither arm gets a head start from where the domain rules live. The hidden suites are byte-identical and framework-neutral (`verify.mjs` checks).
- **Idiomatic, not mirrored.** Each starter is what that framework's own docs would have you write: Sygnal with canonical forms only (`sygnal-check --strict` 0 warnings on every starter and reference), React with hooks, props/callbacks and contexts, and at level L the libraries the React arm already uses elsewhere (react-router, react-hook-form, zod). So a modification exercises each framework's own structure: in Sygnal an intent action + model entry (+ sinks) + view, in React a state hook + handler + JSX.
- **Size.** Sygnal is a little terser for the same behaviour at M (414 vs 389 lines is close) but not at L (633 vs 732), where React carries providers and fetch hooks. All three levels are below the sizes first planned (M ~500–700, L ~1,100–1,600 app lines); counting the project's own tests, M is ~650–720 and L ~900–1,050 lines per arm. The relative step S → M → L (about 1 : 2.5 : 4) is what the tier measures.
- **Tests as part of the change.** The `project:` test makes "keep the existing suite green" a requirement in both arms; the change tasks (36, 39, 42) and 38 and 41 break specific starter tests by design, and a mutant that leaves them un-updated fails only that test. Deleting failing tests instead of updating them is caught: each task's `project:` test requires at least `MIN_PASSING_OWN_TESTS` passing own tests (a per-task constant in the hidden suite, with a comment giving its reason; the starters' suites have the same counts in both arms, so one constant serves both and the hidden files stay byte-identical). add and change tasks: the starter's count (an agent that updates tests keeps it; the references keep it and may add tests): 35 and 36: 11; 38 and 39: 15; 41 and 42: 16. remove tasks: the starter's count minus the tests that only cover the removed feature: 37: 10 (11 − the Low stock tab test; the reference replaces it with an empty-pantry test, 11); 40: 13 (15 − `ActivityLog.test.jsx`'s 2, as the reference); 43: 14 (16 − `SettingsPage.test.jsx`'s 2, as the reference; `App.test.jsx`'s nav assertion must be updated). The `deleted-failing-tests` mutants (36, 39, 43, both arms) fail only `project:`; before this floor (≥ 3 tests) they passed. Limits: an agent can still delete a broken test and write a new one, or weaken an assertion, and pass; the count only stops plain deletion.
- **Audits are symmetric.** Each removed feature uses the same distinctive identifiers in both starters, and the regexes never match unrelated code (each reference passes its audit; each starter fails it). Where an arm's own spelling differs (Sygnal `SHOW_ALL`, React `setListMode`), both are covered.
- **Known asymmetries**: Sygnal agents get `sygnal-check` and AGENTS.md (starter 2, as in every variant run) and the skill; React agents get neither, as in every tier. Sygnal's runtime diagnostics run in its own tests (`strict: true`).
- **Scoring.** `pass` needs every hidden test (behaviour, `project:` and `audit:`); `behaviorPass` and the per-group counts are recorded separately and reported by `analysis/mod.mjs`.

## Running it

```bash
node evals/agent-ergonomics/verify.mjs --arm both --task 35-43            # references pass, starters and mutants fail
node evals/agent-ergonomics/orchestrate.mjs --run p5-mod-sonnet --variant p5-final --arms sygnal,react \
  --tasks mod --trials 5 --concurrency 4 --model claude-sonnet-5-5 --dry-run
node evals/agent-ergonomics/analysis/mod.mjs --run p5-mod-sonnet            # after the run
```

**Verify** (2026-10-06, packed `p5-mod` build): `verify.mjs --arm both --task 35-43 --reruns 2` → `ALL OK: 18 task(s), 196/196 checks as expected` (98 variants × 2: every starter fails, every reference passes, all 44 mutants fail). Hidden tests per task: 35: 8, 36: 7, 37: 7, 38: 14, 39: 13, 40: 9, 41: 6, 42: 5, 43: 6 (level L has one router app per file, so its tests are few and broad: partial credit there is coarse). `sygnal-check --strict`: 0 warnings on all three Sygnal starters and all nine references.

**Estimate** for `p5-mod-sonnet` (90 trials). The dry-run estimator says ≈ $10.35 and ≈ 39 min at concurrency 4, but it has no history for 35–43 and falls back to each arm's mean over all Sonnet records, which are mostly small tasks. From `p5-final-sonnet` (30–34: Sygnal ≈ $0.22 and React ≈ $0.09 per trial, 0.3–1 min) scaled by how much code the agent must read and change (S ≈ 1.2×, M ≈ 2×, L ≈ 3.5×): Sygnal ≈ 15 × ($0.26 + $0.45 + $0.80) ≈ $23, React ≈ 15 × ($0.11 + $0.18 + $0.32) ≈ $9, so **≈ $32 (range $20–50)** and about 1–1.5 h of wall time at concurrency 4.
