Sygnal 6.0 Gap Study

This report compares Sygnal with React 19.3, Vue 3.5/3.6, Svelte 5, Solid 2, Angular 22, Qwik, Lit, Elm, Preact and htmx 4. It covers only capabilities that the PLAN-3 network work and the PLAN-4 ecosystem work don't already include. Each candidate gets a fit and importance score, a sketch of how it would read in Sygnal, its cost against the 6.0 budgets, and a recommendation.

Scoring lens: easy for agents to write, easy for humans to read, MVI kept intact (models describe effects, drivers perform them, every state change is an action, views have no event binding). Fit and importance are scored 1–5.

1 bug to fix firstControlled inputs lose keystrokes typed less than about 5 ms apart (found in an experiment).
11 to implementMostly 0 B core: helpers, drivers, checker rules and statics on the PLAN-3 declaration mechanism.
5 to prototypeGate these on an eval or a measurement before committing.
4 docs or later, 5 noSignals, compilers and server components don't fit MVI.

Summary

Ordered by recommended priority. Agent-doc cost is the number of llms.txt lines the feature needs. PLAN-4 currently has at least 15 lines left (D76), so the "implement" set needs about 9 more lines, or some trimming elsewhere.

B-0

Controlled inputs lose fast keystrokes

Fix before 6.0 · P0

This came up while testing Testing Library compatibility (G-14). It is a correctness problem, not a missing feature, so it comes first.

What happened

A plain controlled input (value={state.draft} plus DOM.input('.draft').value(), the canonical form) was typed into with @testing-library/user-event under renderComponent(F, {dom: 'real'}):

  • delay: 0 and delay: 1 ms: typing Hello world leaves Hlowrd in both the field and the state.
  • delay: 5 and 20 ms: correct.
Likely cause

Renders are debounced by 1 ms (component.ts .compose(debounce(1))). controlledInputModule then writes the value from that render's older state back over the newer text in the DOM. React avoids this by re-rendering controlled inputs synchronously.

Where it matters

Barcode scanners (keyboard wedges type 1–5 ms apart), Playwright pressSequentially, text-expander tools, and any slow device where a render takes longer than the gap between keystrokes.

Recommendation: fix in 6.0. Skip the rewrite when the element has had a newer input event than the state being rendered, for example with a per-element input sequence number. Confirm in browser-tests with real keystrokes first, since this was seen in jsdom. Add a regression test that types with user-event at delay: 0.

Candidates in detail

G-1

Reusable behaviors

Implement · P1
Fit●●●●●Importance●●●●●EffortM (most of it in sygnal-check)Core0 B
Elsewhere

Every other framework has a unit of reusable stateful logic: React custom hooks, Vue composables, Svelte runes in .svelte.js, Lit reactive controllers, Angular inject() functions. Agents reach for it by reflex ("extract a usePagination").

Sygnal today

Logic that has its own markup becomes a child component. Logic that spans the host's own markup (pagination over the host's list, selection, keyboard shortcuts, undo) has no documented form. Agents copy intent and model entries between components.

How it could look
// behaviors/pager.js
import { defineBehavior, ABORT } from 'sygnal'
export const pager = defineBehavior({
  initialState: { page: 0, pageSize: 20 },        // lives at state[key]
  intent: ({ DOM }, sel = { next: '.next', prev: '.prev' }) => ({
    NEXT: DOM.click(sel.next), PREV: DOM.click(sel.prev),
  }),
  model: {                                        // reducers see only the slice
    NEXT: (p) => ({ ...p, page: p.page + 1 }),
    PREV: (p) => (p.page === 0 ? ABORT : { ...p, page: p.page - 1 }),
  },
  calculated: { offset: (p) => p.page * p.pageSize },
})

// TaskList.jsx
TaskList.uses = { pager: pager({ pageSize: 10 }) }   // state.pager, actions 'pager.NEXT' / 'pager.PREV'
TaskList.intent = ({ DOM }) => ({ ADD: DOM.click('.add') })
  • Experiment X3: a 12-line use() helper that merges initialState, intent and model at definition time works today, with no diagnostics. The runtime part is easy.
  • The hard part is static: sygnal-check must resolve uses to the behavior module so SYG101/102/110 still see the merged actions and selectors. Without that, behaviors become a blind spot for the checker.
  • Namespacing: prefixing actions with the key (pager.NEXT) avoids collisions and reads well in the DevTools and in t.actions (G-10).
Recommendation: implement. This is the largest idiomatic gap against every other framework, and it keeps MVI, since a behavior is just intent, model and state fragments. Build it as a definition-time helper (0 B core), with full checker support as the acceptance bar. The docs should give one rule for choosing: "has markup → child component; spans the host's markup → behavior". Ship 2–3 first-party behaviors (pager, selection, undo from G-8) to prove the shape.
G-2

Element commands: focus, scroll, dialog, popover

Implement · P1
Fit●●●●●Importance●●●●●EffortS–MCore≈ 0 B (driver; uses the PLAN-3 sender tag)
Elsewhere

Elm models this exactly: Browser.Dom.focus is a command the update function returns. React, Vue and Svelte use refs plus effects, and React 19.3 adds focus() on Fragment refs. Native <dialog> and the Popover API are Baseline, but a modal dialog needs showModal(), which is an imperative call.

Sygnal today

autoFocus/autoSelect work only when an element is first inserted. "Focus the first invalid field after submit", "scroll the new row into view" and "open this native dialog" need createRef plus an EFFECT, which is the least canonical path in the docs.

How it could look
Signup.model = {
  SUBMIT: {
    STATE:   (s) => ({ ...s, errors: validate(s) }),
    ELEMENT: (s) => (validate(s).email ? { focus: '.email' } : ABORT),   // selector scoped to this component
  },
  ADDED:      { ELEMENT: (s, row) => ({ scrollIntoView: `.row[data-id="${row.id}"]`, block: 'nearest' }) },
  OPEN_HELP:  { ELEMENT: { showModal: 'dialog.help' } },
  CLOSE_HELP: { ELEMENT: { close: 'dialog.help' } },
}
Signup.intent = ({ DOM }) => ({ CLOSE_HELP: DOM.close('dialog.help') })   // the native 'close' event

// tests: t.commands('ELEMENT') → [{ focus: '.email' }]; with dom: 'real', document.activeElement moves
  • Commands: focus, blur, select, scrollIntoView, showModal, show, close, showPopover, hidePopover. Commands run after the next patch, so they reach elements that the same action renders.
  • A selector is resolved inside the sending component's DOM scope. That is the same isolation rule as intent selectors, so the existing SYG110 check also covers commands.
  • It gives PLAN-4 a lighter path to modals: a native <dialog> plus this driver instead of an 18.5 KB Zag dialog, which keeps U-1 for the widgets that are hard to build.
Recommendation: implement. It is the purest MVI answer: the model describes the effect, and a driver performs it. Decide at the start whether it is built in (like DOM and EVENTS) or registered; a built-in avoids SYG609 confusion and should cost only a few hundred bytes. Measure that against the D77 reserve.
G-3

Accessibility checks in sygnal-check

Implement · P1
Fit●●●●●Importance●●●●●EffortMCore0 B
Elsewhere

Svelte prints a11y warnings at compile time, and eslint-plugin-jsx-a11y is near-universal in React projects. Angular 22 ships Angular Aria. Agents produce inaccessible markup unless something checks it.

Sygnal today, plus a Sygnal-specific risk

There are no a11y checks. Intent selects by class, so agents attach DOM.click('.card') to a <div>, which keyboard users can't trigger. Only Sygnal's checker can see both halves: it already maps intent selectors to view elements (SYG110).

How it could look
[Sygnal SYG701] a11y: DOM.click('.card') listens on a <div> with no role or tabIndex,
  so keyboard users can't trigger OPEN. Render <button className="card">, or add
  role="button" tabIndex={0} and also handle DOM.keydown('.card').  https://sygnal.js.org/reference/errors#syg701
[Sygnal SYG702] a11y: <input className="email"> has no label (no <label>, aria-label or aria-labelledby).
[Sygnal SYG703] a11y: <img> without alt.   SYG704: <a> without href used as a button.
Recommendation: implement as a new 7xx "a11y" lane (unused today). Use warn severity, on by default in the Vite plugin, and an error in --strict. Start with the cross-intent rule (SYG701), which no other tool can do, plus 5–6 high-precision markup rules. Pair it with G-9 (uid) so a label rule has a clean fix. Keep every example and template a11y-clean as a gate.
G-4

Returning the same object means "no change"

Implement · P1 (breaking: strict rule retired)
Fit●●●●●Importance●●●●●EffortSCore≈ 10 B
Elsewhere

Redux Toolkit made "mutate a draft" the default reducer style. Zustand has an Immer middleware, Solid has produce/createProjection, and Svelte and Vue mutate reactive state directly. Nested spreads are the most verbose and error-prone part of reducers, for agents and humans alike.

Sygnal today (experiment X1)

Immer's curried produce((draft, data) => …) already fits the (state, data) reducer signature. It worked for root reducers, Collection item writes and calculated fields. One gap: a no-op produce returns the same object, which Sygnal treats as a new state. That emits an extra state and render, and strict mode flags it as "use ABORT".

How it could look
import { produce } from 'immer'
Board.model = {
  MOVE: produce((draft, { id, to }) => {
    const card = draft.cards.find((c) => c.id === id)
    if (card.lane === to) return            // same object back = no change (like ABORT)
    card.lane = to
  }),
}
Recommendation: implement the core rule (a STATE reducer returning the identical object is treated as ABORT) and retire the strict "return state" rule. This removes a canonical-form rule from llms.txt instead of adding one. Document Immer as a recipe and don't bundle it (it is about 5 KB). Keep ABORT canonical in plain reducers, and keep the runtime check that flags in-place mutation without produce.
G-5

State persistence

Implement · P1
Fit●●●●●Importance●●●●●EffortS–MCore0 B (static read by a tree-shaken module)
Elsewhere

zustand persist, pinia-plugin-persistedstate, Solid makePersisted and svelte-persisted-store are among the most-installed state add-ons. "Make it survive a reload" is a common follow-up in agent tasks.

Sygnal today

Only HMR keeps state (__SYGNAL_HMR_PERSISTED_STATE). PLAN-4's B-3 adds a storage source, which is a stream, not persistence. A single state tree is the ideal shape for this, which makes the gap more noticeable.

How it could look
TodoApp.initialState = { todos: [], filter: 'all', draft: '' }
TodoApp.persist = {
  key: 'todo-app', pick: ['todos', 'filter'],   // never persist drafts or loading flags
  version: 2, migrate: (old, from) => (from === 1 ? { ...old, filter: 'all' } : old),
  storage: 'local',                              // 'session' | a { get, set } adapter (IndexedDB, cookies)
}
// tests: renderComponent(TodoApp, { storage: { 'todo-app': {...} } }); t.storage('todo-app')
  • The restore merges into initialState before INITIALIZE, so the restore is still an action. Writes are debounced and skipped during SSR.
  • The checker verifies that pick names fields of initialState. A runtime diagnostic covers a schema change without a version bump (a stored key that is no longer in the state).
Recommendation: implement as a root-only static backed by a tree-shaken module. The static reads better than a run() option, and the checker can see it. It is one llms.txt line.
G-6

Reactions to state changes

Implement · P2
Fit●●●●●Importance●●●●●EffortSCore≈ 60 B
Elsewhere

Vue watch, Svelte $effect, Solid and Angular effect, and React useEffect deps all cover "when X changes, do Y": autosave, sync to the URL, analytics.

Sygnal today

It is possible, but awkward: STATE.stream.map(s => s.doc).compose(dropRepeats()).drop(1) in intent. In practice agents put the side effect in every reducer that touches the field, which is the bug-prone version.

Editor.intent = ({ STATE }) => ({
  AUTOSAVE: STATE.watch((s) => s.doc).compose(debounce(1000)),   // changes only; structural compare; no initial value
})
Editor.model = {
  AUTOSAVE: { HTTP: (s, doc) => ({ url: '/api/doc', method: 'PUT', json: doc, ok: 'SAVED', latest: true }) },
}
Recommendation: implement as an enriched stream on the STATE source, so "when" stays in intent. The canonical form replaces the hand-rolled chain, and SYG102 counts it as a trigger. Add a strict-mode hint that flags the same sink duplicated across many reducers for one field.
G-7

Timers and animation frames as declarations

Implement · P2
Fit●●●●●Importance●●●●●EffortS (on __sygnalStatic)Core0 B
Elsewhere

Elm subscriptions are the direct precedent (Time.every, onAnimationFrame), followed by VueUse useIntervalFn and the React useInterval folklore. Stopwatches, countdowns, clocks and games are standard agent tasks.

Sygnal today

xs.periodic can't depend on state without flatten gymnastics, and next('TICK', null, 1000) chains drift and leak after unmount. PLAN-3 left every(ms) out "unless it comes for free". With __sygnalStatic landed, it nearly is.

Stopwatch.timers = (state) => ({
  tick:  state.running && { every: 100, action: 'TICK' },     // falsy = stopped; diffed like connections
  frame: state.animating && { frame: 'FRAME' },               // requestAnimationFrame; data = timestamp
})
Stopwatch.model = { TICK: (s) => ({ ...s, elapsed: s.elapsed + 100 }) }
// tests: vi.useFakeTimers(); await vi.advanceTimersByTimeAsync(300) → 3 TICKs
Recommendation: implement, or fold it into PLAN-4 B-3 if that pack ends up with the same declaration shape. The name should match whatever B-3 settles on.
G-8

Undo / redo helper

Implement · P2
Fit●●●●●Importance●●●●●EffortSCore0 B

The state guide says undo is "trivial" with a state tree, but nothing ships, so every app rebuilds it. redux-undo, zundo and Pinia history plugins exist for the same reason. Experiment X4: a 25-line undoable() model wrapper with past/future snapshots passed, including ABORT on an empty history.

import { undoable } from 'sygnal'
Editor.model = undoable({ ADD_SHAPE: …, MOVE: … }, { key: 'doc', limit: 100, track: ['ADD_SHAPE', 'MOVE'] })
// adds UNDO and REDO entries; state.history = { past, future }; calculated canUndo / canRedo
Editor.intent = ({ DOM }) => ({ UNDO: DOM.click('.undo'), REDO: DOM.click('.redo') })
Recommendation: implement as a reducer helper next to set/toggle. Once G-1 lands, also ship it as a behavior. Guide page only; no llms.txt line.
G-9

Stable per-instance ids

Implement · P2
Fit●●●●●Importance●●●●●EffortSCore≈ 40 B

React useId, Vue 3.5 useId and Svelte $props.id() all exist for the same reason: for/aria-describedby need ids that are unique per instance (every Collection item) and identical between SSR and hydration. Today agents hand-roll 'email-' + state.id.

function Field({ state, uid, label }) {
  return (
    <div>
      <label for={uid('input')}>{label}</label>
      <input id={uid('input')} className="value" aria-describedby={uid('error')} value={state.value} />
      <p id={uid('error')}>{state.error}</p>
    </div>
  )
}
Recommendation: implement. Derive ids from the component's position in the tree (SSR-safe), and reserve uid in the props list (SYG106). It gives the a11y rules (G-3) and forms (F-1) a canonical fix.
G-10

Action log in tests; export a session as a test

Implement · P2
Fit●●●●●Importance●●●●●EffortS (log) · M (export)Core0 B
Elsewhere

The Elm debugger imports and exports action histories. Redux DevTools offers replay and a test generator, and NgRx, Pinia and Zustand reuse that protocol.

Why it matters for Sygnal

Named actions are Sygnal's strongest debugging asset. Yet tests expose only t.states, and the DevTools time-travel through state but don't show "which action did this". Debug time grew from 1.6 s to 2.9 s per trial in REPORT-v2, and in 22 of 24 failing Haiku trials the agent's own tests passed.

t.actions   // [{ type: 'SEARCH', data: 'du', component: 'Search#2', sinks: ['STATE', 'HTTP'], ms: 312 }, …]
t.explain((s) => s.status === 'error')   // the action that first produced a matching state, and its reducer
// DevTools: "Copy as test" → renderComponent + simulateAction sequence + final-state assertion
Recommendation: implement t.actions (one llms.txt fact). Add the DevTools export, and optionally a dev-only Redux DevTools bridge (about 40 lines), as P3.
G-11

App-level error reporting hook

Implement · P2
Fit●●●●●Importance●●●●●EffortSCore≈ 30 B

Sygnal has per-component onError boundaries and dev-time onDiagnostic, but I found no documented production hook for sending caught errors (view, reducer, EFFECT and driver failures) to Sentry and similar services. Vue (app.config.errorHandler), Angular (ErrorHandler) and React (root onCaughtError/onUncaughtError) all have one.

run(App, drivers, {
  onError: (error, { componentName, action, phase }) =>   // phase: 'view' | 'reducer' | 'effect' | 'driver'
    Sentry.captureException(error, { tags: { componentName, action, phase } }),
})
Recommendation: implement. It is small, works in production and is easy to explain. It runs after the component boundary decides on a fallback, so it is reporting only.
G-12

View Transitions

Prototype
Fit●●●●●Importance●●●●●EffortMCore≈ 120 B

Same-document View Transitions are in every engine (Firefox 144, October 2025). React 19.3 stabilised <ViewTransition> in September 2026, and Astro, SvelteKit and Angular's router use them. One opt-in could cover route changes, list reorders and shared-element moves, which overlaps with PLAN-4's A-1 FLIP work.

Board.viewTransitions = ['MOVE', 'SORT']   // renders caused by these actions run inside document.startViewTransition
function Card({ state }) { return <div className="card" style={{ viewTransitionName: `card-${state.id}` }}>…</div> }
// router: makeRouterDriver({ routes, viewTransitions: true })
Recommendation: prototype before A-1. If View Transitions cover Collection moves well enough, A-1's FLIP can shrink to a fallback. Respect prefers-reduced-motion by default. The router option is the cheap first step.
G-13

Publish Sygnal components as custom elements

Prototype
Fit●●●●●Importance●●●●●EffortMCore0 B (sygnal/element entry)

PLAN-4 W-3 makes web components easy to consume. The other direction (Vue defineCustomElement, Svelte customElement, Angular Elements, solid-element) is how a framework gets into existing apps, CMSs and micro-frontends without a rewrite. That makes it an adoption channel.

import { defineElement } from 'sygnal/element'
defineElement('task-board', TaskBoard, {
  props: ['tasks', 'readonly'],                 // properties/attributes → state
  events: { PARENT: 'task-picked' },            // PARENT output → CustomEvent('task-picked', { detail })
  shadow: false,

// <task-board readonly></task-board>  el.tasks = […]  el.addEventListener('task-picked', (e) => e.detail)
Recommendation: prototype after W-1/W-3, since it shares their event conventions. Ship it if the prototype stays under about 60 lines and works with HMR.
G-14

Testing Library queries on renderComponent

Docs + eval
Fit●●●●●Importance●●●●●EffortSCore0 B

Testing Library has adapters for React, Vue, Svelte, Angular, Preact and Solid, and agents write getByRole and userEvent by habit. Experiment X2: within(t.container) plus user-event already works under dom: 'real', apart from B-0. Role-based queries also push markup toward accessibility, which supports G-3.

t = renderComponent(AddTask, { dom: 'real' })
await t.user.type(t.screen.getByRole('textbox', { name: 'Task' }), 'Milk')   // optional peer dependency
await t.user.click(t.screen.getByRole('button', { name: 'Add task' }))
await t.next((s) => s.items.length === 1)
Recommendation: document the pattern now, after the B-0 fix. Add t.screen/t.user getters only if an eval A/B shows less test-authoring time; that phase is currently +1.8 s against React.
G-15

Live dev-server context for agents

Eval-gated · P3
Fit●●●●●Importance●●●●●EffortMCore0 B (Vite plugin)

Next.js's devtools MCP reads live errors and logs from the running dev server. Svelte and Angular ship official MCP servers and agent skills. Sygnal already has the parts: the sygnal-check MCP server, getDevTools().inspect() in the browser, and runtime diagnostics. What is missing is a channel from the running app to a terminal agent, such as /__sygnal/inspect on the Vite server serving the live graph, recent actions (G-10) and diagnostics.

Recommendation: hold. PLAN-2's E8 found MCP in agent docs didn't pay off, and agents in the evals work through tests, not browsers. Revisit only with an eval task that needs a running app.
G-16

Performance baseline

Measure first
Importance●●●●●EffortS–MCore0 B

The other frameworks compete hard on rendering cost: React Compiler 1.0, Vue Vapor (3.6 RC), Solid's and Svelte's no-VDOM output, Elm Html.Lazy. Sygnal has no published numbers, and every component re-runs its view when its state stream emits. I have no evidence of a problem, and no evidence against one.

Recommendation: add a keyed and a non-keyed js-framework-benchmark implementation, plus a "1,000-row Collection, edit one row" benchmark in browser-tests, before 6.0 ships. Decide on memoization (an Elm-style lazy view or slice-equality skipping) only from those numbers.
G-17

Deferred loading triggers

After B-3

Angular's @defer (on viewport | idle | interaction), Vue 3.5 hydration strategies and Astro's client:visible load code when it is needed. Sygnal has lazy() with Suspense but no triggers. Possible shape: lazy(() => import('./Chart'), { when: 'visible' }). Recommendation: build it on PLAN-4 B-3's intersection/idle sources once they exist. Astro users already have client:visible.

G-18

Scoped styles

Docs only

Vue, Svelte and Angular scope styles per component, and CSS @scope became Baseline in December 2025. In Sygnal, class names are both style hooks and intent selectors, so compiler-hashed classes would complicate intent. Recommendation: a guide page showing CSS Modules (className={css.card} in the view and DOM.click('.' + css.card) in intent) and plain @scope (.task-list) to (.task-item). No API.

G-19

Storybook / component workbench

Later

Storybook 10 supports nine frameworks, Sygnal not among them. It matters to teams more than to agents. Recommendation: a recipe using Storybook's HTML/web-components renderer, with stories that mount through run() (or through G-13's elements). A first-party renderer only on user demand.

G-20

Declared props contracts

Later

Vue defineProps (types, defaults, validators), Angular input.required() and Lit properties let tools check call sites. Sygnal props are destructured, so sygnal-check can't flag a missing required prop in JS projects. TypeScript users already get it through Component<…, Props>, and no eval failure traced to props. Recommendation: defer. If added later, use Rating.props = { name: 'string', value: { type: 'number', default: 0 } } or a Standard Schema, so it doubles as defaults for the reducer's props argument.

N-1…5

Not recommended

Don't
  • N-1 Fine-grained signals as the state model (Angular, Vue, Svelte, Solid, Preact, Qwik; TC39 Signals is still Stage 1). They would replace the single state tree and actions, which are the source of Sygnal's testability, time travel and agent-readable wiring. If G-16 shows a need, optimise rendering under the existing model instead.
  • N-2 A compiler or Vapor-style output. It costs a lot, it adds a build step that every agent path must understand, and React Compiler shows the realistic win is memoization. Revisit after G-16.
  • N-3 Server components, resumability (Qwik) and streaming SSR in-house. Vike and Astro integrations already cover SSR and islands, and PLAN-3 covers server functions. Building this in would be a different framework.
  • N-4 Two-way binding sugar (v-model, bind:value, defineModel). Binding in the view breaks "views have no event binding". The real need (less boilerplate per field) belongs in PLAN-4 F-1's forms API.
  • N-5 An optimistic-update primitive (useOptimistic, createOptimistic). In MVI it is already natural: a STATE update plus an HTTP request with error: 'ROLLBACK'. PLAN-3's recipe is enough.

Budget and sequencing notes

  • Agent docs: the "implement" set needs about 9 llms.txt lines. That is G-1 (4), G-2 (2), G-3, G-5, G-6 and G-10 (1 each), less 1 from G-4. PLAN-4 has at least 15 lines and also needs about 13 for F-1 and W-1. Either raise the 300-line cap slightly or move the G-6/G-10 facts into the skill. Run PLAN-3's learn-time check on these too.
  • Core bytes: G-4, G-6, G-9, G-11 and G-12 together are about 260 B. Everything else is 0 B core. G-2 is the only one that might want to be built in; measure it against the D77 reserve.
  • Order: B-0 can start any time. G-4 and G-11 are small and independent. G-2, G-5 and G-7 depend on PLAN-3's sender tag and __sygnalStatic. G-1 should land before the first-party behaviors (G-8). G-3 and G-9 go together. G-12 goes before PLAN-4 A-1.
  • Breaking changes this major can absorb: G-4 (a same-reference return no longer emits; the strict rule is retired), the new reserved prop uid (G-9), and the new reserved statics uses, persist, timers and viewTransitions.

Method and experiments

Inputs: llms.txt on plan3-integration, PLAN-3 and PLAN-4, REPORT-v2 (agent eval findings), and the 6.0 source tree. A web survey checked framework releases up to 2 October 2026. Experiments ran on a throwaway Vitest + jsdom project against a fresh build of main (6b7144e); they are saved in dev-plans/research/gap-study-experiments/.

  • X1 Immer reducers: passed for root reducers, Collection item writes and calculated fields. A no-op produce emitted 1 extra state (basis for G-4).
  • X2 Testing Library + user-event under dom: 'real': queries work, and typing exposed B-0.
  • X2b keystroke timing: Hello world became Hlowrd at 0–1 ms between keys, and was correct at 5 and 20 ms.
  • X3 behavior composition: a 12-line definition-time merge helper passed with no diagnostics (basis for G-1).
  • X4 undoable() model wrapper: undo and redo passed with no diagnostics (basis for G-8).
