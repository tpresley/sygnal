## 2. The layout decision

**The constraint** (plugins reference, Path rules): every component path must resolve inside the plugin root; `..` fails validation, and "a symlink that leads outside the plugin" is rejected, "other than links between plugins within one marketplace". So `editors/claude-code/.claude-plugin/plugin.json` can't say `"skills": "../../skills/sygnal-dev"`.

**Options considered:**

| Option | Verdict |
|---|---|
| Plugin root = repository root (`.claude-plugin/plugin.json` at the root, the default `skills/` scan finds `skills/sygnal-dev`) | **Rejected.** An install copies the plugin directory into the cache: the whole repository (≈ 4,000 tracked files, ≈ 54 MB). The root has `package.json` + `package-lock.json`, which triggers Claude Code's automatic dependency install in the cache. `validate` also warns about the root `CLAUDE.md`. Contradicts PLAN-7's `editors/claude-code/` |
| Marketplace entry with `source: "./"` and `skills: ["./skills/sygnal-dev"]` | Same copy-the-repository problem |
| `git-subdir` source for `editors/claude-code` | Fetches only that subdirectory, so the skill outside it is missing |
| Generated copy of the skill in the plugin + drift test | Works everywhere, but a second 42 KB copy next to a file that already has sync tests and doc tests; only worth it if the link fails |
| **Symlink in the plugin** | **Chosen.** The "Share files within a marketplace with symlinks" rule: when Claude Code copies a marketplace plugin into its cache, a symlink to "elsewhere within the same marketplace" is dereferenced (its target's content is copied in its place). The marketplace root is the repository root, so `skills/sygnal-dev` qualifies |

**Verified, without any model call:**
1. **Git-hosted marketplace install.** `/plugin marketplace add file://…` is refused ("Invalid marketplace source format"), and a dumb-HTTP clone fails (Claude Code clones shallow). So the branch was served over **smart HTTP** from a bare clone (`git http-backend` behind a 30-line Node server on 127.0.0.1), the same clone path as GitHub. In an isolated `CLAUDE_CONFIG_DIR` (the user's settings untouched):
   - `claude plugin marketplace add http://127.0.0.1:8766/mkt.git` → "Successfully added marketplace: sygnal";
   - `claude plugin install sygnal@sygnal` → installed at `cache/sygnal/sygnal/0.1.0/` (version from `plugin.json`, `gitCommitSha` recorded);
   - `cache/…/0.1.0/skills/sygnal-dev` is a **real directory**, byte-identical to `skills/sygnal-dev` (`diff -r`: identical); only the plugin folder was copied (`.claude-plugin/`, `scripts/`, `skills/`);
   - `claude plugin details sygnal@sygnal`: Skills (1) `sygnal-dev`, LSP servers (1) `sygnal`, always-on cost ≈ 123 tokens, on-invoke ≈ 10.5k.
2. **Local-directory marketplace** (`claude plugin marketplace add <checkout>`; plugins load in place): installed, `details` lists the skill and the server.
3. **`--plugin-dir`**: `validate` says a session follows the link. The `init` event of a real session would confirm it; that is part of run 1 (not run, §5).

**The caveat: Windows.** Git for Windows checks symlinks out as small text files unless `core.symlinks` is on (Developer Mode or the installer option). Claude Code clones the marketplace with the user's git, so on a default Windows setup the plugin installs **without the skill** (the language server still works). The README says so and points at the manual copy. If users report it, switch to the generated copy: a `scripts/sync-plugin-skill.mjs` that copies `skills/sygnal-dev` into the plugin, and a root test that fails when the two differ.

**Version and content.** `version` is pinned (`0.1.0`), so an installed copy changes only when the string changes. The skill comes through the link, so **a change to `skills/sygnal-dev` reaches plugin users only with a plugin version bump**, and two users who installed on different days can both have "0.1.0" with different skill text. Release steps (§7) bump the plugin version whenever the skill or the plugin changes.

## 3. When the project has no capable sygnal-check

**What Claude Code 2.1.287 does with a server that can't start** (read from the bundle: the per-server lifecycle with `restartOnCrash`, `maxRestarts`, `startupTimeout`):
- The server is started by the Edit/Write tool's `changeFile` without awaiting it. A process that exits before answering `initialize` sets the server state to `error`, counts a crash, and logs `Failed to start LSP server 'sygnal': …` at error level in the **debug log**. The tool result is unaffected; the model sees nothing.
- The next edit of a mapped file tries to start it again, until the crash count passes `maxRestarts` (default 3). Then it logs `LSP server 'sygnal' exceeded max crash recovery attempts (3)` once and stops trying. With `restartOnCrash: false` it would stop after the first failure.
- So bare `npx --no-install sygnal-check lsp` in a project without sygnal-check costs up to **4 spawns a session**. Each is `npm exec`: it resolves the package against the registry (here it printed `npm error npx canceled due to missing packages and no YES option: ["sygnal-check@0.3.0"]`, so it went to the network), writes a new file to `~/.npm/_logs/`, and exits 1 after about a second.
- With **sygnal-check 0.3.x** installed, `sygnal-check lsp` treats `lsp` as a path: `no such file or directory: lsp`, `no source files found in lsp`, exit 2. The same crash path.

Run 2 (bare npx, no sygnal-check) would confirm this from the debug log; it is scripted but not run.

**The launcher** (`scripts/sygnal-lsp.mjs`, 90 lines, no dependencies):
1. Resolves `sygnal-check` from the working directory up (`createRequire(<cwd>/noop.js).resolve('sygnal-check')`), which is the copy `npx --no-install` runs. `SYGNAL_LSP_PROJECT` overrides the start directory.
2. Imports it in-process and calls `runLspServer({ cwd })`, the documented export that `bin/sygnal-check.js lsp` calls. One process, no npm, no registry lookup, no `npx.cmd` quirks on Windows.
3. If there is no package, it fails to load, or it has no `runLspServer` (0.3.x), it writes **one line** to stderr:

   ```text
   sygnal: no sygnal-check with a language server (>= 0.4.0) in this project, so Sygnal diagnostics are off for this session. Install it with `npm install -D sygnal-check` and start a new session.
   ```

   It then runs an **idle server**: `initialize` → `{ capabilities: {}, serverInfo: { name: 'sygnal (inactive)' } }`, `shutdown` → `null`, other requests → `-32601`, notifications ignored, exit on `exit` or stdin end. Claude Code sees a healthy server: one start, no crash, no restarts, no findings, and the skill works as before.

The capability test is the export, not a version number: this branch's sygnal-check is still `0.3.0` in `package.json` but has the server, and the real 0.4.0 will too.

**Why not the documented command in the manifest.** PLAN-7 and the brief name `npx --no-install sygnal-check lsp` as the manifest command. The launcher runs the same code (same package resolution, same entry point), and the tests pin that link: the README's start command, the CLI's `lsp` route to `runLspServer` in `src/lsp/server.js`, the export in `src/index.js`, and the launcher's `resolve('sygnal-check')`. The bare command stays the documented one for every other editor.

## 4. G-658: the finding after the last edit

**The question:** in 0-S2 runs 3 and 4, the SYG110 that stayed in `C.jsx` after the agent's last edit never reached the model, although (run 4) the server seemed to publish it before the tool result.

**Answer: a race in Claude Code between the server's publish and the attachment pass.** The debug-file run that would show it line by line (`LSP: Sent didChange`, `Received diagnostics from sygnal`, `LSP Diagnostics: Checking registry - N pending`) is run 1, not run (§5). The answer below comes from the 2.1.287 bundle and the 0-S2 run 4 session file, read again:

1. **The Edit tool** (and Write) does, in order: clear the file's delivered set, purge the file's pending entries, then `changeFile` + `saveFile`, both **fire-and-forget** (`.catch` only). The tool result returns without waiting for the server.
2. **The publish handler** registers each non-empty `publishDiagnostics` in the session's pending registry at once (path-keyed; no filter other than the stale-`version` check, which doesn't apply: sygnal-check sends no `version`).
3. **The attachment pass** (`lsp_diagnostics`, one of ~30 attachment generators computed together) runs in the query loop **after the tool batch ends** (after PostToolUse hooks and any PostToolBatch hooks), before the next model request. It drains the registry (`takePending`, then `clearPending`). Nothing else drains it; no other code removes pending entries.
4. **No pass, no delivery.** If the model ends its turn after the batch, no pass runs until the next user message. In `-p` the session ends, and the pending finding is dropped with it.

**0-S2 run 4 re-read with this:**
- Session file: the Read; then **both Edits in one assistant message** (streamed tool execution: Edit 1 result at 11:29:07.496, Edit 2 block at 11:29:08.352, result at 11:29:08.362); **one** attachment pass after the batch at 11:29:08.374 with A.tsx and B.tsx only; then the final answer. There was no pass between the two edits.
- Server log: its clock (`t0` in `0-S2/server.mjs`) starts **after** the server's top-level `await import()` of sygnal-check (Babel included), not at launch. The launcher logged 11:29:07.523, and Edit 1's tool result (11:29:07.496) came before even that: the spawn is fire-and-forget. `initialize` shows up at t = 1 ms, so Claude Code had been waiting through the import. Startup publishes at t = 26/31 ms (A, B, C) went pending; Edit 2's purge removed C's; `didChange`/`didSave` at t = 814 ms, the new C publish (`SYG110`) at t = 821 ms. The Edit tool sends `didChange` before it returns, so t = 814 ms is no later than Edit 2's result (11:29:08.362); that bounds `t0` to at most 11:29:07.548 and puts the publish (t = 821 ms) at or before about 11:29:08.369. So the publish fell **inside the ~12 ms window between Edit 2's result and the attachment message (11:29:08.374)**, the window in which the pass drains the registry (all generators start together and the LSP one drains synchronously when it starts; the message is written when all of them finish). A publish a few milliseconds after the drain matches the observation; one before it would have been delivered. The "19 ms before the tool result" in 0-S2 took the launcher's timestamp as the log's zero.
- A and B were delivered because they had been pending since the server started; C's own finding had been purged by the edit and re-published too late.

**What the server can change: nothing that fixes it.** It already checks at once on `didSave` (D306) in a worker. To win it would have to finish the whole-project check and get the notification through Claude Code's pipe within the ~10 ms between the tool result and the drain, every time. Larger projects make it worse. A small server-side gain (publishing the edited file's findings before the others) doesn't change the outcome either. No `sygnal-check/src` change.

**What the plugin can change: a settle hook.** Because the drain runs after the tool's `PostToolUse` hooks, a hook on `Edit|Write|MultiEdit` that waits (≈ 150–300 ms) lets the server's publish land first, so the edit's own findings reach the model with the very next request, including after the last edit of a turn, as long as the model makes one more request. (After the final answer there is no request, so a finding still can't arrive after the model has stopped.) Costs: the wait on every edit, Node's start-up (≈ 40 ms) if the hook is a `node -e` timer, and the hook is a no-op for non-Sygnal files only if it checks the extension. Better than a fixed wait: the server could write "checked through version N" to a small file in `$CLAUDE_PLUGIN_DATA` and the hook could wait for that, up to a cap.

Not shipped: run 4 (`settle-plugin`, 300 ms) would test it first, and E-1 should measure it as a variant (plugin vs plugin + settle hook), since it changes what "findings before the agent's last edit" (D308) means.

**For E-1 now:** on short fix tasks, expect the plugin to deliver almost nothing about the last edit; on feature tasks, the next tool call (a test run, a Read) carries it. Count per finding whether it arrived before the agent's last edit (D308) and whether a later tool call carried it.

## 7. Release steps (proposed for RELEASING.md)

How a plugin version reaches users: `/plugin marketplace add tpresley/sygnal` clones the repository's **default branch** (`main`); `#<ref>` would pin another. The plugin's source is a relative path, so its files come from that clone, and with `version` set in `plugin.json` that string is the plugin's version: Claude Code replaces an installed copy only when it changes. Users get it through `/plugin marketplace update sygnal` + `claude plugin update sygnal@sygnal`, or auto-update, which is **off by default** for third-party marketplaces (each user turns it on under `/plugin` → Marketplaces).

Proposed section:

> ### The Claude Code plugin (`editors/claude-code`)
>
> The marketplace (`.claude-plugin/marketplace.json`) is read from `main`. Users get a new plugin version only when `version` in `editors/claude-code/.claude-plugin/plugin.json` changes.
>
> 1. **When:** bump the plugin's `version` in any release that changes `editors/claude-code/` **or `skills/sygnal-dev/`** (the plugin's skill is a link to it). Patch for skill text or docs, minor for new plugin behaviour.
> 2. **Order:** publish sygnal-check first when the plugin needs a newer server (0.1.0 needs sygnal-check ≥ 0.4.0 for diagnostics; the skill works without it).
> 3. **Check:** `claude plugin validate editors/claude-code` (one expected warning: the skill symlink), `claude plugin validate skills`, `claude plugin validate --strict .`, and `npx vitest run test/p7-i1-claude-plugin.test.js`.
> 4. **Merge to `main` and push.** Then `claude plugin tag editors/claude-code --push` creates and pushes `sygnal--v<version>` (it checks that `plugin.json` and the marketplace entry agree; `--dry-run` first). The tag is for plugins that depend on this one and for history; installs follow `main`.
> 5. **Smoke test:** in a scratch `CLAUDE_CONFIG_DIR`, `claude plugin marketplace add tpresley/sygnal`, `claude plugin install sygnal@sygnal`, `claude plugin details sygnal@sygnal` (Skills 1, LSP servers 1).
> 6. CHANGELOG: a line under the sygnal-check or sygnal release that ships it.

> ## Claude Code
>
> The Sygnal plugin gives Claude Code the `sygnal-dev` skill and runs sygnal-check's language server, so Claude sees wiring findings after it edits a file, without running the checker itself.
>
> ```text
> /plugin marketplace add tpresley/sygnal
> /plugin install sygnal@sygnal
> ```
>
> It needs `sygnal-check` 0.4.0 or later in the project (`npm install -D sygnal-check`; `create-sygnal-app` projects have it). Without it the plugin stays quiet and only the skill works.
>
> **How the findings arrive.** The server starts on Claude's first edit of a `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs` or `.cjs` file and checks the whole project. Claude Code adds new findings to Claude's next request after a tool call, as a short list (at most 10 per file, 30 at a time, errors first), each finding once per session. They are the CLI's messages, `Component: problem (fix)`, so they make sense without the docs link, which Claude Code doesn't pass on. Findings in files Claude didn't touch are included, so a project that already has findings shows them after the first edit. A finding left by Claude's last edit in a turn can arrive only after your next message.
>
> **Settings.** The plugin sends none: the project's `sygnal-check.config.json` decides, as for the CLI and CI.
>
> **Turning the findings off.** Disable the plugin for the project (`"enabledPlugins": { "sygnal@sygnal": false }` in `.claude/settings.local.json`), or load a local copy of `editors/claude-code` with `"diagnostics": false` in its `lspServers.sygnal`.
>
> **The MCP server** isn't part of the plugin. To add it: `claude mcp add --scope project sygnal-check -- npx --no-install sygnal-check mcp`.
>
> The language server works the same way in other editors; see [VS Code](#vs-code) and [other editors](#other-editors).
