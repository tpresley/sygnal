# PLAN-7 spike 0-S1: ranges

Branch `exp/p7-s1` (from `plan7-integration` at eb208337). Question (PLAN-7 §2 Phase 0): for every
sygnal-check rule, which AST node is its diagnostic reported at today, which node should an editor
underline, and how much work is C-2 (end ranges)?

## Summary

- **C-2 is cheap because the runner already has the node.** Every rule reports through one
  `report({ code, file, node, ... })` callback (`sygnal-check/src/rules/index.js`); `runRules()`
  (`src/run.js`) turns `node` into `line`/`column` with `loc(node)`. No rule computes a position by
  hand. Adding `endLine`/`endColumn` from `node.loc.end` in the runner gives all 57 rule codes a range
  without touching a rule. The prototype does exactly that (+ SYG900 parse errors: the parser's
  position, one character).
- **For 45 of 58 codes the node a rule reports today is already the right underline** (the selector
  string, the model/intent key, the JSX attribute, the static's `X.static` member, the misspelled
  identifier). The test suite produces 1,111 findings across all 57 rule codes: none of them has a
  multi-line range after the prototype, and the longest underline is 62 characters (a SYG505 raw EVENTS function).
- **13 codes needed a better node** (wide or multi-line today); all 13 are converted on the branch:
  9 trivial (the right node was in hand), 3 small (find a key in an object), 1 trivial-by-runner
  (SYG900 parse error). One sub-case is **hard**: SYG900 for a rule that *crashed* has no file and no
  node at all.
- **Moving a node's start can break existing `// sygnal-ignore` comments** (the comment matches the
  start line or the line above). Three narrowed codes can move the start to a later line (SYG731,
  SYG152, SYG422). The prototype adds an optional `anchor` (the old, wide node) whose line is also
  matched; `suppress-check.mjs` proves an old comment still works. C-2 should keep this.
- **`npm --prefix sygnal-check test` stays green: 714/714, no snapshot updated.** The two snapshot
  files hold the `file:line:col CODE message` text (`formatDiagnostic`), not the diagnostic objects,
  so the added fields don't show; the narrowed nodes start on the same line and column in every
  snapshotted case (the moved starts are all in rules whose tests assert lines only).
- **Effort for C-2: about 2 days** (1.5–2.5), most of it tests and docs, not rule changes (see below).

## What the prototype changes (`sygnal-check/src`)

| File | Change |
|---|---|
| `ast.js` | `endLoc(node)` → `{ endLine, endColumn }` (1-based, **endColumn exclusive**, i.e. `node.loc.end.column + 1`); without a location a one-character range at the start |
| `diagnostic.js` | `makeDiagnostic` copies `endLine`/`endColumn` when given (after `column`, so `--json` key order stays line, column, endLine, endColumn) |
| `run.js` | `report()` adds `...endLoc(r.endNode \|\| node)`; optional `r.endNode` ends the range at another node (`<img` = opening element .. its name); optional `r.anchor` also matched by suppressions; SYG900 parse error gets `endColumn = column + 1`; a `SYGNAL_RANGE_LOG` hook (spike only, remove in C-2) logs each range for the audit script |
| `model/modelEntries.js` | `sinkValues[]` carry `keyNode` (the sink key: `HTTP:` or the `'A \| HTTP'` shorthand key) |
| 12 rule files | the 12 narrowed codes below (marked `// C-2` in the source) |
| `rules/index.js` | the `report()` contract documents `endNode` / `anchor` |

Column units: Babel's columns count UTF-16 code units, which is LSP's default `positionEncoding`, so
the server can pass `line - 1`, `column - 1`, `endLine - 1`, `endColumn - 1` straight through.

## Recommendation

1. Take the prototype's shape for C-2: the range comes from the node in the runner; rules keep
   `report({ node })`, with two optional fields: `endNode` (end the range elsewhere: `<tag`) and
   `anchor` (an older node whose line suppressions still match). `makeDiagnostic` takes the end as
   data (`endLine`/`endColumn`), so the SYG900 paths without a node can pass a loc. Exclusive
   `endColumn`, UTF-16 columns.
2. Keep the 13 narrowed codes (all on `exp/p7-s1`); cherry-picking the `sygnal-check/src` diff
   minus the `SYGNAL_RANGE_LOG` hook is a fair start for C-2.
3. Add the range assertions before more narrowing; the plan's "range snapshot test per rule
   fixture" is best done as underlined text in the existing snapshots plus one assertion per code.
4. Decide whether `related` is part of C-2 or C-3. The pair and cross-file codes look fine without it
   (the squiggle is on the side to edit), so it is not a blocker.
5. No rule needs a new analysis to get a good range; nothing here changes PLAN-7's ordering
   (C-4 after C-2 still holds: SYG505's range coincides with its `--fix` edit, which C-4 can use).
