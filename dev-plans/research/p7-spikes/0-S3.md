# PLAN-7 spike 0-S3: positions (sizing N-1 / N-2)

2026-10-10, branch `exp/p7-s3` (from `plan7-integration` at eb208337). Question: what does the project model already keep for each entity N-1 needs, what is missing, and what N-2's features would cost. Input for P7-Q6.

`sygnal-check/src` is **unchanged**. The prototype reads the model through the existing API; the recovery experiment subclasses `Project` to read one file from memory (the throwaway form of L-1's `readFile` overlay).

Spike code: [`0-S3/positions.mjs`](0-S3/positions.mjs), [`0-S3/recovery.mjs`](0-S3/recovery.mjs), an edge-case fixture [`0-S3/fixture/`](0-S3/fixture), and the raw outputs `0-S3/out-*.txt`.

## Summary

- **Actions are nearly free.** Every action occurrence the model collects already keeps its AST node: intent keys, model keys, `next('X')`, `ok:`/`error:`/`delta:`/`tool:`/`block:`, `decide()` replies, `connections`/`resources`/`route`/`timers`/`browser` names, `agent.actions` keys. On the three examples the prototype located all **289** host-side occurrences (43 more are first-party behavior actions, which have no source). What's missing is a range helper (the model has `loc()`, start only), a per-name index, sub-ranges for `'A | SINK'` keys, and nodes for behaviors' own actions.
- **The rest is partly kept.** EVENTS, selectors, children and Collection `from` keep their nodes. **Lost:** the view's class/id tokens (a `Set` of names), `calculated` and `context` keys (sets of names), context consumption (computed in `graph.js`, names only), and behavior definitions' actions (`Map<string, sinks>`). The class/id tokens are the only large piece: the names go through `strings.js`, which deals in strings, not nodes.
- **`errorRecovery` doesn't help mid-edit.** `parseSource()` already passes `errorRecovery: true`. It only recovers *semantic* errors. Every syntax error a user makes while typing still throws: 0% usable on every edit that breaks syntax. A repair suffix at the cursor gets 100% on the realistic mid-edit cases. The text before the cursor, read with the last good AST, classifies the completion context correctly 100% of the time (99% on truncated files).
- **Estimate: N-1 ≈ 5 days. N-2:** completions ≈ 4, definition/references ≈ 2, rename ≈ 3, code lens ≈ 1. Total about **15 days** (range 11–19).
- **Recommended order:** completions (they barely need N-1), then the actions part of N-1 with definition/references and code lens, then the rest of N-1, then rename last.

## 1. Entities: where the model builds them, and what's kept

"Node kept": the model structure holds the AST node, so `node.start/end` and `node.loc` give a range. Babel's columns are UTF-16 code units, the same unit LSP positions use, so no conversion is needed.

## 2. Prototype results (`positions.mjs`)

`node dev-plans/research/p7-spikes/0-S3/positions.mjs <dir> [--all]` builds the project with `buildProject` and prints, for each action of each component, every occurrence with `file:line:col-endCol` and its role (intent / model / next / reply / agent). With `--all` it also prints selectors with the view tokens they match (re-derived), EVENTS, Collection `from` → `initialState` key, context provided (re-derived) and children.

|---|---|---|---|---|---|---|---|

| examples/ai-panel-spa | 13 | 5 | 30 ms | 25 | 55 | 17 intent, 24 model, 14 next | 0 |

Sample (kanban, `--all`): `.lane-title` at `LaneComponent.jsx:50:30-41` matches the view token at `:19:28-38`; `DELETE_LANE` is emitted at `LaneComponent.jsx:100:33-44` and selected at `RootComponent.jsx:67:35-46`; `<Collection from="lanes">` at `RootComponent.jsx:20:46-51` maps to the `initialState` key at `:27:3-8`.

**What it couldn't locate with the current model:**
- **First-party behavior actions** (`history.UNDO`, `sort.MOVE`, ...): there's no source. Point at the `uses` entry's key instead.
- **User behaviors' own `next()`/reply names** (3 in plan5-showcase: `COMMIT`, `SAVE`, `SIGN_UP`): `def.nextTargets` / `replyTargets` are `string[]`. The `form` behavior's `submit: 'SIGN_UP'` option *is* locatable through `entry.options` (node kept), but nothing links it to the name.
- **A user behavior's model keys**: located only by re-running `analyzeModel` on the `defineBehavior` options (the prototype does this for `c.RESET`).
- **A computed intent key** (`[ACTIONS.TICK]`): dropped, so the intent is `known: false`.
- **Constant-built names:** `next(PREFIX + '_DONE')`, `` next(`${PREFIX}_MORE`) ``, and `EVENTS.select(SAVED)` with `SAVED` imported. All are dynamic: the node is kept, the name isn't.
- **`undoable()`'s UNDO/REDO:** located only at the `undoable` identifier (synthetic).
- **Not actions:** the view's class/id tokens (re-derived only for literal `className`/`id` on intrinsic elements), `calculated` keys, context consumption. Collection `from` in a collection item without `initialState` (kanban's Lane `from="tasks"`) has no target: its state comes from the parent's lens.

## 3. Error recovery (`recovery.mjs`)

For every completion site in the three examples (intent keys, model keys, selector strings, `next`/reply literals, Collection `from`, `className` strings), the script applies the edits a user makes while typing there. It then tries three ways to get a usable context at the cursor:
- **A:** parse as is, with `errorRecovery` (today's `parseSource`).
- **B:** if A throws, insert a repair suffix at the cursor (`'`, `"`, `'),`, `0,`, ` }`, …, or close everything left open) and retry.
- **C:** don't parse: classify the text before the cursor on its line with regexes. The *which component / which static* half comes from the last good AST.

"Usable" (A, B) means:
- the file parses;
- the component is still discovered with its intent and model;
- no more than one action is lost;
- the cursor is inside the component's intent, model or view.

1,966 edits:

| Edit | n | A: errorRecovery | B: + repair suffix | C: line prefix + last good AST |
|---|---|---|---|---|
| `autoclosed`: `DOM.click('\|')` (editor auto-closes quotes) | 366 | 100% | 100% | 100% |
| `unterminated`: `DOM.click('.ad\|` (no auto-close) | 366 | **0%** | 100% | 100% |
| `key-typing`: `{ NE\|⏎ OLD: … }` | 251 | **0%** | 100% | 100% |
| `key-colon`: `{ NEW: \|⏎ OLD: … }` | 251 | **0%** | 100% | 100% |
| `open-call`: `{ X: DOM.click('\|⏎ OLD: … }` | 115 | **0%** | 100% | 100% |
| `truncate`: nothing after the cursor (worst case) | 617 | **0%** | 14% | 99% |
| **all** | 1,966 | 19% | 73% | 100% |

- **A fails on every syntax error.** Failures: 984 `UnexpectedToken`, 616 `UnterminatedString`. Babel's `errorRecovery` covers errors such as duplicate declarations or a misplaced `return`, not unterminated strings or missing values. Its 19% is just the edits that leave the syntax valid.
- **B:** repairs that worked: `"` 243, `: 0,` / `0,` 251 each, `'` 122, `'),` 115, ` }` 70, close-all 16. Every realistic mid-edit case recovers (the rest of the file is intact). Truncation doesn't: open JSX elements and apostrophes in JSX text defeat a naive bracket closer, and the statics after the cursor are gone anyway.
- **C** is right 100% of the time on everything but truncation, where 5 of 617 cursors sit right after a bare quote at a line start. It can't see which object it's in (intent vs model vs `agent.actions`), so it needs the last good AST. Map the cursor offset through the edits since the last good parse (LSP `didChange` gives the ranges); offsets before the edit don't move.

**Recommendation for completions:**
1. Try a normal parse.
2. Else try B's few repairs at the cursor, each a single-file parse plus discovery (the whole run, 1,966 edits with up to 20 attempts each, took 1.9 s).
3. Else fall back to C with the last good file model.

The server needs the last good AST per file anyway (L-1: "a parse error … keeps the other files' findings").

## 4. What each N-2 feature needs

### Completions
- **Cursor context:** the parse → repair → last-good + line-prefix chain above, then the deepest node at the cursor, walking up to:
  - a key of the intent's returned object;
  - a key of the model object or of a model entry's sink object;
  - the string argument of `DOM.<event>(…)` / `DOM.select(…)` (`domChain` in `intent.js` already recognises it);
  - `EVENTS.select(…)`, `next(…)`, a reply key (`ok:` …) in a request object, a timers spec's `action`;
  - `from="…"` on a Collection.
- **Sources:** names the model already has, so this barely depends on N-1:
  - intent action names, for model keys;
  - `viewInfo.classes/ids.names` and controls, for selectors;
  - `project.events.emitted` types, for `EVENTS.select`;
  - model entry actions, for `ok`/`error`/`next`;
  - `initialState` / `calculated` keys, for `from`.
- **Positions needed:** only the range of the token being completed (a `textEdit` replacing the string contents), which comes from the buffer.
- **LSP:** `completionProvider` with trigger characters `'` `"` `` ` `` `.` `#`. Returning items only in these contexts avoids competing with TypeScript elsewhere.

### Definition / references
- An index per file: an interval list `{ start, end, kind, name, component }` for each occurrence. Position → occurrence by binary search. From there to the rest by `(component, name)` for actions, or `(project, type)` for EVENTS.
- Directions:
  - intent key ↔ model entry ↔ `next`/reply/`agent`;
  - selector token → view token(s) and control declaration;
  - `EVENTS.select('X')` ↔ emitters across files;
  - `from` → `initialState` key;
  - context consumer → provider (needs the ancestor search).
- Everything except view tokens, context and behavior actions is available today (§2).

### Rename
- **Occurrences of an action:**
  - intent key, model key (sub-range for shorthand), `next('X')`;
  - reply names (`ok`/`error`/`delta`/`tool`/`block`, `decide()`), `connections`/`resources`/`route`/`timers`/`browser` names;
  - `agent.actions` key;
  - a host's `'key.ACTION'` entries;
  - for an EVENTS type, every emit and select in the project.
- **Refuse (`prepareRename` returns an error):**
  - the cursor's component has `intent.known` or `model.known` false (spreads, computed keys);
  - the name has dynamic uses in the same component (`dynamicNext`, `replyDynamic`, `connections.dynamic`);
  - EVENTS: any `dynamicSelected` / `dynamicEmitted` in the project (they're global), or an `implicit` select (`Toaster`'s `TOAST`);
  - names built from constants (`[ACTIONS.TICK]`, `next(PREFIX + …)`, `select(SAVED)`). Either refuse, or (later) rename the constant's value when it has exactly one definition;
  - built-ins (`BOOTSTRAP`, `INITIALIZE`, `DISPOSE`, `READY`, `RESOURCE`) and synthetic UNDO/REDO;
  - first-party behavior actions (`pager.NEXT`), and a user behavior's actions when the behavior is used by more than one component (v1);
  - a model object shared by two components: dedupe edits by node, and include both components' intents or refuse.
- **Warn, don't refuse:**
  - `agent.actions` keys: renaming changes the tool name the LLM sees;
  - tests and other files outside the scan. Example tests are excluded by default (`includeTests`), and kanban's tests reference `model.START_EDIT(...)` and `describe('START_EDIT')`. Rename should scan test files with `includeTests` for member-access/string uses and offer them as a separate, unchecked change group (`WorkspaceEdit` change annotations with `needsConfirmation`).

### Code lens (optional)
- On intent keys: "handled by model · emits EVENTS 'X' · next → Y", or "no model entry".
- On model keys: "triggered by intent / reply / next / agent".
- Built on the same index; the graph already computes `trigger` and sinks.
- Client support varies: as far as I know, Helix has no code lens, and Neovim needs `vim.lsp.codelens.refresh()`. Verify in 0-S2's matrix.

## 6. Risks

- **Rename can break apps silently.** These are string-wired seams: a missed occurrence is a dead action at runtime with no type error. The refusal rules must err on refusing. The main gap is files outside the scan (tests, other packages, docs samples).
- **No AST mid-edit.** `errorRecovery` doesn't cover syntax errors. The repair suffixes are heuristics measured on three example apps; JSX text and unusual formatting will produce misses. The last-good-AST fallback degrades gracefully but can be stale after large edits.
- **Duplicates with TypeScript.** In fully typed TSX (`ActionsOf<typeof intent>`, the `SygnalEvents` registry), TS completes some of these strings too, so VS Code may list both. The research leaves a tsserver plugin as a later option.
- **Ownership ambiguity:**
  - a model object shared by components, or an intent defined in another file;
  - helper-function JSX counted in several views;
  - behaviors' namespaced names, and first-party behaviors without source.
  Definition can show several targets; rename must refuse.
- **Class tokens in dynamic expressions** (template literals, `clsx`, `classes()`, spreads) are only partly locatable. Selector → element will sometimes have no target; it should then say "dynamic className in the view" rather than nothing.
- **Latency.** Completions and navigation need a fresh model per request. That's 8–47 ms warm on the examples (ide-tooling.md re-measure); a large project needs L-1's per-file cache, and probably a cached model between keystrokes.
- **Client variance:** `prepareRename`, change annotations, code lens and completion trigger characters differ across VS Code, Neovim, Helix, LSP4IJ and Claude Code (which uses no completions at all). That limits N-2's value for agents: E-1 can't measure it.

## 7. Recommended order (value per day)

1. **Completions** (4 days, little of N-1). The most visible gain, and it's for JS/untyped users, who get nothing today (`DOM` is `any`). It needs the cursor-context chain and names the model already has.
2. **N-1, the action part** (about 1.5 days: range helper, index, shorthand, synthetic) **+ definition/references for actions and EVENTS** (about 1.5 days). Nodes are already kept, so it's cheap and needed by everything after it.
3. **Code lens** (about 1 day) on the same index. Cheap, but only where clients support it.
4. **The rest of N-1** (view tokens, context, behaviors, constants: about 3 days) and the definition/references it enables: selector → element, context → provider.
5. **Rename last** (3 days). It has the highest risk of doing harm, needs the most complete index, and a refused rename is no worse than today.

If P7-Q6 approves only part: steps 1–2 (about 7 days) deliver completions and action/EVENTS navigation, the bulk of the research's §5 items 3–4, without rename.
