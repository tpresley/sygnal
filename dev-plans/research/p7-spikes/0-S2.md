# 0-S2: the PoC server in real clients

Spike for PLAN-7 §2 0-S2, 2026-10-10, branch `exp/p7-s2` (from `plan7-integration` at `eb208337`).

**Question:** which LSP features do the real clients use, and how does Claude Code surface plugin LSP diagnostics to the model? L-1 targets the answers, and E-1's design depends on the second.

**Short answers:**
- **VS Code 1.138** (`vscode-languageclient` 10.1.2): it supports everything L-1 plans. But **when a server offers both push and pull diagnostics, VS Code uses both and shows every finding twice.** With pull only, files the user hasn't opened get no findings, so the cross-file findings that are the point of Sygnal's checker disappear. **L-1 should push, and not offer pull to a client that also gets pushes.**
  - Watched files and configuration need **dynamic registration from the server** (`client/registerCapability`).
  - Folder-level settings need `"scope": "resource"` in the extension's `contributes.configuration`.
- **Claude Code 2.1.287:** diagnostics reach the model **as an attachment**: a `<new-diagnostics>` system reminder added to the *next* model request after a tool result. They are not part of the tool result, there is no tool call involved, and they never appear in `--output-format stream-json`.
  - **No flag is needed.** `ENABLE_LSP_TOOL=1` changed nothing; the (deferred) `LSP` tool was offered without it.
  - The server is spawned **at the first Edit/Write of a matching file**, not at session start and not on Read.
  - Claude Code delivers each identical finding once per session, from every file the server publishes, not only the edited one. It caps an attachment at 10 findings per file and 30 in total, errors first.
  - It drops `codeDescription`, `data` and `relatedInformation`, and has no code actions at all.
- **Neovim, Helix, LSP4IJ:** not installed. Configuration snippets from their current docs are in §5, all **untested**.

Spend: **$0.1375** for 4 Haiku runs (§8).

## 3. VS Code findings

1. **Push plus pull duplicates everything.** With both offered, VS Code 1.138 pulled `C.jsx` (`identifier: 'sygnal'`) and also kept the pushed set: 6 sygnal findings instead of 3, and two identical "Change to '.inc'" quick fixes. vscode-languageclient keeps pull and push in separate diagnostic collections. Push only: 3 findings, one fix. Pull only: 3 on the open file, but **0 on unopened files** (`A.tsx`, folder `b`'s `C.jsx`), and **0 for a new file written on disk** (`D.jsx`).
2. **Cross-file findings need push** (or `workspace/diagnostic`, which neither LSP4IJ nor Claude Code supports). A Sygnal edit in one file can break another (EVENTS, child components, Collections), and only push puts the finding on that other file.
3. **Pull is cancelled on every keystroke.** With a 400 ms artificial pull delay, 4 of 9 pulls were cancelled (`$/cancelRequest`) as edits arrived. The server answered with `-32800` and VS Code re-pulled. A real server must keep checks cheap and answer cancelled requests rather than drop them.
4. **Dynamic registration is required.** Without `synchronize.fileEvents` in the client, VS Code sends `didChangeWatchedFiles` only for watchers the server registers. It accepted `**/*.{js,jsx,ts,tsx}`, `**/sygnal-check.config.json` and `**/package.json` and reported the new `D.jsx`. Likewise `didChangeConfiguration` arrives only after the server registers it (`registerOptions: { section: 'sygnal' }`). VS Code then sends it straight away and on each change, but with window-scoped values, so the server should treat it as a signal to re-request `workspace/configuration` per folder.
5. **`workspace/configuration` works per folder**, provided the extension contributes its settings with `"scope": "resource"`. Under the default (window) scope, folder `a`'s `.vscode/settings.json` value came back as `null`. A setting update made through the API (`strict: false` at workspace level) produced a `didChangeConfiguration` and fresh per-folder values.
6. **Round trips work.** `codeDescription.href` is rendered as a link on the code. `relatedInformation` and `data` came back intact in `codeAction.context.diagnostics`, so C-4's fix edits can travel in `data`, as L-1 says.
7. **Noise to tolerate:**
   - `$/setTrace` notifications (10 per session);
   - frequent automatic `codeAction` requests (`triggerKind: 2`, `only` unset, usually without our diagnostics) on cursor moves and edits;
   - the built-in TypeScript server's own findings beside ours.

   Copilot's "Fix"/"Explain" actions appear next to the server's quick fixes in 1.138 (built in).
8. The CLI is not needed: `@vscode/test-electron` launched `/Applications/Visual Studio Code.app/Contents/MacOS/Code` directly. On macOS, `--user-data-dir` must be short, or the IPC socket path exceeds 103 characters and VS Code exits. The runner uses `os.tmpdir()`.

### 4.2 How diagnostics reach the model

Observed in the stored session files and confirmed in the 2.1.287 bundle (`strings` on the binary; the identifiers are minified):

- **Passive push only.** Every `publishDiagnostics` (non-empty, not stale by `version`) is registered in a per-session pending registry "for async delivery".
- **Delivered as an attachment.** When Claude Code builds the next model request after a tool use, it drains the registry into one `{ type: 'diagnostics', files, isNew: true }` attachment. The model sees it rendered as `<new-diagnostics>The following new diagnostic issues were detected: …` inside a system reminder. It is **not** the tool result, **not** an `LSP` tool call, and **not emitted in `--output-format stream-json`**: the only record is the session file. (`captures/claude-code-diagnostics-attachment.json` has the shape: `uri` is a plain path; `severity` is `"Error"/"Warning"/"Info"/"Hint"`; `code` is a string; `source` is kept.)
- **Deduplicated per session:** key = message + severity + range + source + code, per file (an LRU of 500 files). An identical finding is delivered once. Editing a file clears its "delivered" set and purges its pending entries, so findings for that file can be delivered again.
- **Volume limit:** per attachment at most **10 per file and 30 in total**, sorted errors first. The plugin option `diagnostics: false` turns the injection off and keeps the navigation tool.
- **Not just the edited file:** anything the server publishes is delivered, so a whole-project push puts other files' pre-existing findings in front of the agent (runs 1–4 all did).
- **No waiting.** The attachment is built a few milliseconds after the tool result (3–12 ms in the runs). Claude Code doesn't wait for the server to re-check, so findings from edit *N* reach the model only with the request after the next tool call. After a turn's **last** edit, nothing triggers another request: the finding stays pending until the user's next message.
- **Start-up:** the server is spawned when the first Edit/Write touches a mapped extension. `didOpen` carries the **post-edit** text, so the first edit's own findings can't make the request that follows it.
- **The `LSP` tool** (definition, references, hover, document/workspace symbols, call hierarchy) is listed without any flag, as a **deferred** tool (the model must load it with ToolSearch). Haiku never used it in four runs. `ENABLE_LSP_TOOL` still exists in the env-var table but changed nothing observable.

**Open:** in runs 3 and 4, the SYG110 that remained in the edited file after the last edit was never delivered. In run 4 it was even published before the tool result. The bundle code doesn't explain this:
- the Edit tool purges the file's pending entries *before* sending `didChange`;
- the finding had never been delivered before.

The likely explanations are ordering inside Claude Code (the notification is processed after the purge or after the attachment is built) or an undocumented filter. One more run with `--debug-file` would settle it: it logs `LSP Diagnostics: Registering …`, `Purged …`, `Deduplication removed …`. It costs about $0.03 and wasn't run because of the 4-run cap. It matters for E-1: it decides whether an agent sees the finding on the line it just wrote.

### 4.3 What it means for E-1

- **Count diagnostics from the session file**, not from the stream-json transcript: the `diagnostics` attachments in `~/.claude/projects/<slug>/<session>.jsonl`. `lib/headless.mjs` needs to find that file (session id from the stream's `init`/`result` events) and copy it next to the run. The "transcript counter for LSP diagnostic events" in §1.6 should count attachments, findings per attachment and their codes.
- **Expect delivery one tool call late, and none after the final edit.** On feature tasks the agent usually runs tests or reads more after editing, which gives the attachment a turn to arrive. On short fix tasks it often ends right after the last edit (runs 1–4), and the plugin then contributes nothing. Measure "findings delivered before the agent's last edit" as well as totals.
- **Noise from untouched files is real:** each run delivered the other fixture files' findings. In real apps with pre-existing findings, every session starts with up to 30 of them after the first edit. E-1's fixtures should be clean at the start (the tier tasks are), or the arm measures noise.
- **No flag in the variant;** `--setting-sources project,local` plus `--plugin-dir` is enough. The plugin must not depend on user settings: the LSP config must come from the plugin itself.
- **Isolation check:** with `--setting-sources project,local`, user-installed plugins didn't load; only built-in `cc-plugin-*` plugins and the probe did (stream `init` event). The `plugins` variant field can rely on `--plugin-dir`.

### 4.4 What it means for I-1 (the plugin)

- The manifest shape works as planned. Put `lspServers` **inline in `plugin.json`**, because `claude plugin validate` checks inline configs but doesn't read `.lsp.json` (docs). Unknown keys inside an `lspServers` entry are errors.
- **Add `"settings": {}`** (even empty) so Claude Code advertises `workspace/configuration`; otherwise the server gets no configuration channel. `initializationOptions` is the simpler channel in this client.
- Consider **`"startupTimeout"`** (a cold check is about 25 ms here, but `npx --no-install` adds process start-up) and `"restartOnCrash": true` (the default).
- Nothing in the plugin can make delivery earlier. The server side can (§6): publish quickly after `didSave`, and push only what changed.
- `codeDescription` and the fix text in `data` don't reach the model. **The message must stand alone:** the component name, the problem and the fix ("did you mean '.inc'?"), as L-1 already specifies ("the fix text in the message"). The docs link can't be relied on in this client.

## 6. Requirements for L-1 (what it should implement)

Changes to PLAN-7's current text are marked **(change)**.

1. **Push diagnostics, always (change).** PLAN-7 §1.2 says "pull diagnostics as well as push". That duplicates findings in VS Code, and pull alone loses cross-file and unopened-file findings. Instead:
   - **push by default to every client;**
   - offer pull (`diagnosticProvider`) only when `initializationOptions.diagnosticMode === 'pull'` (or a setting) and **then stop pushing**;
   - if pull mode is kept, it must also implement `workspace/diagnostic`, or the pulled view is incomplete.

   It's simpler to drop pull from 0.4.0 and keep it as a follow-up: every client in the matrix supports push.
2. **Publish soon after `didSave`; don't hold a 150 ms debounce for agent edits.** Claude Code sends `didChange` and `didSave` together for each edit and builds its next request about 10 ms after the tool result. Debounce `didChange` without `didSave` (keystrokes) at ≈150 ms, but check **immediately on `didSave`** (a whole-project check is a few ms here, under 100 ms on plan5-showcase). This doesn't guarantee delivery (§4.2, open), but a debounce guarantees lateness.
3. **Publish only what changed (change, minor).** Today the PoC re-publishes every file on every check. Keep the last published set per URI and send a file only when its list changed, or an empty list when it cleared. This cuts traffic in every client, and in Claude Code it avoids re-registering identical sets, which its dedup would drop anyway.
4. **Order findings by severity in each file, and keep messages self-contained:** component name, problem, fix. Claude Code shows only the first 10 per file, errors first; it drops `codeDescription`/`data`/`relatedInformation`. VS Code renders the extras, so keep sending them.
5. **Register `workspace/didChangeWatchedFiles` dynamically** when `capabilities.workspace.didChangeWatchedFiles.dynamicRegistration` is true. Use relative patterns per folder when `relativePatternSupport` is set: `**/*.{js,jsx,ts,tsx}`, `**/sygnal-check.config.json`, `**/package.json`. Without that capability (Claude Code, Neovim on Linux), rely on `didSave`/`didChange` and re-read the disk on every check: the C-3 cache is keyed by content, not by watcher events.
6. **Configuration:**
   - read `initializationOptions` at start-up (every client sends them);
   - if `workspace.configuration` is true, request `section: 'sygnal'` per workspace folder (`scopeUri`) after `initialized`, and again on any `didChangeConfiguration`; ignore that notification's payload, because VS Code's is window-scoped;
   - register `workspace/didChangeConfiguration` dynamically when the client supports it, or VS Code never sends it;
   - V-1 must contribute every `sygnal.*` setting with `"scope": "resource"`.

   Precedence, as L-1 says: editor settings over the C-5 file; an unset (`null`) value means "the file decides".
7. **Workspace folders:** use `params.workspaceFolders` when present, even if the client advertises `workspaceFolders: false` (Claude Code does, and still sends one folder). Otherwise use `rootUri`, then `rootPath`, then the cwd. Support `workspace/didChangeWorkspaceFolders` when advertising `changeNotifications`.
8. **Cancellation:** keep a per-request flag. Answer a cancelled request with error `-32800` (RequestCancelled), and answer `$/cancelRequest` for already-answered ids by ignoring it. VS Code cancels pending requests on every edit.
9. **Accept and ignore unknown notifications** (`$/setTrace`, `$/…`), and answer unknown requests with `-32601`. The PoC logged `$/setTrace` as unhandled, which is harmless only because it's a notification.
10. **Exit cleanly without `exit`.** Claude Code sends `shutdown` and then closes the pipe or kills the process. Exit on stdin end; never leave a timer keeping the process alive.
11. **Code actions are cheap and selective.**
    - VS Code fires automatic `codeAction` requests (`triggerKind: 2`) constantly. Return `[]` fast when the context has no `source: 'sygnal'` diagnostics and `only` doesn't ask for `source.fixAll*`.
    - Use the `data` round trip (works in VS Code) for C-4 edits, and fall back to recomputing from the message when `data` is missing (LSP4IJ/Helix untested; Claude Code has no code actions).
    - Answer `only: ['source.fixAll']` as well as `source.fixAll.sygnal`, since `editor.codeActionsOnSave` sends the prefix.
12. **Hover:** markdown when `textDocument.hover.contentFormat` includes it (all tested clients), plaintext otherwise. Claude Code's LSP tool can call hover, which is the one place the `explain` text could reach an agent on demand.
13. **Don't assume a client capability you didn't check** (I-2's rule holds). The two places it bites: dynamic registration (only VS Code and LSP4IJ), and `workspace/configuration` (Claude Code only with `settings`).

## 7. Surprises

1. VS Code duplicates diagnostics when a server offers both models. Nothing warns about it; it looks like a server bug.
2. Claude Code's diagnostics are invisible in `stream-json`: they live only in the stored session file. A harness that reads the stream would conclude "no diagnostics reached the model".
3. Claude Code spawns the server on the first **edit**, not on Read or at start-up, so the first edit never gets its own findings in time.
4. Claude Code delivers findings for files the agent never touched, as soon as the server is running: whole-project push meets "new diagnostics" semantics.
5. Claude Code sends `didSave` with every edit and never sends `exit`.
6. Claude Code advertises `workspace/configuration` only when the plugin declares `settings`, and advertises `workspaceFolders: false` while sending a `workspaceFolders` array.
7. VS Code's default setting scope silently ignores folder-level values in a multi-root workspace.
8. `ENABLE_LSP_TOOL` is still in Claude Code's env-var table, but in 2.1.287 the tool is present without it.
9. The **open** item in §4.2: a finding left in the file by the model's last edit was never delivered, even when published before the tool result.
